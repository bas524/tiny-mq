# verify

Критерий «сделано» для контура «Верификация».

## Процедура

0. **Куда писать вывод.** Все прогоны сохраняются в файл: `evidence` в пакете передачи — это
   **путь к логу, а не проза о нём** (Стандарт 15):
   ```
   mkdir -p handoffs/current/<spec>/logs
   ```

1. **Сборка** (проверочная конфигурация):
   ```
   cmake --build --preset debug --parallel 2>&1 | tee handoffs/current/<spec>/logs/build.log
   ```

2. **Все тесты:**
   ```
   ./cmake-build-debug/tiny_mq --gtest_filter='-*Bench*' 2>&1 | tee handoffs/current/<spec>/logs/verify.log
   ```
   Один набор: `./cmake-build-debug/tiny_mq --gtest_filter=<идентификатор>`.

3. **Чистота сборки.** Предупреждения — по политике проекта. Если предупреждения считаются ошибками,
   чини причину, не подавляй.
   Перед отправкой C++ тестов в PR проверь, что Debug-сборка запустила `clang-tidy` по
   [PROJECT.md](../../../PROJECT.md). GCC с `-Werror` требует фигурные скобки вокруг
   условного `EXPECT_*` или `ASSERT_*`. Сохрани результат вместе с логом сборки.

4. **Сборка в конфигурации поставки**, если она отличается: `cmake --build --preset release --parallel`, вывод в
   `logs/build-release.log`. Конфигурация поставки видит то, чего не видит проверочная:
   отключённую отладочную трассировку, другие флаги.

## Критерий прохождения

- сборка в обеих конфигурациях без ошибок;
- все тесты зелёные (0 failed).

## Что возвращать (Стандарт 15)

В `evidence` — **пути к логам**. Маршрутизатор проверяет, что файлы существуют и непусты, а их отсутствие
трактует как сфабрикованную проверку. Строку итогов пиши в `evidence_summary`, поле **без
доказательной силы**. Не объявляй задачу сделанной без зелёного прогона.
