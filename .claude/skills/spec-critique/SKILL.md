# spec-critique

Критика намерения (AEF, Том IV, §5.3). Она стоит **перед** парой «агент-автор ↔ агент-рецензент» и применяет к
намерению те же запрет по умолчанию и ограниченные итерации, что эта пара применяет к результату.

## Зачем это отдельный шаг

Раунд ревью по диффу стоит дороже раунда критики по тексту, а ловит то же самое, только позже.

## Предусловие

SDD выбрана (`docs/jms-spec/<NN>-*.md`), код по ней ещё **не написан**. Реализацию не читай:
знание кода маскирует пробелы в тексте, а проверяешь ты именно текст.

## Шаги

1. **Прочитать** SDD, намерение в редакции из строки `Намерение:` и контракты стыков по ссылкам
   `product-kb:contracts/<файл>@<коммит>` в указанных редакциях. Прочитай источники каждого требования с редакцией
   и фрагментом, а также эталон поведения продукта
   `[Jakarta Messaging 3.1, Final Release](https://jakarta.ee/specifications/messaging/3.1/jakarta-messaging-spec-3.1.html) и Javadoc 3.1`: SDD другой стороны стыка не читать, сверка идёт с контрактом (Том IV, §5.3).
2. **«Что я понял»** — пересказ своими словами: назначение, наблюдаемая семантика, границы.
3. **«Что я НЕ понял»** — поимённо, с цитатой, **машиночитаемо**: у каждого вопроса закрытое
   множество вариантов, `other` и `answer_goes_to`. Непонимание критика по умолчанию считается недоопределённостью SDD. Оспоренные вопросы разрешаются отдельно по шагу 7.
4. **Замкнутость (Стандарт 5).** `Entity inventory` есть, непуст, машиночитаем (таблица с ID,
   `Kind` ∈ `type · method · header · storage-field · config · test-suite · concept · frame · API`). Формулировки открытого множества — находка.
5. **Полнота критериев (Стандарт 3).** Каждое требование `Acceptance Criteria` ↔ сценарий ↔ строка `Test:`
   (`Suite.Case`), в обе стороны. Формальную часть прогоняет
   `python3 .claude/chain/trace.py sdd <SDD>`: строка `Источник: <id>@<редакция>` в начале `Problem`,
   ровно одна строка `Компонент:` (Стандарт 6), `ID:` и `Источник:` у каждого требования, `Test:` у каждого сценария.
   Источники repo: читаешь в Git компонента, product-kb: — в `product-kb`, в коммитах и фрагментах из строк источников. Лог — в `evidence`. `critic.json` с твоим `provenance.model` — запись об этом
   разборе, и разбиравший отличается от агента-автора.
6. **Контракт стыка.** SDD следует контракту: одно именование, один формат, одна семантика ошибок. Всё, что SDD
   ожидает от другой стороны, записано в контракте, а своими словами обязанности другой стороны SDD не описывает.
   Если контракт молчит о нужном или допускает два прочтения — вопрос с `answer_goes_to: "contract:<файл>"`,
   ответ ложится в контракт через «Утверждение архитектуры».
7. **`Stop-conditions` (Стандарт 2).** Секция непуста и покрывает найденные тобой неоднозначности.
   Применимые НФТ — требования Acceptance Criteria с ID, условиями замера, сценарием и Test.
   Stop-conditions ссылается на них без копии порога. Для partial следуй разделу «Ограниченный допуск» HANDOFF.md.
   Проверь содержание отдельных требований и набора по шести критериям Стандарта 7 в роли spec-critic.
   Редакцию, область, вывод и вопросы запиши в существующем отчёте.
8. **Оспоренные вопросы (Том IV, §5.3).** Открытые попытки (`python3 .claude/chain/critic_dispute.py list <задача>`) решаешь ты:
   прочитай исходный вопрос и указанное место в действующей SDD, вынеси по каждой `answered | gap | unresolved`
   с обоснованием в `dispute_decisions` (формат — роль `spec-critic`). Ссылка автора вопрос не закрывает.

## Вердикт (пакет передачи, Том IV, §5.2)

```
status:    criticized
verdict:   clean | partial | needs-work | critical
questions: [ { id, quote, question, options: [..., "other"], answer_goes_to }, ... ]
```

- `clean` — `questions` пуст, маршрутизатор выводит команду агента-автора;
- `partial` — allowed проверен как независимая часть, вопросы совпадают с blocked, admission содержит SHA-256 декларации оркестратора;
- `needs-work` — оркестратор отвечает на каждый вопрос **правкой секции `answer_goes_to` SDD**,
  не в чате (Закон 1). Вопрос с `contract:` ждёт решения «Утверждение архитектуры» по контракту. Новый раунд ведёт новый агент со свежим контекстом (Стандарт 13);
- `critical` — сразу эскалация к `Owner`.

Лимит раундов — [CALIBRATION.md](../../chain/CALIBRATION.md).

## Границы (что это НЕ)

- Не ревью кода (→ `cross-model-review`): кода ещё нет.
- Не проектирование: назвать, что выбор не сделан — да; сделать выбор — нет.
- Не правка SDD: критик только читает, правит только оркестратор.
