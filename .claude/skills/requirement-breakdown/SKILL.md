# requirement-breakdown

Стадия до входа в цепочку. Артефакт — **черновик разбора** по `templates/breakdown.md`. Автор результата — человек.

## Предусловие

Есть полный INT в конкретной редакции и **граница работы**. Отдельная копия бизнес-требования
или рабочей истории не нужна. Если границы нет,
работа не останавливается: первый блокирующий вопрос черновика — об объёме, а детальный разбор покрывает
только ядро работы.

## Шаги

1. **Зафиксировать вход.** Строка источника `product-kb:<ID>@<коммит>#<фрагмент>` или `repo:<путь>@<коммит>#<фрагмент>`, редакции опорных документов,
   коммиты кода. Всё это — в шапку черновика и в `evidence` пакета.
2. **Граница работы** (раздел 0). Выписать, какие пункты источника входят в работу и какие нет. Сверить
   опорный документ с текущим поведением кода: то, что следует сверх явного описания работы, пометить
   «вне явного описания, следует из …».
3. **Как устроено сейчас** (раздел 1.1). Пройти путь данных и обработки в коде затронутых компонентов,
   с `файл:строка`. Найти действующие требования функции и спецификации-факты, которые работа меняет
   или удаляет.
4. **Функции и компоненты** (разделы 1.2–1.3). Функции с источником и типом. Зависимости с видом:
   по ценности, технически, по усилию. Компоненты — по действующей карте и ADR. Если компонентов больше
   одного — черновик стыков и декомпозиции по `templates/intent.md`.
5. **Детальный разбор** (раздел 2). Черновик SDD на компонент отдельным файлом
   `handoffs/current/intent-<NN>/sdd-<компонент>.md` по `templates/sdd.md`: `Problem` со строкой
   источника и строкой `Компонент:`, `Outcome`, `Acceptance Criteria` в форме «требование → сценарий → `Test:`»
   с пометкой типа и ссылкой на действующее требование, `Entity inventory` с путями.
6. **Вопросы** (раздел 3). Блокирующие — граница работы, источник данных, противоречия входа. Если блокирующих
   вопросов много, граница работы, скорее всего, не задана: вернись к шагу 2. Уточняющие — по делу. У каждого варианты с пунктом «иное» и адресат из таблицы
   Тома II, §1.2. Если в коде есть прецедент решения — назвать его в вопросе.
7. **Самопроверка.** Пройти по каждому требованию: есть ли ссылка на источник; в границе ли оно; помечен
   ли тип. Требование без ссылки перенести в вопросы. Проверить формат черновиков SDD:
   `python3 .claude/chain/trace.py sdd handoffs/current/intent-<NN>/sdd-<компонент>.md` для каждого, вывод —
   в `handoffs/current/intent-<NN>/logs/trace-sdd.log`. Ошибка формата — правка черновика, а не пометка.
8. **Пакет передачи** `breakdown.json` со `status: drafted` (см. роль `analyst`).

## Чего не делать

- Не править код, `product-kb`, требование-источник и не писать `Owner`.
- Не выбирать развилку, которую решает настройка установки, а не код.
- Не писать план работ вместо спецификации.
- Не разбирать источник за границей работы без пометки «вне объёма».
