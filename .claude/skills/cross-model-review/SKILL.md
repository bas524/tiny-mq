# cross-model-review

Процедура Reviewer'а (контур Review, Standard 12). Ключ — **независимость**: ревью выполняется моделью, отличной от той, что писала код (Закон 6). Производитель не проверяет сам себя.

## Как обеспечить «другую модель»
- Предпочтительно: делегируй агенту **`jms-reviewer`** (его frontmatter несёт `model: MiniMax-M3`, отличную от Producer `claude-sonnet-4-6`).
- Fallback (если роутинг per-subagent-модели не подтверждён — см. Verification в плане harness): запусти ревью **отдельной** CLI-сессией `claude-minimax-m3` против диффа.

## Чек-лист ревью
1. **Спека:** каждый пункт `Test plan` из `docs/jms-spec/<NN>.md` покрыт GTest-кейсом, и тест реально проверяет семантику (не проходит вхолостую).
2. **Скоуп:** нет изменений «мимо спеки».
3. **Инварианты:** перф (горячий путь → есть `perf-check` без регрессии); `-Werror` чисто; обе durable-ветки (`save`/`deliverCommitted`); threading-модель (ADR-0005); durable-ключ `(clientID,name)`; формат `0x02`; `MessageProperty`↔`PocoAnyVisitor.h`.
4. **ADR:** решения не нарушают `arch/0001..0005`; меняющие инвариант — требуют ADR.

## Вердикт (handoff §5.2)
```
status:   approved | rejected | escalated
evidence: <что смотрел: тесты, бенчи, конкретные места диффа>
```
- `approved` — только при полном покрытии и целых инвариантах.
- `rejected` — точное указание нарушенного пункта `Test plan`/инварианта. Не чинить самому.
- **default-deny (§5.3):** после N=2 безрезультатных раундов Producer↔Reviewer — `escalated` (третейская модель/специалист/человек). Спорное НЕ сливается.
