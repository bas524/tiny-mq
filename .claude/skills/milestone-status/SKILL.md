# milestone-status

Контур Knowledge (Standard 8, садовник). Держит карту прогресса честной и подтверждённой evidence, а не памятью.

## Предусловие
Обновляй статус на `done` **только** при наличии пакета от Reviewer со `status: approved` + зелёный `cpp-verify` (+ `perf-check` без регрессии, если тронут горячий путь). Нет evidence — нет «done».

**Standard 15:** evidence — это существующие файлы прогонов по путям из пакета, а не строка
«тесты зелёные». Открой их и убедись, что прогон был. Отметка `done`, опирающаяся на прозу,
фиксирует в карте прогресса заявление вместо свидетельства — ровно то, ради чего карта и ведётся.

**Standard 20:** при расхождении между `*.json` агента и журналом роутера `handoffs/<spec>/chain.log`
приоритет у журнала: его пишет harness, а пакет агент пишет о себе сам. Расхождение —
отдельная находка, а не мелочь.

## Процедура
0. **OpenSpec archive** (гибрид, см. `openspec/README.md`): если doc-writer сдал
   `openspec/changes/<NN>-<slug>/` — `python3 .claude/chain/openspec.py archive <NN>-<slug>`;
   0 ошибок обязательны, результат merge в `openspec/specs/<capability>/spec.md` идёт в тот же
   коммит закрытия. Нет change'а — спека закрывалась до гибрида, бэкфилл — задача садовника.
1. **`tasks/UNIFIED-PLAN.md`:**
   - в таблице «Карта: спека → майлстон → статус» переведи строку спеки `⬜ planned` → `✅ done` с краткой пометкой, что именно реализовано (по образцу уже закрытых строк M0);
   - если это была последняя спека майлстона — обнови заголовок раздела майлстона (напр. «— ✅ ЗАКРЫТ»).
2. **`tasks/CONTINUE-HERE.md`:** укажи следующий шаг — какая спека идёт дальше по зависимостям/критическому пути `M0→M1→…→M6`.
3. Если решение меняло инвариант — убедись, что `knowledge-gardener` завёл ADR (`adr-write`), и сошлись на него.

## Формат пометки
Кратко и проверяемо: `✅ done (что сделано; имя ключевого теста)`. Пример из M0: `✅ done (SendOptions: send(msg,opts)/setDefault; SendOptionsTest)`.
