# adr-write

Контур «Знание» (Стандарт 9). Значимые решения фиксируются как нумерованные ADR в `arch`,
чтобы их можно было пересмотреть осознанно.

## Проверка на дубликат — до записи (Стандарт 16, п. 9)

```
REUSE (решение уже зафиксировано → сошлись на него)
  > EXTEND (есть близкий ADR → допиши раздел или поставь статус `superseded`)
    > JUSTIFY (действительно новое → обоснуй, чем отличается от ближайшего)
      > ESCALATE (сомнение → человек)
```

Два ADR про один инвариант хуже, чем один неидеальный: читатель не знает, какой действует.

## Процедура

1. Следующий номер берётся по таблице `arch/README.md` и файлам `NNNN-*.md`: максимальный плюс один, 4 цифры.
2. Создай `arch/NNNN-<slug>.md` по `templates/adr.md` (MADR): Контекст · Варианты · Решение · Последствия.
3. **Статус** из словаря: `proposed` / `accepted` / `superseded by ADR-XXXX` / `deprecated`. Поле `Review Date` обязательно (Стандарт 7).
4. Строка в таблицу `arch/README.md`.

## Когда ADR обязателен

- Отклонение от унаследованных ограничений (`см. INHERITED_CONSTRAINTS в PROJECT.md`).
- Обоснованная НФТ-регрессия (осознанный компромисс) фиксируется здесь, а не замалчивается.
- Дефект, повторившийся дважды, закрепляется как инвариант (`исключения из деструктора (ADR-0006); регрессия кешированных заголовков (ADR-0008)`).

ADR — это «почему», а не пересказ кода.
