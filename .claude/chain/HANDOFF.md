# Контракт передачи в событийной цепочке (AEF, Том IV, §5.2)

Минимальная событийная цепочка агентов. Каждая стадия по завершении пишет
**машиночитаемый пакет передачи** — это и есть «событие готовности» для следующей стадии.
После стадии оператор запускает маршрутизатор `route.py`. Маршрут выбирается по паре
**стадия × статус**.

Пороги и обоснование привязок — [CALIBRATION.md](CALIBRATION.md), исполняемые значения — `chain.env`.

## Куда писать

```
handoffs/current/<spec>/<stage>.json     напр. handoffs/current/12/producer.json
handoffs/current/<spec>/logs/*.log       прогоны, на которые ссылается evidence
handoffs/current/<spec>/chain.log        журнал маршрутизатора (пишет оснастка, не агент)
```

`<stage>` ∈ `critic` · `producer` · `reviewer` · `nfr` · `conformance` · `security` · `docwriter` · `explainer` · `orchestrator`.
Каталог `handoffs/current/` эфемерный, он в `.gitignore`.

## Формат пакета (ядро обязательно)

```json
{
  "spec": "12",
  "sdd_ref": "docs/jms-spec/12-<slug>.md",
  "stage": "producer",
  "status": "produced",
  "iteration": 1,
  "artifact": "git diff --stat; <файлы>",
  "evidence": [
    "handoffs/current/12/logs/verify.log",
    "handoffs/current/12/logs/bench-<path>.log"
  ],
  "evidence_summary": "verify: N/N passed; bench: <метрика> было→стало",
  "evidence_tree": "tree:<хеш из .claude/chain/fingerprint.py>",
  "target_files": ["<файл>", "<файл>", "tests/<файл>"],
  "provenance": { "model": "<model-id>", "role": "Producer", "autonomy": "R2" }
}
```

Значения `stage` и `provenance.role` (`Producer`, `Reviewer`, `Specialist`) — идентификаторы: их задают
промпты маршрутизатора, и по ним читают журнал. Русские имена ролей — в агентах и в README кита. Исключение — поле `role` в событии `CONSULT`
журнала: там стоит русское имя роли из таблицы Тома II, §1.2, или `NONE`, если строки в таблице нет.

Обязательное ядро: `spec · status · artifact · evidence · provenance`. Пакет без ядра маршрутизатор
считает **не готовым** и ничего не запускает. Это проверка формата на границе, а не блокирующий
шлюз: блокирующие шлюзы стоят только на необратимых рубежах (Стандарт 21).

`evidence_tree` обязателен у стадий, которые прогоняют проверки: `producer`, `reviewer`, `nfr`, `conformance`,
`security`, `docwriter` (Стандарт 15). Стадия снимает отпечаток рабочего дерева (`.claude/chain/fingerprint.py`)
до проверок и после последнего прогона, и при совпадении кладёт второй в пакет. Маршрутизатор считает его заново:
нет поля — `BAD-EVIDENCE-TREE`, другое дерево — `STALE-EVIDENCE`, отпечаток не вычисляется — `FINGERPRINT-FAILED`.
Совпадение отпечатков подтверждает совпадение покрываемого состояния в момент снятия и в момент маршрутизации.
Привязка лога к этому состоянию требует неизменности входов во время проверки. Факт прогона и неизменность входов
маршрутизатор не устанавливает: их подтверждает собственный прогон проверяющего. Что отпечаток покрывает и что
нет (игнорируемые файлы, подмодули), сказано в заголовке `fingerprint.py`.

Стадийные поля: `dispute_decisions` — у `critic`, если есть открытые попытки оспаривания (Том IV, §5.3):
по одному решению `{attempt, decision: answered|gap|unresolved, rationale}` на каждую открытую попытку, `product_delta` — обязательно у `docwriter` (путь к продуктовой дельте или `null`,
Том IV, §10.6), `questions` — только у `critic` и `breakdown`, `question` — только при `status: paused`,
`verdict` — только у `critic`. У вопросов `breakdown` два поля сверх критика: `addressee` (роль из таблицы
Тома II, §1.2) и `blocking` (блокирующий или уточняющий). Все пять полей вопроса разбора (`id`, `question`,
`options`, `addressee`, `blocking`) обязательны: вопрос без любого из них останавливает цепочку
(`BAD-QUESTIONS`), ранг и адресат умолчанию не оставляются.

### `evidence` — ссылки, а не проза (Стандарт 15)

`evidence` — **массив путей к файлам с выводом реальных прогонов**. Маршрутизатор проверяет, что каждый
путь существует и непуст. Отсутствующий файл означает сфабрикованную проверку: событие `FABRICATED`, остановка.
Элемент массива, который не строка, — `BAD-EVIDENCE … element=<тип>`, остановка.

`evidence_summary` — необязательное поле **без доказательной силы**. Оно существует, чтобы человек
читал пакет глазами, и не может быть основанием для вердикта.

### `target_files` — целевой набор (Стандарт 18)

Целевой набор файлов сессии, объявленный **до** старта стадии. Маршрутизатор сверяет рабочее дерево с
набором. Выход за набор — **остановка цепочки** (`SCOPE-VIOLATION`), а не предупреждение.
Знание продукта (`PRODUCT_KB_PATH`) в `target_files` не входит никогда: сессия его только читает.
Изменения или неотправленные коммиты в его клоне — тоже остановка (`KB-WRITE`).

Слоение (Том IV, §5.2): работа агента-автора не закоммичена до рубежа человека, поэтому базовая линия
для всех последующих стадий — его набор. Стадии, которые только читают (`critic`, `reviewer`, `nfr`,
`conformance`, `security`), не должны добавлять к нему ничего. Изменяющие стадии после него
(`docwriter`, `explainer`) проверяются на свой набор поверх него. Артефакты цепочки (`handoffs/current/`, `docs/reviews/`) из сверки исключены.
Дельта стадии знания тоже не закоммичена до рубежа человека. Когда маршрутизатор принимает пакет `docwriter`,
он фиксирует набор и снимок его файлов (`knowledge.accepted.json`, событие `KNOWLEDGE-ACCEPTED` с хешем записи).
Этот набор наследует только стадия объяснения и только в зафиксированном состоянии: изменённый файл —
`KNOWLEDGE-CHANGED`, изменённая запись — `KNOWLEDGE-RECORD-CHANGED`. Пакет `docwriter`, который маршрутизатор
не принимал, ничей набор не расширяет.
Расширение набора посреди задачи — решение оркестратора, записанное в `chain.log` вместе с
ревизией SDD.

## Стадия × статус → маршрут

| стадия | status | что делает маршрутизатор |
|---|---|---|
| critic | `criticized` | открытая запись оспаривания без решения в `dispute_decisions` → **остановка** (`BAD-DISPUTE`); решение `unresolved` → **остановка**, решает `Owner` (`DISPUTE-UNRESOLVED`); решения дописываются в записи (`DISPUTE`). Затем: `verdict: clean` или допустимый `partial` → запись входа разбора `critic.input.json` (`CRITIC-INPUT`) и **агент-автор**; иначе **остановка**: SDD правит оркестратор по `answer_goes_to`, вопрос с `contract:` — `CRITIC-CONTRACT`, ответ в контракт через «Утверждение архитектуры» |
| producer | `produced` | **агент-рецензент** (`cross-model-review`) |
| любая | `rejected` | `iteration < CHAIN_MAX_ITER` → **агент-автор** на правку (iteration+1); иначе **эскалация** |
| перед агентом-автором и на `explained` | — | сверка входа разбора с текущим: `INPUT ok`; изменился — **остановка** `INPUT-CHANGED what=<sdd\|intent\|contract:<путь>>`, нужен новый раунд критика; не прочитан — `INPUT-UNREADABLE`; записи нет или она не разбирается — `NO-CRITIC-INPUT` |
| reviewer | `approved` | первый шлюз из `SPECIALIST_GATES`; список пуст → **агент знания**, при partial → **PARTIAL-COMPLETE** |
| nfr / conformance / security | `approved` | следующий шлюз; после последнего → **агент знания**, при partial → **PARTIAL-COMPLETE** |
| любая | `paused` | **остановка**: `Stop-conditions`, вопрос к `Owner` и подсказка о консультации. Не ошибка, работа возобновляема |
| docwriter | `documented` | `product_delta` не `null` и не непустая строка → **остановка** (`BAD-PRODUCT-DELTA`); путь не ведёт к непустому обычному файлу → **остановка** (`FABRICATED`); иначе **стадия объяснения**: её вход — дельта и отчёты шлюзов, а не код заново |
| explainer | `explained` | **остановка** на рубеже человека (R1): прочитать объяснение, затем `openspec.py archive`, `milestone-status` и коммит. Если у стадии знания есть продуктовая дельта — напоминание завести задачу знания (`KNOWLEDGE-TASK-NEEDED`). Нет пакета стадии знания с полем — `PRODUCT-DELTA-UNKNOWN` |
| breakdown | `drafted` | **остановка**: черновик разбора адресован человеку, вопросы печатаются по рангу, ничего не запускается. Стадия стоит до цепочки: цепочка начнётся с критика, когда появится подписанная SDD. `drafted` от другой стадии — запрет по умолчанию |
| любая | `escalated` | **остановка**: точка решения человека |
| прочее | прочее | **запрет по умолчанию**: остановка |

`iteration` — счётчик раундов «агент-автор ↔ агент-рецензент». Проверяющие копируют его из входного пакета,
агент-автор увеличивает при правке.

Для критика действует отдельный предел `CHAIN_MAX_CRITIC_ROUNDS` из `CALIB_CRITIC_ROUNDS`
(при отсутствии переменной — стартовые 5, без изменения `CHAIN_MAX_ITER`). Маршрутизатор записывает
номер и хеш пакета событием `CRITIC-ROUND` в `chain.log` каталога задачи. Новый пакет увеличивает
номер как минимум на один, `iteration` критика может поднять его, но не уменьшить. Повтор содержимого
не считается новым раундом. Перезапуск процесса и оспаривание вопроса число раундов не обнуляют.
При обновлении ранее записанные номера критика из `SEEN` сохраняются как нижняя граница.
Повреждённая запись счётчика запрещает продолжение.

Новый `SEEN` критика сохраняет `critic_digest`. После сбоя до `CRITIC-ROUND` повтор тех же байтов
сохраняет номер, новый пакет получает следующий. Записи чужих стадий в счётчик не входят.
Повреждённые номера и хеши, разные номера одного пакета и невозрастающие номера разных пакетов
запрещают продолжение. Полная `CRITIC-ROUND` достаточна для восстановления без `SEEN`,
её точный дубль допустим. Календарная проверка и полный аудит связей событий сюда не входят.
Оспаривание использует сохранённый номер раунда, в том числе в `resolution.critic_iteration`.
Служебный `critic.input.json` исключён из очереди, чтобы повтор после сбоя продолжал пакет критика.

Чистый результат последнего разрешённого раунда проходит обычные проверки. Оставшиеся вопросы,
в том числе при противоречивом `clean`, на этом раунде дают `CRITIC-LIMIT` и эскалацию к `Owner`.
За пределом лимита ни один вердикт не запускает автора. Продолжение требует решения человека
о дальнейшей работе, а не уменьшения `iteration` или удаления истории. Это ограничение при обработке
результата: ручной запуск внешней модели сам маршрутизатор не запрещает.

### `paused` ≠ `rejected` ≠ сбой

- `rejected` — есть дефект, работу надо **переделать**;
- `paused` — агент упёрся в неоднозначность из `Stop-conditions` и остановился вместо умолчания.
  Сделанное корректно, работа **возобновляема** с той же точки;
- сбой агента или инфраструктуры — отдельная категория: `INFRA-FAIL` в журнале, возобновление из
  сохранённого дерева.

### Подсказка о консультации на `paused` / `escalated`

Решение принимает **`Owner` SDD** (Стандарт 2). Маршрутизатор читает `Owner` из `sdd_ref` и печатает,
с какой ролью из замкнутой таблицы Тома II, §1.2 ему имеет смысл свериться. Ключ — стадия × тип
артефакта (локальное соответствие — CALIBRATION.md). Это консультация, а не передача решения.
Событие `CONSULT` в `chain.log`.

## Что подаётся стадии на вход (Стандарт 13, ось контекста)

Проверяющему (`reviewer`, `nfr`, `conformance`, `security`) подаются **только**: `sdd_ref`, дифф
относительно основной ветки, пути из `evidence` (чтобы **перепрогнать**), `target_files`.
**Не подаются** описание в `artifact` и `evidence_summary` агента-автора.

Стадии объяснения (`explainer`) подаются дельта, отчёты шлюзов, ADR и журнал, то есть уже
произведённые и проверенные артефакты, и лишь затем дифф для ссылок на места в коде. Разбор
агента-автора ей тоже не подаётся, и по той же причине: объяснять надо результат, а не замысел
(Закон 6). Её `evidence` подтверждает не корректность изменения, а то, что утверждения объяснения
не выдуманы. Вердикта у этой стадии нет по построению (Стандарт 4).

## Журнал маршрутизатора: свидетельство и заявление (Стандарт 20)

`chain.log` пишет **оснастка**: время, стадия, статус, модель, результат проверок, команда запуска,
завершение запущенной стадии (`EXIT` с кодом возврата и наличием пакета, при ненулевом коде ещё `INFRA-FAIL`).
`*.json` пишет о себе агент — **заявление**. При расхождении приоритет у журнала, расхождение —
событие `MISMATCH`.

Записи, которые вносит **человек** (`HUMAN-DECISION`, `RESUME`, `HUMAN-GATE`), — записи решения.
Они правомерны для того, что произвести может только человек. Событие, которое оснастка могла наблюдать
сама (код возврата, отсутствие пакета, ответ 429 или 400), но записанное рукой, — дефект маршрутизатора, а не
свидетельство. Словарь событий — Приложение H книги.

### `questions` критика — закрытые множества, ответ в SDD

`critic.json` при `verdict ≠ clean` несёт `questions[]`: `{id, quote, question, options[…, "other"],
answer_goes_to}`. Ответ **возвращается в спецификацию**, а не остаётся в переписке (Закон 1).
Непустой `questions` при `verdict: clean` — противоречие, маршрутизатор трактует его как `needs-work`.
`questions`, который не массив объектов, — `BAD-QUESTIONS`, остановка при любом вердикте.

### Вход разбора критика — запись оснастки

При `clean` или `partial` маршрутизатор пишет `critic.input.json` в каталоге задачи: объект с полями `package`,
`sdd`, `sdd_snapshot` (снимок `fingerprint.py --paths`), `intent` (`null` или `{ref, path, pinned}`), `contracts`,
`sources` (массивы таких объектов) и `admission` (`null` для полного допуска или объект ниже).
Его источник — `trace.py input <SDD>`: намерение из строки `Намерение:`, источники отдельных требований и контракты
из ссылок `product-kb:contracts/<файл>@<коммит>`, `pinned` — объект Git файла в коммите ссылки. Перед каждым запуском
агента-автора и на `explained` вход сравнивается с текущим по содержимому: снимок SDD, ссылки и `pinned` против
файла в `HEAD` клона `product-kb`. Запись не правится руками: она — наблюдение оснастки, а не заявление критика.

У источника `ref` — вся строка `repo:<путь>@<коммит>#<фрагмент>` или
`product-kb:<ID или путь>@<коммит>#<фрагмент>`. Разные фрагменты дают разные записи, полный повтор сливается.
Порядок — первое появление ссылки. `path` — разрешённый путь документа, `pinned` — его Git blob.
`trace.py input` дополнительно возвращает `head`, который заново вычисляется при сверке и в запись не входит.
Источники repo читаются из репозитория компонента. Источники product-kb — из PRODUCT_KB_PATH.
Старая запись без sources/admission не принимается. Нужен новый раунд критика.

## Ограниченный допуск

Известный вопрос закрывается до зависимой работы. Оркестратор может выделить независимую часть в
Stop-conditions той же SDD: текст вопроса, обоснование независимости и один блок:

```aef-admission
{"allowed":["REQ-1"],"blocked":{"Q1":["REQ-2"]},"stop_when":"Для REQ-1 понадобился выбор по Q1"}
```

allowed и объединение blocked должны точно разделять все ID Acceptance Criteria. Обе части непусты,
пересечения запрещены. Один ID может зависеть от нескольких вопросов. Вопросы критика точно соответствуют
ключам blocked. Общее условие остановки действует всегда: для allowed понадобилось решение хотя бы
одного blocked-вопроса. stop_when уточняет его, но не сужает.

До критики оркестратор записывает декларацию в существующий `orchestrator.json` каталога задачи:

```json
{"spec":"01","sdd_ref":"docs/spec/01-demo.md","admission":{"target_files":["src/a.py","tests/test_a.py"]}}
```

Это вход, а не завершение стадии. Критик не меняет декларацию. Он проверяет достаточность allowed,
независимость от blocked и соответствие набора, затем возвращает `verdict: partial`, вопросы и
`admission: {"scope_sha256":"<SHA-256 байтов orchestrator.json>"}`. Набор берётся только из декларации.
Верхнеуровневый target_files критика пуст. Декларация остаётся неизменной до окончания частичной работы.

Набор содержит только уникальные относительные пути файлов внутри компонента. Каталоги, glob,
выход через `..` или symlink, служебные каталоги, SDD и её локальные источники запрещены.
Общий файл для нескольких требований не доказывает их независимость. Это проверяют по смыслу и по диффу.

При partial поле admission записи входа содержит allowed, blocked, stop_when, target_files и scope_sha256.
Изменившийся вход или декларация запрещает продолжение. Автор и проверяющие передают requirement_ids,
точно равный allowed. Автор не расширяет набор файлов. Рецензент независимо проверяет разрешённое поведение
и отсутствие реализации blocked, в том числе внутри общих файлов. Специалисты проверяют ту же область.

| Результат | Переход |
|---|---|
| clean без вопросов и блока допуска | обычный цикл всей SDD |
| partial с проверенной границей | автор, рецензент и обязательные специалисты в пределах allowed |
| все проверки частичной работы пройдены | PARTIAL-COMPLETE, остановка до docwriter и explainer |
| прямой documented/explained при partial | PARTIAL-NOT-ACCEPTED, полной приёмки нет |
| сработал Stop-conditions | paused и решение Owner |
| вопрос решён, SDD обновлена | новый clean по всей SDD, затем обычный цикл |

Лимит раундов сохраняется. Допустимый partial на последнем раунде проходит, за пределом — нет.
После полного clean декларация больше не участвует в допуске. Файл может снова служить пакетом оркестратора.
Коды отказа: BAD-ADMISSION, ADMISSION-SCOPE, INPUT-CHANGED, NO-CRITIC-INPUT.

Маршрутизатор обнаруживает выход за набор после стадии. Установка обязана механически ограничить запись
до исполнения и защитить постановку, декларацию и запись допуска. Этот протокол не заменяет песочницу.
Archive выполняется после решения человека и отдельно проверяет свежий полный допуск. Простого удаления
блока из SDD недостаточно. Правила task_ref и archive — в [openspec/README.md](../../openspec/README.md).

Поля, которые маршрутизатор читает из других пакетов задачи, проверяются по тем же типам: `target_files`
у `producer.json` при сверке целевого набора, `product_delta` у `docwriter.json` у стадии объяснения,
`critic_iteration` у записи оспаривания `disputes/<попытка>.json`. Не тот тип — `BAD-SOURCE pkg=<пакет> field=<поле>`,
остановка.

## Как запускается цепочка

1. Оркестратор или человек запускает `spec-critic` на SDD → `critic.json`.
2. После `clean` оператор вызывает `python3 -B .claude/chain/route.py` и запускает выведенную команду агента-автора.
3. После каждого пакета — ручной вызов `route.py` и печатаемой команды. Порядок стадий: агент-рецензент → шлюзы →
   агент знания → стадия объяснения → `explained` → остановка на рубеже R1.
4. `rejected` → назад к агенту-автору (не больше `CHAIN_MAX_ITER` раундов).

В установленной копии `CHAIN_EXEC=0` в `chain.env`. Маршрутизатор печатает команду для оператора. Предохранители: метки `*.routed` и `*.notready`, `CHAIN_MAX_ITER`,
потолок `CHAIN_MAX_DISPATCH` **на одну задачу**, проверка свидетельств, целевой набор, остановка на
`explained`, `paused` и `escalated`. В метке записан хеш содержимого разобранного пакета, а не его имя.
Поэтому переименованный пакет повторно не разбирается, а новый пакет под прежним именем разбирается.
