# ADR-0010: Решение локальной транзакции и восстановление доставки

- Статус: proposed
- Дата: 2026-11-16

## Контекст

[SDD 72](../docs/jms-spec/72-jakarta-delivery.md) требует общей границы видимости
для входов и выходов сессии, включая durable fan-out. Модель отказа охватывает
аварийное завершение процесса и повторное завершение во время восстановления
в том же каталоге данных. Хранилище сохраняет форматы сообщения `0x02` и `0x03`.

## Решение

Exchange сериализует устойчивые решения commit и DLQ. Файл `delivery-72/decision`
хранит один кадр и предшествующий ему байт состояния. Файл открывается один раз.
Подготовка при байте 0 записывает кадр и выставляет длину файла по его размеру.
Завершённая позиционная запись байта 1 фиксирует исход. Байтом 0 после применения
освобождается место для следующего кадра. Содержимое за байтом 0 игнорируется
при старте, включая оборванный хвост. Неизвестный байт состояния, неверная длина,
граница или контрольная сумма за байтом 1 препятствуют запуску с диагностикой.
При освобождении крупных кадров файл усекается до байта состояния. Запись
байта и кадра возвращается после передачи в файловый кэш ядра, что соответствует
заданному профилю остановки процесса.

На POSIX Exchange открывает корень данных до replay. Вложенные каталоги журнала
и внешних кадров открываются относительно дескрипторов родителей без перехода
по символическим ссылкам. Чтение, запись и усечение `decision` используют один
дескриптор обычного файла. Внешний кадр читается через дескриптор обычного файла
и публикуется через эксклюзивно созданный временный файл. Переименование, обход
и удаление привязаны к открытому каталогу `attempt-72`. Удаление может убрать
саму ссылку, а чтение отклоняет её. При невозможности безопасно открыть каталог
очистка при ack оставляет метаданные для следующего открытия хранилища.

Кадр решения начинается с восьми байтов `TMQ72W01`, затем содержит 64-битную
длину полезной нагрузки, полезную нагрузку, CRC-32 полезной нагрузки и восемь
байтов `TMQ72END`. Многобайтовые числа в служебных кадрах записываются в little
endian. Полезная нагрузка начинается с 32-битного количества операций. Операция
содержит однобайтовый тег (`1` append, `2` remove), относительный путь хранилища
с 32-битной длиной, UUID хранилища (16 байтов) и UUID экземпляра доставки
(16 байтов). Append добавляет 64-битную длину и данные LinearStorage,
состоящие из байта типа и сериализованного сообщения.
Путь проверяется на принадлежность каталогу Exchange. Зарегистрированная durable
подписка использует каталог и UUID поколения. Очередь и legacy durable сохраняют
существующие каталоги и UUID хранилищ. Ключ записи отдельный от публичного ID
сообщения. Порядок операций соответствует подготовленному набору копий.

До решения сессия удерживает входы, а подготовленные выходы хранятся в памяти.
Подписки и селекторы выбираются при подготовке commit. Replay проверяет
существование записи по UUID перед append и удаляет вход по UUID, если он ещё
активен. В живом процессе append использует выделенный ключ, а remove может
использовать уже известную позицию записи. LinearStorage отбрасывает оборванную последнюю запись перед перестроением
индекса. После применения всех операций и сброса файлов байт `decision` переводится в 0
до допуска последующего ack. Так повторный запуск после ack не воспроизводит
выход. При ошибке применения после решения брокер прекращает обслуживать этот
каталог до успешного replay. Применение при запуске предшествует открытию очередей,
подписок и приёму клиентов. Публикуемые в живом процессе копии становятся доступны
для claim и browse общей границей после применения набора. Порядок и владение
каждой копией остаются в состоянии назначения согласно ADR-0009.

Для первой persistent попытки без лимита, backoff и DLQ используется первый байт
прежнего выравнивания заголовка записи `.tom` сразу после `deleted`. Значение 1
означает in-flight. Метка `<номер тома>.delivery-72` создаётся перед первой записью
в новый том. Значения прежних томов без метки игнорируются. Побайтовый формат
сообщений и смещения существующих полей `.tom` сохраняются. Изменение однобайтовой
фазы или `deleted` записывается после claim и до возврата соответствующей операции.
На POSIX используется отображение страницы файла в общий файловый кэш, на Windows
позиционная запись. Счётчик первой передачи берётся из записи. Состояние повторов
хранится во внешнем кадре, который применяется и к помеченным томам.

Для legacy, настроенной или повторной persistent попытки кадр `attempt-72/<uuid>`
имеет внешнюю структуру кадра решения с заголовком `TMQ72A01`. Полезная нагрузка
содержит фазу (u8: in-flight=1, scheduled=2, terminal=3), счётчик (i32),
`nextRedeliveryAt` (i64), лимит (i32), два интервала backoff (i64), признак DLQ
(u8) и при его наличии адрес хранилища в формате операции решения. Кадр заменяется
атомарным переименованием соседнего временного файла и имеет приоритет при
чтении. Фаза scheduled сохраняет абсолютный срок, terminal сохраняет результат
выбора перед решением о переносе. Переход между исходной записью и DLQ использует
кадр решения. Ack удаляет запись, затем внешний кадр при его наличии.
При открытии оставшиеся метаданные без активной записи удаляются. При отсутствии метаданных запись открывается с
историческими заголовками и счётчиком. Отдельная метка повторной готовности
позволяет сохранить публичный JMSDeliveryTime. Объём метаданных ограничен числом
активных persistent записей, а объём журнала размером одного решения.

Сессия сохраняет thread-affinity ADR-0005. Она сериализует вызовы listener
и отдельно вызовы завершения отправок. Явные close и stop устанавливают границы ожидания. Деструкторы действуют по
ADR-0006. Заголовки и кеш сериализации обновляются совместно по ADR-0008.

## Откат

1. Перед обновлением остановить брокер и сделать согласованную копию всего каталога,
   включая реестр подписок и `.tom`.
2. Для отката остановить приём, закрыть сессии, дать текущей версии завершить replay,
   остановить её и скопировать каталог в отдельное место. В этой копии прочитать
   первый байт `delivery-72/decision`. Пустой файл или 0 разрешает переход дальше.
   При 1 открыть копию текущей версией для replay и повторить сверку. Другие
   значения требуют диагностики текущей версией.
3. Выгрузить манифест активных записей и доставок. В порядке имён каталогов и томов
   пройти каждый числовой `.tom` по смещениям, начиная с 0. В текущих профилях
   заголовок занимает 32 байта, UUID расположен по смещению 0, длина данных u64
   в порядке байтов платформы по смещению 16, `deleted` по 24. Следующая позиция
   равна текущей плюс 32 и длина данных. Для каждой записи с `deleted=0` записать
   относительный каталог, UUID, SHA-256 данных и поколение из каталога подписки.
   Добавить фазу из байта 25 для помеченного тома. Если для UUID есть внешний
   кадр, проверить длину и CRC и выгрузить его фазу, счётчик, срок и адрес DLQ.
   Сохранить с манифестом файл реестра подписок. Проверить целостность: отсутствие
   оборванных записей, уникальность пары каталог/UUID, наличие хранилищ поколений.
4. Открыть отдельную копию старой версией и сверить с манифестом активные записи,
   подписки, порядок и сроки до допуска клиентов. Если старый формат не представляет
   активную фазу, счётчик или срок, нужны проверяемые преобразования этих записей
   с той же семантикой. При невозможности переноса остановить откат, сохранив
   рабочий каталог и обе копии.
5. Удалить метки `*.delivery-72` только на проверенной рабочей копии для legacy
   версии после переноса метаданных и сверить её открытие повторно. Повторное
   обновление откроет новый том. Резервную копию до обновления использовать
   для запуска после сохранения и проверенного переноса записей, принятых
   после обновления.

## Рассмотренные варианты

Разрозненные журналы по назначениям не дают общего решения для входов, очередей
и поколений подписок. Бессрочный WAL потребовал бы отдельного протокола checkpoint
и удерживал бы уже применённые решения. Один кадр, удерживаемый до полного применения,
позволяет сбрасывать журнал на каждой границе commit.
