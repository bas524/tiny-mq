# ADR-0007: Delivery delay — таймер на Destination, ленивый старт потока

- Статус: accepted
- Дата: 2026-08-01

## Контекст

Спека 13 (JMS 2.0 §7.8, `docs/jms-spec/13-delivery-delay.md`) реализует
`MessageProducer.setDeliveryDelay` / `JMSDeliveryTime`: сообщение не должно
быть видно потребителю, пока не наступило `deliveryTime`. Это требует
какого-то механизма таймера — что-то должно разбудить доставку, когда срок
настаёт, а не только когда придёт новое сообщение.

Спека сама помечает вопрос как открытый: «Single global timer vs
per-destination timer? Start with per-destination for isolation».

Реализация (`DeliveryScheduler.h/.cpp`) выбрала: один `DeliveryScheduler` на
`Destination` (владеет `Destination`, см. `Destination.h`), с воркер-потоком,
который стартует **лениво** — только при первом вызове `enqueueOrSchedule`,
которому реально нужно отложить доставку (`deliveryTime` в будущем). Пока
у назначения не было ни одного отложенного сообщения, никакого потока нет.

Это прямо соседствует с ADR-0005, которое отклоняет «поток на сессию на
сервере» доводом «не масштабируется, дублирует модель реактора». Ревью спеки
13 (раунд 1, `docs/reviews/13-delivery-delay.review.md`, блокер B3) указало,
что тот же довод формально применим и здесь: при delayed-трафике на N
назначениях получается N спящих потоков, и решение ушло в код без записи —
триггер «решение меняет инвариант → нужен ADR» по чек-листу ревьюера.

## Решение

**Оставляем per-destination scheduler с ленивым стартом** как решение для M2
(текущий этап — in-process broker, без сетевого реактора). Явно фиксируем:

- Единица изоляции — `Destination`. Тяжёлый delayed-трафик на одном назначении
  не задерживает срабатывание таймера на другом (это и есть буквально то, что
  просила спека формулировкой «for isolation»).
- Горячий путь (неотложенные сообщения, подавляющее большинство трафика) платит
  ровно одну проверку `deliveryTime != 0` (`Consumer::push`,
  `Destination::deliverCommitted`) — сравнимо с ADR-0005 нулевой ценой не
  используемого фильтра.
- Ленивый старт — не косметика, а собственно средство смягчения довода
  ADR-0005: 100 назначений без delayed-трафика дают 0 потоков, а не 100.
  Цена растёт только вместе с фактическим использованием delivery delay, а не
  с числом назначений как таковым.
- Цена, которую мы принимаем осознанно: как только у назначения был хотя бы
  один отложенный send, поток живёт до разрушения `Destination` — воркеры не
  освобождаются между всплесками delayed-трафика. При N назначениях, каждое
  хоть раз использовавшее delay, получаем N спящих потоков на `wait_until`.
  Это линейный рост по назначениям с delayed-трафиком, не по общему трафику.

## Рассмотренные альтернативы

**Один глобальный таймер (timer wheel) на весь `Exchange`.** Единственная
очередь дедлайнов, один поток на весь брокер вне зависимости от числа
назначений. Соответствует целевой модели ADR-0002/0005 (реактор + пул потоков)
естественнее, чем N спящих потоков. Отклонено для M2: `Destination` сегодня не
имеет доступа к общему таймер-сервису на уровне `Exchange`, а вводить его сейчас
означало бы тянуть в спеку 13 архитектуру, которая осмысленно появится вместе с
реактором (M3+). Пересмотр: см. «Условие пересмотра» ниже.

**Поток на сессию** (по аналогии с моделью доставки клиента в ADR-0005). Не
рассматривался всерьёз для сервера — ADR-0005 отклоняет его явно тем же
доводом о масштабируемости, а delivery delay — атрибут назначения (сообщение
задерживается для всех потребителей одинаково), не сессии; привязка к сессии
не имела бы смысла семантически.

**Poco::Timer / единый таймер на процесс без привязки к Destination.**
Рассматривался мельком: Poco предоставляет `Timer`, но требует либо периодического
поллинга (лишняя задержка срабатывания и лишние пробуждения на простое), либо
собственной реализации min-heap дедлайнов поверх него — по сложности не
отличается от уже написанного `DeliveryScheduler`, а выигрыш в потоках получаем
только сведя его к одному экземпляру на `Exchange`, что и есть первая
альтернатива.

## Почему ADR-0005 не нарушается

ADR-0005 отклоняет поток-на-сессию как *постоянную* модель сервера. Здесь поток
не постоянный: он либо не существует вовсе (ленивый старт), либо существует
ровно потому, что назначение активно использует фичу, которая по определению
требует ожидания истечения времени вне событий ввода-вывода. Изоляция по
`Destination`, а не по клиентскому соединению — тот же принцип, что и у
`ConcurrentLinearStorage` (один воркер на назначение для персистентности), уже
принятый в проекте до этого ADR.

## Условие пересмотра

Решение пересматривается (переход на единое таймер-колесо на уровне `Exchange`,
интегрированное с пулом потоков реактора) при первом из:

- интеграция с сетевым реактором (M3+, ADR-0002) — тогда единый таймер-сервис
  на процесс естественно ложится в ту же событийную модель, и держать
  отдельные потоки на назначение перестаёт быть оправданным;
- появление рабочих сценариев с сотнями одновременных назначений, активно
  использующих delivery delay (а не сотнями назначений вообще — ленивый старт
  уже держит эту цифру нулевой без delayed-трафика).

## Последствия

- `DeliveryScheduler::stop()` — обязательная явная точка останова
  (per ADR-0006); `Destination` обязан вызывать её до разрушения `_scheduler`.
- Тест на нежелательный поздний старт потока после `stop()` — часть чек-листа
  ADR-0006 при следующих правках `DeliveryScheduler`
  (см. `DeliveryDelayTest.testSchedulerDeliversImmediatelyInsteadOfStartingThreadAfterStop`).
- При M3 переход на глобальный таймер потребует ревизии владения:
  `DeliveryScheduler` перестанет быть членом `Destination` и станет сервисом
  `Exchange`, на который `Destination` только ссылается.
