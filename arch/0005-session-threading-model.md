# ADR-0005: Потоковая модель сессии (thread-affinity по JMS)

- Статус: accepted
- Дата: 2026-05-23

## Контекст

Спецификация JMS гарантирует, что `Session` и созданные из неё
`MessageProducer`/`MessageConsumer` — **однопоточные** объекты: приложение не
должно использовать одну сессию из нескольких потоков одновременно. При этом
сервер строится на асинхронном реакторе ([ADR-0002](0002-tcp-transport-and-framing.md)),
где сетевые события обрабатываются в пуле потоков реактора. Нужно определить,
как доставка сообщений и обработка команд соотносятся с потоками.

## Решение

**Сервер:**

- Сетевой ввод-вывод (чтение/запись кадров) — в потоках реактора.
- Бизнес-логика по соединению сериализуется: команды одного `Connection`
  обрабатываются строго последовательно (per-connection mailbox/strand), чтобы
  состояние сессий не требовало мелкоблочных локов.
- Доставка сообщений потребителю кладёт кадр в исходящую очередь соединения;
  реактор асинхронно её сливает в сокет. Ядро (`Consumer`) уже использует
  блокирующую очередь `moodycamel::BlockingConcurrentQueue` — на сервере переход
  от блокирующего `recv()` к push-доставке в сокет.

**Клиент:**

- Каждая `Session` имеет ровно один поток доставки. Для асинхронных
  `MessageListener` (onMessage) — этот поток вызывает листенер; гарантируется
  последовательность вызовов в рамках сессии (JMS требование).
- Синхронный `receive()` блокирует вызывающий поток на очереди сессии.
- Объекты `Session`/producer/consumer не делаются потокобезопасными наружу
  (как и в JMS): за корректное использование отвечает приложение. `Connection` —
  потокобезопасен для start/stop/close.

## Рассмотренные альтернативы

- **Поток на сессию на сервере** — отклонено: не масштабируется, дублирует
  модель реактора.
- **Полная потокобезопасность Session наружу** — отклонено: противоречит JMS,
  лишние локи на горячем пути, ложное чувство безопасности у пользователей API.

## Последствия

- Нужен per-connection strand/очередь команд на сервере.
- Push-доставка вместо pull на серверной стороне consumer'а: при сетевом
  клиенте брокер сам инициирует отправку, а не ждёт `recv()`.
- Flow control (M5) обязателен: без него быстрый producer переполнит исходящую
  очередь медленного consumer'а.
- Клиентская библиотека владеет потоками доставки и обязана корректно
  останавливать их при `close()`.
