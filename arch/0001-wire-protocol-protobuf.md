# ADR-0001: Wire-протокол — STOMP 1.2 (v1) → свой protobuf (v2)

- Статус: accepted (пересматривает первоначальный выбор «только protobuf»)
- Дата: 2026-05-23
- Решение принято: совместно с владельцем проекта; согласовано с `docs/jms-spec/50-protocol-choice.md`

## Контекст

Брокер работает только in-process: богатое ядро есть, сетевого слоя нет.
Существовали два несогласованных решения:

- `docs/jms-spec/50-protocol-choice.md` (статус «decided»): **v1 = STOMP 1.2**,
  v2 = AMQP 1.0, admin = gRPC/HTTP. Custom-protobuf оценён как ⚠️ «брать только
  если ни STOMP, ни AMQP не подходят».
- Первая редакция этого ADR: сразу свой protobuf-протокол.

Конфликт разрешён в пользу комбинированного варианта.

## Решение

- **Data plane v1 — STOMP 1.2.** Текстовое кадрирование, тривиальная реализация
  с обеих сторон, отлаживается готовыми STOMP-клиентами, есть библиотеки на всех
  языках. Быстрее всего разблокирует реальных клиентов и позволяет проверить
  маппинг JMS-семантики на спецификации `docs/jms-spec/*`.
- **Data plane v2 — свой бинарный протокол на Protocol Buffers** (замена AMQP 1.0
  из исходного плана). Причина замены: жёсткое требование производительности
  (см. `CLAUDE.md` и `tasks/README.md`) лучше закрывается компактным protobuf с
  маппингом JMS 1:1, чем тяжёлым AMQP с impedance mismatch. AMQP остаётся
  возможной альтернативой, если потребуется широкий interop (см. «Когда
  пересмотреть»).
- **Admin/control plane — gRPC, либо HTTP+JSON для первой версии** (по
  `docs/jms-spec/43-admin-introspection.md`). Не используется как data plane.

Кадрирование и транспорт обоих data plane — в [ADR-0002](0002-tcp-transport-and-framing.md).

## Рассмотренные альтернативы

- **Только STOMP (v1 и навсегда)** — не закрывает требование высокой
  производительности (текстовый формат, слабый flow-control).
- **Только protobuf с самого начала** — медленнее даёт работающий сетевой
  брокер, нет готового тулинга для отладки, противоречит уже написанным спекам
  40/60/61.
- **STOMP → AMQP 1.0 (как в docs)** — AMQP корректно реализовать с нуля очень
  дорого, модель сообщений ≠ JMS; для «tiny» брокера и требования perf protobuf
  выигрывает.

## Последствия

- Слой кадров абстрагируется: `StompCodec` (v1) и `ProtobufCodec` (v2) делят
  общий back-end `Connection`/`Session` (см. [ADR-0004](0004-build-targets-layout.md);
  кодек `AmqpCodec` из спеки 60 переименовывается в `ProtobufCodec`).
- v1: первоклассный STOMP-кодек пишем сами (framing тривиален, не растим vcpkg).
- v2: добавляется зависимость `protobuf` (vcpkg) и кодоген `.proto`.
- `docs/jms-spec/40` и `50` обновлены: v2 = protobuf вместо AMQP.
- Java-клиент (спека 61) поверх STOMP v1 остаётся в силе без изменений.
- Схема `.proto` (v2) становится контрактом совместимости и проходит ревью
  наравне с публичным API.

## Когда пересмотреть

Если возникнет сильный спрос на широкий interop со сторонними брокерами/языками
для бинарного канала — вернуть AMQP 1.0 как v2/v3 (можно через `qpid-proton` как
кодек), оставив protobuf как внутренний высокопроизводительный транспорт.
