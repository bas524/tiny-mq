# Работа в tiny-mq

Начни с [START-HERE.md](START-HERE.md). Значения проекта и команды проверок — в
[PROJECT.md](PROJECT.md). Для принятого поведения читай [OpenSpec](openspec/README.md),
для будущего — конкретную SDD из [карты покрытия](docs/jms-spec/README.md).

## Контекст и артефакты

- Передавай стадии её роль и нужные разделы SDD, INT, ADR и источников. Читай SDD целиком,
  когда это требует роль. Открывай соседние документы, когда текущая задача от них зависит.
- Вместо копий используй пути, строки, ID и редакции. В контекст модели передавай итог проверки
  и строки сбоя. Полный обязательный лог хранится по пути из `evidence`.
- Дополняй действующий артефакт нужного класса. Новый файл нужен, когда у результата есть отдельная
  роль в приёмке, сопровождении или запуске. При замене удали устаревшую копию после переноса уникального
  содержания и обновления ссылок. Сохраняй требуемые пакеты AEF, закреплённые источники и свидетельства.

## AEF в Codex

Роли, навыки и проверяющие программы лежат в `.claude/` по путям эталонного кита.
Загружай инструкцию роли явно из промпта стадии в новой сессии. Модели назначаются через
[chain.env](.claude/chain/chain.env). Обёртки используют встроенный OpenAI provider
или профиль `deepseek`/`deepseek-pro` для `api.deepseek.com`. CLI `-p` означает
профиль, а `-p PROMPT` на входе проектной обёртки — аргумент с промптом кита.

### История ручной цепочки

Перед критикой выполни `python3 -B .claude/chain/trace.py sdd <путь-SDD>` и
`python3 -B .claude/chain/trace.py input <путь-SDD>`. Критик читает постановку,
INT, закреплённые фрагменты и применимые контракты. Раскладку пакета задаёт
[HANDOFF.md](.claude/chain/HANDOFF.md). Первый критик запускается оператором на
`./.claude/chain/codex-deepseek-pro -p "…"` с явно подготовленным контекстом,
согласно разрешениям владельца на передачу данных провайдеру.

После каждого handoff запусти из корня `python3 -B .claude/chain/route.py`. Маршрутизатор
проверит пакет и напечатает команду отдельной интерактивной сессии, если есть следующий
переход. Запускай её вручную из корня изолированной рабочей копии. После стадии проверь
артефакты и повтори вызов маршрутизатора. Рабочие пакеты пишутся в `handoffs/current/`.
У критика и автора разные провайдеры. Рецензент начинает новую сессию и повторяет проверки сам.

## Проверки изменений

Для изменения объяви `target_files` до редактирования. Чистая база рабочей копии нужна для
сравнения изменений с HEAD. Для сборки и тестов соблюдай [PROJECT.md](PROJECT.md), для
горячего пути также [baseline](benchmarks/baseline.md) и [nfr-gate](.claude/skills/nfr-gate/SKILL.md).
Сценарии записи и доставки проверяй с persistent и non-persistent сообщениями, включая
обычную отправку и commit. Политика архивирования и проверки допуска — в [OpenSpec](openspec/README.md).

## Native Runtime

Для новых изменений используй `python3 -B .claude/chain/aef.py <operation> <change>`.
Начни с валидного комплекта OpenSpec и `prepare`. `status` показывает состояние,
`next` выполняет разрешённый шаг, `record-decision` регистрирует решение Owner.
Технические операции: `verify`, `resume`, `archive`, `audit`, `provider-probe`,
`request-exception`. Правила ручной цепочки выше описывают прежний маршрут
и остаются справкой для исторических пакетов.

По умолчанию используется профиль `harness` для `.claude/chain`. Для изменений C/C++
в `server/src` укажи `prepare <change> --profile cpp`. При переходе на `nfr`
запусти `verify <change> --actor nfr` в согласованное окно замера. Область записи,
SDK и проверки описаны в [PROJECT.md](PROJECT.md), приёмка профиля — в
[M-06](tasks/M-06-compact-runtime-provider-smoke.md).
