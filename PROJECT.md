# PROJECT.md — проектные значения оснастки

Класс документа: **K1 — исполняемое знание** (AEF, Стандарт 6): читает агент во время работы.

Это **единственное** место, где живут значения, зависящие от проекта. Роли (`.claude/agents/`),
навыки (`.claude/skills/`) и маршрутизатор (`.claude/chain/`) ссылаются на слоты отсюда и не
переопределяют их у себя. Незаполненный слот (`{{…}}`) в любом файле кита — сфабрикованная
оснастка (Стандарт 15): `.claude/chain/check-placeholders.py` обязан быть пустым до первого запуска цепочки.

Пороги и привязка моделей здесь **не** живут — они в `.claude/chain/CALIBRATION.md` (Приложение C).

## Сборка и проверка

Для чистой конфигурации укажи `VCPKG_ROOT`, затем выполни `cmake --preset debug` или
`cmake --preset release`. Локальные пресеты могут задавать путь к vcpkg. В текущей сборке
`ENABLE_TESTS=ON` добавляет GoogleTest в `tiny_mq`. Clang и GCC собираются с
`-Wall -Werror -Wextra -Wshadow`.

При доступном `clang-tidy` Debug-сборка Ninja или Make проверяет C++ тесты правилом
`readability-braces-around-statements`. Фигурные скобки вокруг условных
`EXPECT_*` и `ASSERT_*` обязательны: GCC диагностирует неоднозначный `else`
в раскрытии макроса GoogleTest. На macOS подходит `brew install llvm`.
CMake ищет `clang-tidy` также в каталоге LLVM Homebrew. Для диагностики сборки
используй отдельную цель `cmake --build --preset debug --target tiny_mq_test_clang_tidy`.
Linux CI проверяет эти же файлы под GCC с `-Werror`.

| Слот | Значение | Что это |
|---|---|---|
| `BUILD_CMD` | cmake --build --preset debug --parallel | команда полной сборки в проверочной конфигурации; предупреждения = ошибки, если проект так решил |
| `BUILD_RELEASE_CMD` | cmake --build --preset release --parallel | команда сборки в конфигурации поставки, если она отличается от проверочной (иначе `—`) |
| `TEST_CMD` | ./cmake-build-debug/tiny_mq --gtest_filter='-*Bench*' | команда полного прогона тестов с выводом в стандартный поток |
| `TEST_FILTER_CMD` | ./cmake-build-debug/tiny_mq --gtest_filter= | команда прогона одного набора или теста: дописать идентификатор сразу после `=` |
| `TEST_ID_FORMAT` | Suite.Case | форма идентификатора исполняемого критерия в строке `Test:` (например, `Suite.Case`, `path::test_name`) |
| `REQ_ID_FORMAT` | REQ-<NN>-<k> | форма устойчивого идентификатора требования в строке `ID:` (например, `REQ-<NN>-<k>`). Идентификатор не меняется при правке требования и переживает перенос в спецификацию-факт |
| `REQ_ID_PATTERN` | REQ-[0-9]{2}-[0-9]+ | регулярное выражение, по которому идентификатор требования узнаётся в коде тестов; согласовано с `REQ-<NN>-<k>`. Без него тест-сироту не отличить от текста — `trace.py tests` останавливается |

| `BENCH_METRIC` | медиане CPU time/op по 9 повторам, ABBA на одной машине | какая метрика сравнивается и как (например, медиана времени на операцию по N повторам) |

## Обязательный CI и НФТ

Защита `main`: `strict=true`, `enforce_admins=true`; обязательны шесть checks обычного CI:
`ASan gate`, `Jakarta Messaging contract (Java)`, `Сборка и тесты (macos-latest)`,
`Сборка и тесты (ubuntu-latest)`, `Дистрибутив (macos-latest)`, `Дистрибутив (ubuntu-latest)`.
Основание: [снимок required checks](handoffs/current/72/logs/main-required-ci-checks.json)
и решение Owner R1 от 2026-11-19. GitHub Performance не требуется: workflow отключён
глобально и удалён по решению Owner.

НФТ-бюджет +5%, CPU CV ≤5%, ABBA, девять повторов на сторону и учёт CPU storage workers
сохраняются; методика — [nfr-gate](.claude/skills/nfr-gate/SKILL.md).
Waiver разрешает только SDD 72 / PR №12 по обычному CI: REQ-72-9 остаётся открытым в
[M-05](tasks/M-05-local-nightly-performance.md), технический performance verdict rejected.
Локальный ночной job ещё не настроен; до согласования времени Owner расписание не создаётся.


## Проверенный профиль native Runtime

Текущий `workflow-checks.json` регистрирует только `harness` с
`code_paths=[".claude/chain"]`; NFR `not_applicable` относится к этой области.
Профиль `cpp` unavailable до реальных проверок продуктовых команд, NFR и
изоляции. Harness не покрывает C++, не заменяет сборки, ASan, шесть required CI
checks и не переносит waiver SDD72 на новую работу. Для записи/доставки нужны
persistent и non-persistent сообщения, обычная отправка и commit; для горячих
путей сохраняются baseline и nfr-gate. M-05/REQ-72-9 остаются открытыми.

Публичный CLI и ограничения переключения — [AGENTS](AGENTS.md), план проверки
C++ профиля — [M-06](tasks/M-06-compact-runtime-provider-smoke.md).
Нового performance job или расписания change79 не вводит; числовая экономия
времени/стоимости не измерена. Функция продукта и доменная модель не меняются.
