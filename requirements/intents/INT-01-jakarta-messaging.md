## Цель

Команды приложений на разных языках должны иметь возможность обмениваться сообщениями через
единый сервис tiny-mq с общей семантикой JMS. Им нужны одинаковые гарантии маршрутизации,
квитирования, транзакций и восстановления после сбоя для операций, доступных их клиентам.
Java-приложения подключаются через стандартный Jakarta Messaging API и меняют настройки
провайдера при переносе. Приложения на других языках подключаются напрямую через клиентскую
библиотеку своего языка или документированный сетевой протокол. Оператор воспроизводит эти
сценарии под нагрузкой. При отказе одного узла клиенты возобновляют работу через оставшиеся узлы
с сохранением подтверждённых данных.

## Ограничения

- **Граница работы.** Очереди и топики, classic, simplified и legacy domain API, отдельный Java SE клиент,
  плюс профиль Jakarta EE с XA, серверной доставкой, управляемым контекстом и MDB. Рекомендуемый стандартом
  адаптер Jakarta Connectors входит в выбранный профиль проекта. Нормативная редакция — финальная 3.1.
- C++ входит в первый выпуск как полноценный клиент брокера наряду с Java. Для других языков
  точка интеграции — версионированный сетевой контракт, достаточный для независимой реализации клиента.
  Список дополнительных SDK и порядок их выпуска определяются отдельными постановками.
- Основа — брокер на C++ и его персистентные данные. C++20 — текущий минимум. Допускается поднять
  стандарт, если это позволяет использовать стандартные средства, сократить зависимости или даёт
  измеримое преимущество. При повышении фиксируются минимальные версии компиляторов, проверяются
  поддерживаемые платформы и совместимость публичного API. Существующий C++ API и формат данных меняются по
  описанной миграции и с проверяемым откатом. Деструкторы не выпускают исключения, а заголовки не расходятся
  с кешированной сериализацией. Сетевые контракты опираются на ADR-0001 и ADR-0002. Адаптация этих ADR для
  недостающей семантики проходит через новое решение архитектуры до реализации зависимых операций.
- Обязательства формулируются для Java SE, Jakarta EE, межъязыкового сетевого контракта и расширений tiny-mq.
  Для каждого поддерживаемого клиента опубликованы доступные операции, типы данных и гарантии главы 9
  с учётом режима доставки, подписки, назначения, транзакции и допустимых сбоев. Для переносимых типов
  сохраняются значения и типы на обеих сторонах. Семантика типов, зависящих от языка, описана явно.
- **Производительность.** Измеряются пропускная способность, p95/p99 задержки, CPU и память при
  репрезентативной нагрузке. Существующий порог регрессии CPU time/op на горячем пути — 5%.
  Для первого выпуска отдельно задаются абсолютные цели для штатного режима и режима после отказа узла.
- **Минимум сторонних зависимостей.** Используются средства стандартного C++ и его библиотеки,
  когда они выполняют требования по корректности, скорости и переносимости. У каждой необходимой
  сторонней библиотеки указаны назначение, рассмотренные альтернативы и область использования.
  Состав зависимостей брокера, клиентов и адаптеров учитывается отдельно от инструментов сборки и тестов.
- **Отказоустойчивость.** При перезапуске и при потере одного узла подтверждённые persistent-сообщения
  и зафиксированные транзакции сохраняются. Восстановление учитывает durable-подписки и подготовленные
  ветви XA. Допустимые повторы доставки и неопределённые исходы операций видны клиентам.
- **Высокая доступность.** В профиле HA отказ одного узла не требует его возврата для возобновления
  обслуживания. Клиенты автоматически переключаются в рамках заявленных возможностей и бюджета
  времени восстановления. При сетевом разделении запись разрешена стороне, способной обеспечить
  единую историю фиксации. Пределы доступности и модель отказов указаны в профиле эксплуатации.
- DLQ, безопасность транспорта и операционные интерфейсы нужны проекту по прежнему плану.
  Поддержка брокера как TCP-протокола другой реализации, перенос программ с `javax.jms` без миграции
  и обещание сертификации платформы Jakarta EE находятся за границей намерения.

## Критерии успеха

- **INT-01-INTEROP.** WHEN Java-приложение отправляет persistent-запрос в очередь, отдельный
  нативный C++ процесс через сетевой клиент получает его по селектору и отправляет ответ
  в назначение из `JMSReplyTo`, THEN Java-приложение получает ответ с `JMSCorrelationID`,
  равным `JMSMessageID` запроса. Обе стороны сохраняют значения и типы тела и свойств,
  а C++ клиент подтверждает полученный запрос.
  Test: `ReleaseConformanceTest.JavaAndCppRoundTrip`.
- **INT-01-SE.** WHEN отдельный Java SE процесс через JNDI читает из очереди зафиксированное
  persistent-сообщение и в одной локальной транзакции пересылает его в топик, а перед успешной попыткой
  откатывает первую, THEN вход повторно доставлен с признаками redelivery, исходящая копия отката не видна,
  после commit и рестарта сообщение доступно отсутствовавшему durable-подписчику. Получение и отправка на
  разных этапах используют classic и simplified API. Test: `ReleaseConformanceTest.JavaSeRecoveryRoundTrip`.
- **INT-01-EE.** WHEN приложение в целевом EE-контейнере получает persistent-сообщение через MDB и
  в общей транзакции пишет в независимый XA-ресурс, затем брокер перезапускается после prepare,
  THEN решение менеджера транзакций восстанавливает обе ветви, а управляемый JMSContext живёт в области
  транзакции. Повтор сценария с rollback оставляет исходное сообщение доступным для redelivery и не
  фиксирует запись ресурса. Test: `ReleaseConformanceTest.JakartaEeXaRecovery`.
- **INT-01-HA.** WHEN при параллельной сетевой нагрузке Java и C++ отказывает обслуживающий узел,
  THEN оставшиеся узлы возобновляют отправку и получение в пределах согласованного RTO. Проверка
  сверяет подтверждённые persistent send, ack и commit с восстановленным состоянием. Потери
  подтверждённого состояния при этом отказе равны нулю. Test: `AvailabilityTest.SingleNodeFailover`.
- **INT-01-PERF.** WHEN кандидат проходит согласованный профиль нагрузки в штатном режиме, во время
  переключения и после него, THEN отчёт подтверждает цели по throughput, p95/p99, CPU и памяти в
  применимых режимах, включая существующий порог регрессии горячих путей.
  Test: `ReleaseConformanceTest.PerformanceProfile`.
- **INT-01-DEPS.** WHEN артефакты собираются в конфигурациях поставки, THEN фактический
  состав сторонних зависимостей соответствует инвентарю релиза. У каждой поставляемой зависимости
  есть обоснование, а зависимости тестов и бенчмарков исключены из поставки.
  Test: `ReleaseConformanceTest.DependencyFootprint`.
- Перед заявлением о совместимости каждый нормативный пункт имеет вердикт по применимому профилю.
  Официальный TCK подтверждает заявленный профиль Jakarta Messaging для Java.
  Test: `ReleaseConformanceTest.TckAndCoverage`.

## Критерии отмены

- Владелец отменяет или меняет намерение, если межъязыковое взаимодействие или совместимость с Jakarta
  Messaging перестают быть целями поставки либо согласованные бюджеты производительности, восстановления
  и зависимостей делают сквозные результаты недостижимыми. Сужение набора клиентов или профилей требует решения
  о приоритете и обновления критериев, связанных SDD и публичного заявления.

## Ожидаемый бизнес-эффект

Команды могут развивать взаимодействующие приложения на разных языках и использовать общий брокер.
Эффект проверяется контрольными приложениями Java и C++, которые обмениваются сообщениями с сохранением
согласованной семантики. При переносе Java-приложения достаточно сменить настройки провайдера и назначения.
Сопровождение определяет доступные операции, среды и пределы гарантий по версии клиента и протокола.
При отказе узла приложения возобновляют обмен в пределах согласованного времени. Инженер эксплуатации
может воспроизвести этот результат под заявленной нагрузкой и проверить состав поставки.
