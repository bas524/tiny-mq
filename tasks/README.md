# tiny-mq — дорожная карта задач

> **Главный документ — [UNIFIED-PLAN.md](UNIFIED-PLAN.md):** объединяет детальные
> спеки `docs/jms-spec/` (фичи JMS), эти майлстоны (доставка) и ADR. Начинать с него.

Цель: брокер сообщений, поведенчески соответствующий **JMS 2.0**, с **C++ и Java**
клиентскими библиотеками. Протокол: **STOMP 1.2 (v1) → свой protobuf (v2)**
(см. [ADR-0001](../arch/0001-wire-protocol-protobuf.md)). Файлы `M*.md` ниже —
детализация отдельных майлстонов; сводная карта спека↔майлстон в UNIFIED-PLAN.

## Где мы сейчас

Готово (in-process ядро):
- Exchange / Destination (Queue, Topic, Temporary*), routing.
- Session, Consumer, Producer; 4 режима квитирования.
- Selector (JMS SQL-92), durable subscribers, транзакции (TransactionBuffer),
  персистентность (ConcurrentLinearStorage).
- 5 типов сообщений (Text/Bytes/Map/Stream) + JMS-заголовки в модели данных.

Не готово (главные пробелы):
- **Нет сети** — `main.cpp` пустой каркас, всё работает только в одном процессе.
- **Нет Connection/ConnectionFactory** — иерархия JMS обрывается на Session.
- **Нет протокола и клиентской библиотеки.**
- Часть JMS-семантики не *принуждается* (expiration, priority-ordering,
  redelivery/DLQ).

## Принцип приоритизации

Приоритет = (близость к критическому пути «работающий сетевой брокер + клиент»)
× (риск/блокирование других задач). Сначала строим вертикальный срез
(end-to-end send/receive по сети), затем наращиваем JMS-полноту, затем
надёжность и конформанс.

определение Definition of Done для первого релиза 0.2.

## Приоритеты — легенда

- **P0** — на критическом пути к первому сетевому релизу, блокирует остальное.
- **P1** — нужно для заявленной цели (JMS-совместимость), но после вертикального среза.
- **P2** — важно для продакшена/качества, не блокирует функциональную полноту.

## Сквозное требование: производительность

Высокая производительность — **жёсткое требование проекта**, а не «фича на потом».
Оно действует на всех майлстонах:

- Перформанс проверяется **после каждого значимого изменения** (любая правка
  горячего пути: routing, доставка, (де)сериализация, хранилище, сетевой
  кодек/реактор, квитирование/транзакции).
- Бенчмарки: `./tiny_mq --gbench [--benchmark_filter=<regex>]` (набор —
  `tests/BenchmarkTest.cpp`). Сетевой путь покрывается в M6-3.
- Зафиксировать baseline и сравнивать с ним; значимая регрессия
  (ориентир: > ~5% throughput/latency без обоснования) — это блокер, а не
  «доработаем позже».
- Каждая задача, трогающая горячий путь, в Acceptance должна включать пункт
  «нет регрессии перформанса относительно baseline».
- Новый функционал на горячем пути сопровождается бенчмарком, если
  существующие его не покрывают.
