# LP-02 — Разбор остаточных падений на Linux после LP-01

**Статус:** ⬜ open (заблокирована LP-01) · **Приоритет:** высокий · **Заведено:** 2026-08-01

## Зачем

LP-01 объясняет все 20 наблюдавшихся падений одной причиной, и по механизму этот вывод
проверен. Но UB имеет свойство маскировать соседние дефекты: пока `propertyValueType()`
возвращала мусор, ни один селектор не доходил до собственно сравнения значений, а
сериализация свойств не доезжала до диска в корректном виде. Значит, часть кода на Linux
**ещё ни разу не исполнялась по-настоящему**.

Отдельно: до 2026-08-01 проект собирался и тестировался **только на macOS/arm64**. Первый
прогон на Linux/x86_64 — это одновременно первая проверка на другой архитектуре, другой
стандартной библиотеке и другом порядке инициализации.

## Что сделать

1. После мержа LP-01 прогнать полный сьют на Linux (CI, задание `build-test (ubuntu-latest)`).
2. Каждое оставшееся падение — отдельная задача в `tasks/linux-port/` с тем же разбором:
   симптом → причина → цепочка → test plan. Не чинить «по симптому», не поняв механизм.
3. Особое внимание местам, где расхождение платформ вероятно по существу:
   - **формат хранения `0x02`**: порядок байт и выравнивание при чтении/записи заголовков
     (`Message::toBytes`, `Destination::priorityFromStorageBytes` читает `int32` по
     смещению 51 — на x86_64 это первый реальный прогон);
   - **`long`/`size_t`**: на macOS/arm64 и Linux/x86_64 совпадают по ширине, но
     сериализация могла закрепить неявные допущения;
   - **порядок статической инициализации** и зависимость от него;
   - **`std::filesystem` / пути**: чувствительность к регистру у файловой системы Linux
     (у macOS по умолчанию — нет). Каталоги durable-подписок формируются из clientID и
     имени подписки, то есть из пользовательских строк.
4. Проверить, не маскировал ли UB долги F6/F7 (изоляция тестов по стораджу): на Linux
   `ClientAckTest.testMixedPersistenceOrdering` и
   `ExpirationTest.testExpiredPersistentMessageDroppedOnRecv` прошли — но CI чистит
   `tiny-mq/` перед прогоном, так что это ничего не доказывает.

## Результат первого прогона после LP-01 (2026-08-01)

Прогон [30703110607](https://github.com/bas524/tiny-mq/actions/runs/30703110607),
ветка `fix-linux-portability`, коммит `160c24b`:

- **`ubuntu-latest` — success.** Все 112 тестов зелёные, включая все 20, падавших до
  LP-01. Остаточных падений, замаскированных UB, на Linux **не обнаружено**.
- `macos-latest` — падение на шаге тестов: не проверка, а аварийное завершение процесса
  (см. LP-03).

То есть по своей исходной формулировке — «какие ещё дефекты маскировало UB на Linux» —
задача отвечает: ни одного. Опасения про порядок байт при чтении `int32` по смещению 51
на x86_64 не подтвердились: `PriorityOrderingTest` и `MessageHeadersTest` на Linux проходят.

Задача остаётся открытой до выполнения критерия ниже, но её диагностическая часть закрыта.

## Критерий готовности

Полный сьют зелёный на **обеих** платформах в одном прогоне CI, без `allow_failure`
и без исключённых тестов. Сейчас блокируется LP-03.

## Границы

Задача диагностическая: она заводит другие задачи, а не чинит всё сама. Если остаточных
падений нет — закрыть с явной пометкой «остаточных падений не обнаружено», указав номер
прогона CI.
