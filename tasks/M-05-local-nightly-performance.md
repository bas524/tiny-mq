## Symptom

[Performance 44475262358](https://github.com/bas524/tiny-mq/actions/runs/44475262358)
сравнил main `230eefe8321f5d9a956a9fb89b09af1dab84cbad` с merge-кандидатом
`35fac1e4131169f0c166f8dc6b60e43b6531420d` для PR head `2b3c536`.
На стандартном Intel Xeon 6975P-C с Clang 18 путь
`AutoAck_NonPersistent_RoundTrip` дал CPU median 106,6 → 113,6 ns/op,
**+6,59%**, при CV 0,57% / 1,73%. Это стабильное превышение бюджета 5%.
Другие прежние прогоны также обнаруживали нестабильность базовых persistent
серий; это отдельное наблюдение, не объяснение данной регрессии.

## Решение Owner о выпуске

19.11 Owner потребовал при очередном неуспехе убрать GitHub perf и перейти к
ночным экспериментам на этой машине. На уточнение о PR ответил:
«Влить по обычному CI, perf — отдельная задача».
Для PR №12 это явное исключение из блокирующего НФТ-гейта. Оно не означает,
что REQ-72-9 подтверждён или что технический результат измерения стал зелёным.
GitHub Performance отключён; обычные CI-проверки обязательны, в том числе для
администраторов. История исходного прогона сохраняется по ссылке выше.

## Cause

Причина устойчивой регрессии AutoAck пока не установлена. Следует отделить
изменение стоимости delivery/ack от компилятора, аппаратной платформы и
планирования потоков. Списывать +6,59% на шум при данных CV нельзя.

## Done criteria

- Согласованы ночное окно и условия тишины на этой Mac-машине; до этого
  периодическое задание не создаётся.
- Baseline закреплён на указанном pre-PR main, кандидат — на фактическом
  merge-коммите PR №12. Ревизии, compiler, режим сборки и состояние машины
  сохраняются перед запуском. Никаких двух прогонов одного бинарника вместо
  сравнения ревизий.
- Release-сборки и одни и те же benchmark registrations сравниваются на одной
  машине: все 15 путей, persistent/non-persistent, обычные send и commit;
  CPU storage workers входит в persistent-метрики. Сохраняются сырые данные,
  медианы CPU, real time и sample CV. Используются штатные tests/nfr72.py
  и tests/nfr71.py; установка Docker не требуется.
- Непригодные серии остаются непригодными, пороги не повышаются. Ночной прогон
  не использует LLM для ожидания и повторного опроса процесса.
- AutoAck профилируется; воспроизводимая регрессия исправляется отдельным
  изменением с независимым review и повтором полного согласованного набора.
- Задача закрывается только по валидным сравнительным данным и при выполнении
  бюджета, не по одному факту настройки расписания.

## Scope-lock

Первый этап — локальная измерительная оснастка и методика. Оптимизация runtime
получит отдельный target_files после установления причины. Сеть, Java/XA,
кластерный профиль и понижение требований не входят в задачу.
