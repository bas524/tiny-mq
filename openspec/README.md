# openspec/ — что система делает сейчас

Класс документа: **K2 — инженерное знание** (Стандарт 6).

## Связь с постановкой и допуск к archive

В `.openspec.yaml` каждого нового изменения укажи `task_ref: <путь постановки от корня компонента>`.
Имя изменения совпадает с именем SDD `<NN>-<slug>.md` или задачи сопровождения `M-<N>-<slug>.md` без расширения.
Путь должен вести внутрь компонента. Archive не принимает отсутствующую или чужую постановку.

У каждого нового или изменённого требования SDD-дельты рядом с ID сохраняется `Источник:` с редакцией
и фрагментом. Переносятся также сценарии, Test и условия измерения. Это связь с основанием, а не вторая
копия требования. Содержание дельты сверяет рецензент. Исторические факты не переписываются автоматически.

Для SDD встроенный `openspec.py archive` проверяет отсутствие ограниченного допуска и актуальную
`critic.input.json` в `handoffs/current/<NN>/`: полный допуск, путь и снимок SDD, ссылки и редакции источников.
Удалить блок aef-admission недостаточно. Нужен свежий полный clean. Решение Owner о приёмке остаётся
обязательным, архиватор не удостоверяет подпись человека. Для сопровождения без SDD критик намерения не нужен.

Validate проверяет форму черновой дельты и не разрешает archive. Эти проверки допуска — профиль кита,
официальный CLI OpenSpec их сам не исполняет. Установка должна защищать постановку и запись допуска от
записи агентом и разрешать archive только после решения человека.

Гибрид AEF и [OpenSpec](https://github.com/Fission-AI/OpenSpec) (Том II, §2.2):

| Артефакт | Где | Роль |
|---|---|---|
| **SDD** — постановка задачи, 10 полей Стандарта 2 | `docs/jms-spec/NN-*.md` | *предложение изменения*; проходит критика, агента-автора, агента-рецензента, шлюзы; после приёмки — история (K4) |
| **Дельта** — `## ADDED/MODIFIED/REMOVED Requirements` | `openspec/changes/<NN-slug>/specs/<capability>/spec.md` | пишет **агент знания** (`doc-writer`) после приёмки: описывает *принятую реализацию* |
| **Спецификация-факт** — `## Purpose` + `## Requirements` | `openspec/specs/<capability>/spec.md` | **единственное место «что система делает сейчас»**; собирается `archive` из дельт |
| Архив изменения | `openspec/changes/archive/<YYYY-MM-DD>-<NN-slug>/` | история; в рабочий контекст агента не индексируется (K4) |

Что **не** переезжает сюда: `Entity inventory`, `Stop-conditions`, `Owner`, `Autonomy Level`,
`Rollback`, пакеты со свидетельствами и шлюзы цепочки — это надстройка AEF, OpenSpec их не знает.

## Формат (совместим с CLI OpenSpec 1.13)

```
### Requirement: <имя>                       ← устойчивый ключ для MODIFIED/REMOVED
The system SHALL …                           ← SHALL/MUST обязателен

ID: `<REQ-<NN>-<k>>`                     ← устойчивый идентификатор (Стандарт 3)
#### Scenario: <имя>
- **WHEN** …
- **THEN** …
- Test: `<Suite.Case>`               ← исполняемый критерий (Стандарт 3)
```

Каждое требование — ≥1 сценарий с телом. Строка `Test:` — наше расширение: OpenSpec её не
проверяет, а `spec-critic` и агент-рецензент проверяют. Сценарий без теста — ручная валидация,
и Стандарт 3 требует её явной пометки и обоснования.

В разделе `## Requirements` и в разделах дельты заголовки `### ` — только требования. Блоки кода
и комментарий HTML, который открывает строку `<!--`, из разбора исключаются: заголовок внутри них не требование.
`openspec.py` и `trace.py` разбирают требования одним кодом.

## Идентификатор требования

Строка `ID:` после утверждения `SHALL` — устойчивый идентификатор требования (трассируемость
требования, Стандарт 3). Он приходит из SDD и **переживает перенос**: по нему инцидент находит
нарушенное требование, а `Spec ref` задачи сопровождения на него ссылается. `openspec.py validate`
считает ошибкой ADDED и MODIFIED без `ID:`, ADDED с идентификатором, уже занятым в спецификации-факте,
MODIFIED, который меняет идентификатор, и дубликат идентификатора между спецификациями-фактами.
Требование без `ID:` в самой спецификации-факте — предупреждение: идентификатор требованию, написанному
до практики, проставляют задним числом, а проверку оно не валит. Официальный CLI OpenSpec читает эту строку как
часть тела требования.

## Инструмент

`.claude/chain/openspec.py` реализует нужное подмножество официального CLI без зависимостей,
а раскладка остаётся читаемой настоящим `openspec`.

```
python3 .claude/chain/openspec.py validate            # все спецификации-факты
python3 .claude/chain/openspec.py validate <NN-slug>  # и дельты изменения
python3 .claude/chain/openspec.py archive  <NN-slug>  # слияние дельт и перенос в archive/ (рубеж человека)
```

## Поставка версиями

Действует, когда `поставка версиями` = `поставка версиями`. При одном развёрнутом экземпляре раздел
не применяется: координата знания одна, это основная ветка.

Спецификация-факт версионируется **тем же механизмом, что код** ([Том II, §2.2] книги): лежит рядом
с ним и ветвится вместе с ним. Координата знания — ветка поддержки или тег релиза.

- **Дельта применяется туда, куда применено изменение.** Исправление, перенесённое в ветку
  поддержки, требует дельты в спецификацию **этой ветки**. Дельта только в основную ветку означает,
  что знание версии начинает врать с первого перенесённого исправления, а обнаружится это на
  обращении заказчика.
- **Один перенос — одна дельта в каждую затронутую ветку.** Попало в три ветки поддержки — три
  дельты, по одной в каждой.
- **Версия вне поддержки** (нет в `— (поддерживаемых выпусков пока нет)`) не сопровождается: её знание — K4,
  хранится, но в рабочий контекст агента не индексируется.
- **Вопрос «что система делает сейчас» без указания версии некорректен.** Отвечая на него, всегда
  называйте ветку или тег.

## Описание задним числом

SDD, закрытые до появления спецификаций-фактов, описываются садовником по отчётам ревью и коду,
по одной возможности за проход (задача сопровождения).
