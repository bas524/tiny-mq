# Реализация контракта сообщений

Класс K2.

## Подготовка C++ сообщения

```cpp
void Message::prepareForJakartaSend(std::string destination, Reliability mode,
                                    int32_t priority, int64_t expiration,
                                    int64_t deliveryTime, bool disableId,
                                    bool disableTimestamp);
```

Метод присваивает UUID попытки отправки. При включённом ID заголовок содержит
`ID:` с этим UUID. При отключённом ID C++ хранит пустую строку, которая в Java
представлена как null. При включённом timestamp используется текущее время в
миллисекундах от эпохи, при отключённом записывается 0. Обе подсказки независимы.
Режим доставки, приоритет, адрес назначения и абсолютные времена передаёт
вызывающий код. Подготовка сбрасывает внутренний счётчик повторов до 0 и
`JMSRedelivered` до false. В локальный Java-адаптер метаданные попытки поступают
отдельно. Первая доставка представлена парой false/1, повторная — true и счётчиком
не ниже 2. Значение JMSXDeliveryCount, заданное клиентом, не переносится в снимок.

## Формат хранилища

Декодер читает прежние записи v02 (`0x02`). Писатель сохраняет v02 для значений,
представимых в этой версии, и пишет v03 (`0x03`) для расширенных состояний.
Среди них двоичный или явно пустой correlation ID, явно пустой JMSType, null-текст,
расширенные свойства, базовое сообщение без тела, присутствующее пустое
непрозрачное тело ObjectMessage и непустой адрес назначения. Версии используют
общие смещения полей истечения и времени доставки. Фоновый свип и обновление
кешированного времени доставки принимают обе версии. Обычная отправка и commit
проверены для persistent и non-persistent сообщений.

Java-тело ObjectMessage хранится в C++ как непрозрачные байты. Необязательный
`className` переносится как метаданные тела. Java десериализует тело с
`ObjectInputStream` по стандартной политике фильтрации JVM.

## Локальный Java-модуль

`tinymq.jms` реализует `Message`, `TextMessage`, `BytesMessage`, `MapMessage`,
`StreamMessage` и `ObjectMessage` через официальный Jakarta Messaging API 3.1.

```java
public static MessageEnvelope snapshotForSend(
    TinyMessage message, String messageId, long timestamp, Destination destination,
    int deliveryMode, int priority, long expiration, long deliveryTime)
    throws MessageFormatException;

public static TinyMessage forDelivery(
    MessageEnvelope envelope, boolean redelivered, int deliveryCount,
    JavaMessageAdapter.Acknowledgement acknowledgement);
```

Оба метода принадлежат `JavaMessageAdapter`. Первый снимает копию для отправки
и выставляет переданные заголовки на исходном сообщении. Второй создаёт новый
экземпляр из сохранённого конверта с режимами чтения для полученного сообщения.
`acknowledge()` делегирует подтверждение внедрённому callback. Проверка
квитирования сессии относится к SDD 72.

Из корня компонента локальные проверки запускаются с JDK и JAR API 3.1.0.
Скрипт компилирует модуль с `--release 11` и запускает проверки с
`tests/MessageContract.tsv`.

```sh
sh tests/java/run.sh /path/to/jakarta.jms-api-3.1.0.jar
```

Сетевые компоненты поставляются по SDD 73/74. Совместимость ID между процессами
и при перезапуске проверяется в SDD 74, сквозной Java/C++ round trip — в SDD 77.

## Откат хранилища

В проверке отката старая сборка прочитала отдельную восстановленную копию
эталонной записи TextMessage v02. Кандидат сохранил запись v03 отдельно. Перед откатом после новых записей сначала обработать
принятые сообщения либо сохранить актуальный экземпляр хранилища и применить
версионно безопасную миграцию, сохраняющую эти сообщения. Старую сборку запускать
на проверенном совместимом экземпляре. Восстановление снимка, снятого до появления
новых записей, допустимо только после обработки или сохранения принятых сообщений
по указанной процедуре.
