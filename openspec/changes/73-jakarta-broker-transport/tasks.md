# План REQ-73-1

Редакция 0.11 от 2026-11-28 (Europe/Moscow), для согласования.

## Autonomy Level

R2 для подготовки в отдельной рабочей копии. Owner на R1 согласует
постановку, а после критики — архитектуру и подготовительные правки
сборки. Приёмка результата, публикация и архивирование — отдельные
действия по AEF.

## Stop-conditions

До согласования постановки критик не запускается. До кода нужны
независимая критика и утверждение архитектуры. Смена wire-контракта,
расширение `target_files` или перенос проверки loopback в другой
доверенный контур требует зафиксированного решения. До полной успешной проверки обоих тестов
`WireContractTest.CapabilityNegotiation` и
`WireContractTest.WireConnectionBoundary` срез остаётся незавершённым.
Приёмку также блокируют неполный red-критерий, непрохождение
[REQ-73-1/WireBaseline](specs/jakarta-broker-transport/spec.md#scenario-wirebaseline)
и отсутствие подтверждений Reviewer по структурным пунктам
[WireConnectionBoundary](specs/jakarta-broker-transport/spec.md#scenario-wireconnectionboundary).
Для существующих путей обязателен актуальный receipt проверки `cpp-nfr`
с `technical_verdict=passed`, связанный с разрешённым результатом стадии
`nfr`. Порядок замера и порог заданы в
[профиле cpp проекта](../../../PROJECT.md#проверенные-профили-native-runtime).

### Подготовка исполняемого критерия (Q4)

После свежего согласования и независимой критики Owner отдельно разрешает
доверенную подготовку контрактных headers и минимального buildable каркаса
в тех же семи Scope-файлах. Это решение ещё не принято данным черновиком.
Каркас имеет точные объявления из design, без реализованного STOMP
поведения, и fail-closed результат. Независимая сторона пишет защищённые
тесты по wire-критериям, не по каркасу. WireConnection.h содержит только
стандартные event/result-типы, BrokerServer.h включает его, обратного
include нет. Поэтому тест компилируется без будущей реализации STOMP.
Каркас — временная подготовительная база, не приёмка production-заглушки
и не будущий ProtobufConnection.

Доверенный оператор с SDK из PROJECT конфигурирует и собирает Debug
на этой базе, проверяет наличие двух точных имён через
`./cmake-build-debug/tiny_mq --gtest_list_tests`, затем запускает
`./cmake-build-debug/tiny_mq --gtest_filter='WireContractTest.*'`.
Сборка должна пройти, оба теста должны выполниться, а wire-ожидания —
дать ненулевой exit из-за поведения каркаса. Ошибка configure, compile,
link, отсутствие теста или запрет loopback не считается поведенческим red.
Лог хранит точную команду, SHA, toolchain, обнаруженные тесты и строки
проваленных ASSERT. Недостаточно искусственного безусловного FAIL.
Автор не редактирует защищённые тесты и CMake после фиксации этой базы.

Native Runtime на `6f79fb4` не имеет отдельной red-стадии и не создаёт
поведенческий red автоматически при prepare. `prepare --profile cpp`
проверяет чистую Git-базу и закрепляет её SHA, targets, контракт, registry
и trusted observer snapshot. Затем `verify --actor reviewer` запускает
зарегистрированный cpp-reviewer через workflow_cpp.py с его Debug,
clang-tidy, полным non-Bench прогоном и Release. На каркасе этот verify
даст rejected из-за тестов. Его runtime receipt может дополнительно
подтвердить red при сохранённом raw логе, но не заменяет независимую
проверку, что оба теста реально исполнялись. Инфраструктурный rejected
не годится. Вызов verify здесь только описан, сейчас он не выполняется.

Текущий результат работы — черновик v0.11 для согласования. Каркас
сейчас не создаётся. Native prepare уже при intake
требует чистый HEAD и закрепляет его как base до бизнес-решения Owner и
native Critic. После native Critic архитектурная карточка связывается с
текущим subject. Нет встроенной операции criterion, rebase или импорта
ручной критики. Проверка source scope сравнивает с pinned base и отвергает
изменённые тесты/CMake вне targets. Поэтому нельзя сначала prepare на
v0.11, а затем подложить каркас и защищённые тесты в тот же
checkpoint.

После отдельного разрешения доверенная подготовка делает чистую
зафиксированную базу с каркасом, независимыми тестами, CMake и red-логом.
Если intake checkpoint закрепил более раннюю базу, он сохраняется
неизменным. Для нового baseline создаётся свежая изолированная рабочая
копия и выполняется новый prepare --profile cpp. Требуемые native решения
и критика получаются заново для нового subject. Старые материалы доступны
как контекст, не как receipts и не как перенесённые решения. Это имеет
дополнительную стоимость повторного допуска. Возможное будущее изменение
runtime для контролируемой перепривязки требует отдельной постановки и
не входит в текущий Scope. Существование reset/reprepare или скрытого
override не предполагается.

Каркас как новая NFR-база должен сохранять работоспособность всего
прежнего функционального набора и 15 benchmark-путей. Автор production
начинает только после установления этой чистой базы и требуемого допуска.

### Испытания и native ограничения (Q3, Q5, Q13)

Оба теста обязательны. CapabilityNegotiation сохраняет всю прежнюю
wire-матрицу, полное применимое кадрирование STOMP и реальный loopback.
WireConnectionBoundary использует независимые factory, ManualClock,
WireBoundaryDouble и ScriptedWriter из tests/WireContractTest.cpp.
Через override constructor BrokerDependencies они внедряются до
startLoopback. CapabilityNegotiation и wire benchmark используют
production constructor BrokerServer(limits). Детерминированный heartbeat
берёт productionDependencies и заменяет только clock, сохраняя реальную
фабрику STOMP и writer.
Проверяется та же production-очередь, события, доступный бюджет, точные
байты, partial/would-block/error, deadline ties, EOF/stop, поколения
уведомлений и изоляция двух объектов. Сценарий не заменяет STOMP-проверку
двойником. notifyClockChanged только будит worker, события сериализованы.
Точная защита generation/descriptor reuse проверяется структурным review
и accept/close stress. Публичный TCP/DI API не гарантирует
детерминированный stale notification. Лог отличает реально наблюдённый
reuse от непопавшего в запуск случая.

Reviewer сам повторяет обе проверки и сверяет независимый raw лог loopback
с точным SHA. Нативная песочница не расширяется автоматически. Если она
запрещает loopback, CI или независимый оператор должен воспроизвести тесты
в разрешённой среде, а допустимость такого контура требует решения Owner.
Непроверенный loopback не становится pass по бумажному свидетельству.

Native `verify --actor nfr` выполняет существующую проверку cpp-nfr. Новый wire-профиль из design не входит
автоматически в workflow_nfr.py. Защищённый runner тестового файла имеет
Google Benchmark регистрацию `WireHandshakeProfile` вне двух
gtest-критериев. Она использует существующий main --gbench и не требует
изменения main.cpp. Точная команда после Release-сборки —
`./cmake-build-releasewithdebuginfo/tiny_mq --gbench --benchmark_filter='^WireHandshakeProfile$' --benchmark_repetitions=9 --benchmark_out_format=json --benchmark_out=<путь-лога>`.
Регистрация задаёт Iterations(1), MeasureProcessCPUTime и UseRealTime.
Одна итерация содержит прогрев и 10000 измеряемых сценариев по design,
а p95/p99, ошибки, throughput и RSS сохраняются benchmark counters.
CPU измеряемой части исключает прогрев через PauseTiming/ResumeTiming.
Non-Bench native gtest-прогон эту регистрацию не запускает. Доверенная
подготовка закрепляет runner и команды до red. Оператор
отдельно сохраняет первый воспроизводимый wire baseline, девять повторов,
метрики и capacity evidence. Reviewer/NFR сверяют их самостоятельно.
До появления зарегистрированного wire check это отдельное обязательное
свидетельство приёмки, а не автоматически выдаваемый native receipt.
При отсутствии доказательства приёмка останавливается. Сравнительные
пороги wire определяются отдельным решением. Нужное расширение runtime не подразумевается Scope.
