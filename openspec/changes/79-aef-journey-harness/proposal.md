# Сокращённая оснастка tiny-mq

Класс: изменение оснастки. Компонент: tiny-mq. Состояние: проект на рассмотрении.
Owner: Alexander B. Дата: 2026-11-19.

## Problem
SDD 72 потребовала 40 переходов. Значительная часть оценочных GPT credits
пришлась на основной чат; причинная доля устранимых затрат не измерена.
Координатор вручную собирает контекст, запускает стадии и сопровождает ожидание.
Технический rejected NFR и разрешение Owner на выпуск машинно различаются
недостаточно строго. После archive остаются недоступные относительные ссылки.

## Outcome
Оператор одним входом status/next/record-decision видит текущее состояние,
основание остановки и следующее разрешённое действие. Runtime выполняет
механические prepare/verify/route и ожидание. Owner принимает отдельные решения
о смысле, архитектуре, исключении и результате на конкретных редакциях.
Следующая разработка tiny-mq начинается только на независимо проверенной замене.

## Constraints
Сохраняются пять полей полного INT, десять полей SDD, независимость моделей,
чистый контекст проверяющего, защищённые входы/решения, изоляция записи,
точные источники, исполняемые критерии, отдельная приёмка, факт и аудит.
Старые механизмы качества работают до проверки замены; успешный тест не
означает принятие архитектуры либо результата Owner.
OpenAI и уже разрешённый прямой DeepSeek; новые внешние сервисы не подключаются.
Python standard library; Docker не используется. INT-01 остаётся общим
намерением Jakarta; SDD73–78 не объединяются. Продуктовый код и зависимости
не меняются. M-05 остаётся открытой: +6,59% при бюджете5% — rejected; Mac
не отменяет автоматически результат Intel, ночное окно согласовывается отдельно.

## Success criteria
Один комплект OpenSpec на связный результат компонента: proposal, specs, design,
tasks, позднее acceptance. Нет сгенерированной копии SDD и авторских отчётов
каждой роли в MR. Из proposal доступны Requirement, Test и свидетельство.
Повтор/параллельный next не дублирует запуск. Остановка и восстановление
идемпотентны. Отрицательная проверка остаётся отрицательной при разрешённом
исключении; непривязанное или поддельное разрешение не открывает переход.
Ссылка после archive разрешается из нового расположения.

До реализации фиксируются исполняемые критерии. Приёмка требует независимых
критики, ревью и безопасности, отрицательных тестов границ и собственного
прогона проверяющего; сохранения старых проверок и проверки установленной CLI.
Структурная цель: один вход и ноль отдельных ручных файлов перехода/ожидания;
числовая экономия денег и времени считается гипотезой до сопоставимого измерения.

## Cancellation criteria
Остановить миграцию и вынести вопрос Owner, если нельзя сохранить независимость,
механическую изоляцию, проверку реальных решений, доступность аудита или
совместимость принятых фактов. Не сокращать проверки ради обещанной цены.
Непроверенная реализация Timeline не является основанием для переключения.

## Expected effect
Меньше ручных технических переходов, повторной передачи больших контекстов
и LLM-опросов процесса. Сравниваются полные расходы всех попыток, вмешательства
Owner, читаемость INT→требование→тест→факт, содержательные возвраты,
инфраструктурные повторы и механические переходы отдельно. Credits не USD.

## Journey
| Участник и действие | Наблюдаемый результат |
|---|---|
| Owner задаёт цель и ограничения | Пять полей INT в одном proposal; общий INT-01 остаётся каноническим |
| Аналитик/платформа готовит контракт | Десять полей SDD распределены по комплекту, критерии до реализации |
| Независимый критик проверяет контракт | Вопросы либо заключение о точной редакции |
| Owner принимает архитектуру | Решение не подменяется выводом модели или наличием файлов |

| Новый читатель открывает proposal/факт | Одним переходом находит требование, тест и его результат |
