# Устройство сокращённой оснастки

Состояние: проект; решение Owner об архитектуре и приёмка результата пока отсутствуют.

## Architecture
Локальный Python stdlib runtime .claude/chain/aef.py с одним входом status, next,
record-decision; prepare, verify, resume и archive — технические операции того же
входа. Существующие trace/admission/openspec/fingerprint переиспользуются,
а их регрессионные проверки сохраняются. Код незавершённой Timeline-замены
не копируется. Новых сервисов, библиотек и автоматических публикаций нет.

Контракт читается напрямую: proposal даёт пять бизнес-полей INT, Owner, Problem,
Outcome и ограничения; design — Architecture, дополнительные технические
ограничения, Rollback и Entity inventory; specs — Acceptance Criteria; tasks —
Autonomy Level, Stop-conditions и Evidence. Адаптер строит SDD в памяти.
acceptance.md создаётся независимым Explainer поздно, не является входом начала
реализации. Для многoэтапной Jakarta-цели канонический INT-01 сохраняется,
будущие связные changes отдельно ссылаются на него и не переписывают бизнес-цель.

### Отображение полей и совместимость
Пять ключей INT: goal←proposal/Outcome, constraints←proposal/Constraints,
success_criteria←proposal/Success criteria, cancellation_criteria←proposal/Cancellation criteria,
expected_effect←proposal/Expected effect. Problem и Journey дополняют цель, не
являются шестым/седьмым полем INT. Owner и Component — служебные метаданные.
Десять ключей SDD: Problem←proposal/Problem, Outcome←proposal/Outcome+Success criteria,
Constraints←proposal/Constraints+design/дополнительные ограничения,
Architecture←design/Architecture, Acceptance Criteria←specs, Rollback←design/Rollback,
Autonomy Level←tasks/Autonomy Level, Stop-conditions←tasks/Stop-conditions,
Evidence←tasks/Evidence, Owner←proposal/Owner. Проверяются именно имена и
непустое содержимое, не только количество ключей. Entity inventory проверяется отдельно.

workflow_contract.load_contract возвращает intent/sdd, requirement records,
contract_hash и виртуальный текст с картой строк к исходным файлам.
trace получает единый accessor contract_view: check_sdd и critic_input читают
виртуальное представление native change, legacy SDD читают прежний текст.
Источник/Компонент перед Problem и метаданные формируются из явных полей
канонических файлов, Version/Review Date из .openspec.yaml; значения не угадываются.
Существующие разбор requirements/ID/Scenario/Test, admission и resolve_source
используются на этом представлении. Снимок native — всего контракта/критериев,
а не одного proposal. Trace errors указывают исходный файл/поле. Legacy SDD и
старые проверки остаются регрессионными входами; native trace не возвращает
фиктивные intent:null/sources:[] для полного нового контракта.

Runtime(root, executor=..., source_reader=..., check_runner=...) допускает внедрение зависимостей
только программным тестовым интерфейсом; production CLI не имеет флагов для
фиктивной модели/источника/receipt. main(argv, runtime=...) позволяет тем же
обработчиком CLI проверить OS-lock в разных процессах без платных вызовов.
Fixture-проход не выдаётся за проверку реальных моделей.
Зарегистрированные проверки находятся в workflow-checks.json: version,
default_profile, profiles с code_paths, gates, checks; у check id/argv/inputs/
environment. Args — массив без shell. Check runner можно внедрить программно
в unit-тесте; production использует только native-ограниченный runner.
Provider probe — отдельный ограниченный QA-сценарий на синтетических данных
с фиксированным guard, не способ обойти продуктовые Owner-gates.

### Состояние и выполнение
Plan, журнал и решения записывает runtime; авторских status.json/пакетов нет.
Управляющее состояние находится в защищённой области общего Git-каталога
с отдельным пространством для рабочей копии/change. HANDOFF_DIR хранит полные
логи и снимки; status возвращает компактное представление и пути к ним.
Нативные стадии не пишут канонические управляющие записи. Старые пакеты
читаются как история, не принимаются автоматически как свежие одобрения.

Prepare закрепляет change, бизнес-источник, критерии/фикстуры, targets, модели,
политику проверок и исходную Git-базу. Следующая стадия допустима только после
независимой критики и нужных отдельных решений Owner. Next сам выполняет
механические переходы, запускает стадии и ждёт до границы Owner, отказа или
завершения разрешённой работы; не создаёт решений за человека.

Захват change атомарен через OS-lock. Параллельный next сообщает уже выполняемый
execution без второго запуска. Завершение обрабатывается ровно один раз.
Незавершённый execution при свободном lock — interrupted, а не running.
Resume требует сверки checkpoint, входов и оставшегося процесса; PID сам по себе
не удостоверяет живость. История прерывания и счётчики не сбрасываются.
429, no_progress, лимит, отказ среды и Owner-wait не снимаются повтором next;
автоматического fallback модели нет. Штатные 12 dispatch/5 итераций сохраняются;
разовый допуск 40 для SDD72 не переносится.

### Роли, проверки и изоляция
Модели берутся из chain.env, сохраняются отдельные обязанности Critic, Producer,
Reviewer, специалистов, DocWriter и Explainer. Автор и Reviewer разных
провайдеров; каждый Reviewer начинает чистую сессию. Контекст содержит роль,
канонические источники/нужные разделы и итог проверки; полный лог остаётся по пути.

Стадии запускаются отдельным codex exec через существующие профили OpenAI /
deepseek / deepseek-pro. Новый режим не наследует произвольные разрешения
пользовательской конфигурации, MCP/плагины, hooks или сеть инструментов. Модель
вызывается только разрешённым провайдером; direct DeepSeek не получает proxy.
Отсутствие поддержки требуемой политики — отказ запуска, а не более широкая среда.

Нативный permissions-профиль Codex разрешает чтение канонических входов и
необходимого toolchain; запись — только в объявленные выходы и рабочую область
сборки/логов. Управляющее состояние, .git, источники и критерии автора закрыты
для записи, credentials/секреты для инструментов закрыты для чтения.
Reviewer получает read-only исходники и отдельные writable build/output каталоги.
Runtime не позволяет расширять scopes флагом из результата модели. Проверяются
реальные отрицательные сценарии записи/чтения, включая новые файлы и symlink.

Для каждого проверяющего runtime выполняет собственные проверки его стадии на
закреплённом содержимом, сохраняет команды, exit, stdout/stderr и окружение;
результат автора не подставляется как собственный прогон Reviewer. Нативные
инструменты могут запросить только зарегистрированные проверки, не произвольную
shell-команду из документа. Автор не формирует trusted receipt. Provenance и
пакеты собирает наблюдатель из фактического запуска, итоговый JSON модели —
заявление, сверяемое с выполнением.

### Технический вердикт и разрешение
Поля раздельны: technical_verdict=passed|rejected|not_applicable|unobserved;
transition=allowed|blocked|owner_required. status=approved вместе с
performance_verdict=rejected без проверенного исключения переход не открывает.

record-decision принимает вид решения, Owner, реальный источник сообщения и
точное связывание. Доверенный координатор проверяет подлинный user_message
из исходного Codex-чата/его локального журнала: ID/редакцию, точный текст, контекст
вопроса для краткого ответа. Пересланное поручение или текст агента не заменяет
сообщение Owner. Запись из модельной стадии запрещена sandbox-политикой и
проверкой активного execution. Возможность передать --owner не удостоверяет личность.
Источник решения — журнал локального аккаунта Codex: sessions рекурсивно по
всем датам и archived_sessions. resolve_codex_source сверяет session_meta.id,
полный внутренний item/message ID, turn_id и digest текста. Принимается только
response_item/message с role=user и content_item_metadata.provenance.type=user.
Tool/delegation/assistant, конфликтующие дубликаты ID, неизвестные ID, неверный
thread/turn, другая цитата и отсутствие происхождения отвергаются. UI-ID при
необходимости нормализуется в реальный item ID вместе с turn/digest, не по
подстроке UUID. Положительный случай читает реальный формат локального журнала.

Граница доверия — Owner локальной сессии и доверенный координатор, который
связывает ответ с показанной карточкой решения и проверяет его смысл.
Runtime не распознаёт согласие по произвольному наличию слова «принимаю».
Краткий ответ требует исходного вопроса/карточки с subject/action/REQ/debt;
pending decision и связь с ответом сохраняются вне writable области агента.
Это не новая криптографическая система удостоверения личности человека и не
автоматическое подтверждение координатором. Привязка показывается Owner.
Доверенное свидетельство регистрации сохраняет исходный user-record/контекст
и digest; исчезновение исходного журнала не теряет уже проверенный аудит.


Решение фиксирует hash proposal/контракта; исключение дополнительно фиксирует
gate и проверенный receipt измерения, полное множество затронутых REQ,
разрешённое действие и связанную открытую задачу с Spec ref. Источник должен
реально существовать и совпадать с сохранённой цитатой. Координатор не расширяет
смысл ответа машинным списком действий. Неизвестный источник/редакция, иные REQ
или действие, изменение измерения/контракта, закрытая задача блокируют переход.

Исключение допускается для явно указанного NFR-результата, сохраняет rejected
и не разрешает обход scope, источников, независимости, изоляции, безопасности
или обязательного CI. Иное изменение политики требует отдельного решения.
SDD72 остаётся исторически принятой с открытым REQ72-9/M05; её старый пакет
не становится универсальным разрешением новой работы.

### Исполняемое подтверждение границ
Кроме быстрых unit-тестов обязательны интеграционные критерии:
(1) два отдельных процесса через main/next с общей стартовой границей и
реальным lock; (2) SIGKILL собственного fixture-наблюдателя с ещё живым
fixture-дочерним процессом, без повторного запуска до reconciliation;
(3) native sandbox с реальной политикой runtime и отрицательными файловыми
операциями; (4) отдельный opt-in codex exec smoke для OpenAI и direct DeepSeek.
Последний использует только синтетический контракт и доверенный guard-скрипт,
не передаёт реальные бизнес-данные/секреты. Проверка настоящих credential-путей
делает только os.open и немедленный close при неожиданном разрешении: ни один
байт секрета не читается и не попадает в вывод. Ожидается отказ доступа.
Новые файлы, atomic replace и symlink также проверяются.

Smoke фиксирует фактическую команду/профиль/binary hash и инструментальный
event выполнения guard с кодом возврата и одноразовым маркером; одного JSON
модели «проверил» недостаточно. Skip/unavailable не считается положительным
результатом при переключении оснастки. В обычном CI платные smoke не запускаются;
перед приёмкой нужен локальный успешный receipt этих проверок.

### Свидетельства и актуальность
Receipt привязан к предмету проверки: содержимое, тесты и их зависимости,
команда, toolchain/configuration/окружение и применимая базовая ревизия.
Правка acceptance не отменяет проверку неизменённого кода; само объяснение
проверяется отдельно. Изменение контракта снимает его прежний допуск; изменение
тестов требует независимого разбора критериев до новой реализации.
Неизвестная зависимость вызывает консервативную повторную проверку.
Изменённый/отсутствующий лог или снимок не принимается.

### Факт, архив и миграция
Факт обновляется только после отдельной приёмки Owner; proposal и старый SDD
не подменяются текущим поведением. При archive относительные локальные ссылки
переносятся с сохранением адресата; для ссылок внутрь change применяется новый
путь архива. Проверка выполняется после переноса. ID и закреплённые ссылки
Источник: repo:...@SHA не переписываются. Переход неполный при потерянной ссылке.

В SDD72 добавляется явная историческая пометка с принятыми REQ1–8, фактом в
OpenSpec и открытой M05. Шесть ссылок её archived proposal исправляются,
исторический текст сохраняется. Никаких новых perf-прогонов и исполнения M05.

До принятия замены старая цепочка остаётся доступна; отдельный интеграционный
тест проверяет её сохранность. Новые SDD/продуктовые changes не запускаются
старым входом: сообщение направляет на status новой оснастки. После независимых
проверок и решения Owner переключаются AGENTS/START-HERE/PROJECT и правила
OpenSpec; старые свидетельства сохраняются, лишние авторские копии удаляются
только после переноса уникального содержания.

Логи не копируются в MR. До закрытия runtime собирает manifest/hash и пакет
аудита в стабильном локальном хранилище проекта, доступном Owner, с командой
проверки. Рабочая копия не единственное место обязательного аудита. Срок хранения
и удаление требуют явного решения, локальная копия не называется вечной/удалённой.
Публикация/merge не выводятся из приёмки автоматически.

## Rollback
До переключения: удалить только новую реализацию/изменённые входы этого change
из ветки, сохранив полные свидетельства и исходную цепочку. После переключения:
остановить новые запуски, согласовать возврат с Owner, восстановить прежнюю
редакцию входа и policy без преобразования accepted фактов в черновики.
Состояние новой цепочки, решения и логи сохраняются read-only. Незавершённые
процессы сначала сверяются и останавливаются; старый router не продолжает их.

## Вопросы до реализации
Owner должен отдельно подтвердить бизнес-текст этой редакции и предложенное
устройство. Технически ещё проверяются codex exec + native profile + прямые
провайдеры, новые/атомарные записи, секреты и собственные проверки Reviewer.
Синтетическая проверка Codex0.170.0 разрешила один файл и запретила запись
контракта/решения/постороннего файла и чтение фиктивного секрета; это не полная
проверка запуска модели и не приёмка оснастки.
