Функционально спека закрыта корректно: **оба пункта `Test plan` покрыты, тесты не
холостые** (проверено мутациями), открытый вопрос про durable-хранилище закрыт

Отклоняю по единственной причине: **новая структура `_inFlight` вносит квадратичную
по числу неподтверждённых сообщений стоимость в `Consumer::acknowledgeOn()`** —
горячий путь ack. На каноничном для `CLIENT_ACKNOWLEDGE` паттерне «принять пачку,
затем подтвердить» ветка медленнее `main` на **+16 % при 100 неподтверждённых и
+134 % при 1000**, при пороге проекта ~5 %. Существующие бенчи этого не видят,
потому что все они работают в режиме «один recv → один ack» (N=1), где эффекта нет.

Это ровно тот случай, который `CLAUDE.md` описывает словами «When adding
functionality on a hot path that existing benchmarks don't cover, add a benchmark
for it» — бенчмарка нет, и потому перф-гейт Producer'а прошёл вхолостую.

## 3. Решение №1 — `refreshCachedStorageBytes()` вместо patch-метода (ADR-0008): **корректно**

### Рассуждение Producer'а верно — проверено экспериментом

Producer утверждает: к моменту `recover()` кэш уже пуст, поэтому patch-метод по
образцу `patchCachedDeliveryTime` (который делает ранний выход при пустом кэше,
`Message.cpp:36`) молча ничего бы не сделал.

Подтверждаю по коду: `Consumer::recv()` на быстром пути делает
`message->_cachedStorageBytes.clear()` (`Consumer.cpp:86`) сразу после `fromBytes`.
То есть после первой доставки кэша нет, и `patch*`-метод был бы no-op.

Подтверждаю экспериментом. Мутация — закомментировал `msg->refreshCachedStorageBytes()`
в `Consumer::recover()`, пересобрал:

```
[  FAILED  ] RecoverTest.ClientAckRedeliversUnacked
    RecoverTest.cpp:80: Value of: again0->jmsHeaders.redelivered
      Actual: false   Expected: true
[  FAILED  ] RecoverTest.DurableSubscriberNotRepersisted
[       OK ] RecoverTest.NonPersistentRedelivery      <-- дефект НЕ виден
```

Это буквальная иллюстрация ADR-0008: непересистентный тест дефект не ловит, а
персистентный ловит. Producer поставил PERSISTENT в основном тесте осознанно и
правильно.

### Сама реализация корректна

```cpp
void Message::refreshCachedStorageBytes() {
  if (!isPersistent()) return;
  auto bytesData = toBytes();
  std::vector<char> data;
  data.reserve(1 + bytesData.size());
  data.push_back(static_cast<char>(type()));
  data.insert(data.end(), bytesData.begin(), bytesData.end());
  _cachedStorageBytes = std::move(data);
}
```

- **Согласованность с `toBytes`/`fromBytes`.** Раскладка `[1-байтовый type][toBytes()]`
  посимвольно совпадает с `Consumer::preparePush` (`Consumer.cpp:179-186`) и с тем,
  что читает быстрый путь `recv` (`Consumer.cpp:82-85`). `type()` и `dataAsBytes()`
  виртуальны, так что подтип (`TextMessage` и др.) сериализуется правильно.
- **Потери данных нет.** Проба `ZZ_RecoverPreservesBodyAndProperties` гоняет
  PERSISTENT `TextMessage` с телом, двумя свойствами (`string` + `int`),
  `correlationId`, `type`, `replyTo`, `priority=7` через полный цикл
  recv → recover → recv. Всё восстанавливается: тело, `uuid`, `number`,
  `reliability` и все четыре строковых заголовка. Поля вне `jmsHeaders`
  (`_number`, `uuid`, `reliability`, свойства, payload) — все они пишутся `toBytes()`
  и читаются `fromBytes()`, ничего из исходной записи не теряется.
- `_storageTomId` / `_storageOffset` не входят в сериализацию и живут в объекте —
  последующий `acknowledgeOn` находит запись по быстрому пути. Проверено пробами.

### Замечание O1 (не блокер): кэш и запись на диске расходятся намеренно

`refreshCachedStorageBytes()` правит только in-memory кэш; запись в
`ConcurrentLinearStorage` остаётся со старыми `redelivered=false` /
`deliveryCount=0`. Следствие: **`deliveryCount` и `redelivered` не переживают
перезапуск брокера**. Измерил пробой `ZZ_DurableRestartAfterRecoverCountsRecords`
(recover → уничтожить `Exchange` → пересоздать → реплей durable-подписки):

```
[PROBE] durable replay count=2  deliveryCount sum=0
```

Спека 23 этого не требует, JMS оставляет долговечность `JMSXDeliveryCount` на
усмотрение реализации — так что это не нарушение. Но поведение стоит записать в
`docs/features/23-*.md`, иначе оно станет сюрпризом при реализации
`maxDeliveryCount`/DLQ. Комментарий в `Consumer::recover()` про «Never touches the
on-disk record» это фиксирует, но только для читателя кода.

## 4. Открытый вопрос спеки — durable-хранилище: **закрыт, подтверждаю фактически**

По коду: `Consumer::recover()` вызывает исключительно `_queue->enqueue(msg)` — не
проходит ни через `Destination::save`, ни через `deliverCommitted`, ни через
`persistToOfflineSub` (`Destination.cpp:203-208`, единственное место записи в
durable-хранилище). Заявление Producer'а верно.

Тест Producer'а `DurableSubscriberNotRepersisted` проверяет только отсутствие
немедленных дублей. Я усилил проверку до реального перезапуска (`ZZ_Durable...`
выше): 2 сообщения отправлено, оба получены, `recover()`, оба получены повторно,
**не подтверждены**, `Exchange` уничтожен и пересоздан, durable-подписка
переоткрыта → **реплей ровно 2 сообщений**. Если бы `recover()` дописывал в
durable-хранилище, было бы 4. Вопрос закрыт по-настоящему.

## 5. Решение №2 — исключение `AUTO_ACKNOWLEDGE` из `_inFlight`

### (а) По JMS — верно **сегодня**, но с оговоркой

По JMS 2.0 сообщение в `AUTO_ACKNOWLEDGE` считается подтверждённым, когда
**либо** успешно вернулся `receive()`, **либо** успешно вернулся `onMessage()`
асинхронного `MessageListener`. Второй случай — это и есть каноничный сценарий, где
`recover()` при `AUTO_ACKNOWLEDGE` обязан что-то вернуть: вызов `recover()` **изнутри**
`onMessage()`, до его успешного возврата, требует повторной доставки текущего
сообщения.

Проверил: в кодовой базе `MessageListener` / `onMessage` / асинхронной доставки
**не существует** (`grep` по всему дереву — ни одного вхождения; M0–M2 — синхронный
in-process `recv`). Значит легитимного сценария, который сейчас теряется, нет:
между возвратом `recv()` и любым возможным вызовом `recover()` сообщение уже
подтверждено по определению. Моя проба `ZZ_AutoAckRecoverIsNoOp` фиксирует текущее
поведение: `recover()` при `AUTO_ACKNOWLEDGE` ничего не возвращает.

**Замечание O2 (не блокер, но обязательное к записи).** Это корректно только пока
нет `MessageListener`. Когда появится асинхронная доставка, исключение
`AUTO_ACKNOWLEDGE` из `_inFlight` станет **дефектом конформанса**. Нужно:
(1) записать это ограничение в `docs/features/23-*.md`; (2) добавить пометку в
спеку `MessageListener`, что она обязана вернуться к `Consumer::recv()`
(`Consumer.cpp:136`). Комментарий в коде хорош, но говорит «нечего восстанавливать»
как о свойстве JMS, а это свойство *текущей* модели доставки tiny-mq.

### (б) Утечка была и устранена — подтверждаю

Утечка реальна: `acknowledgeOn()` при `AUTO_ACKNOWLEDGE` в этой кодовой базе не
вызывается ни одним тестом и ни одним бенчем (проверил `ClientAckTest`,
`BenchmarkTest`), а это единственное место, снимающее запись с `_inFlight`. Без
guard'а вектор рос бы на весь срок жизни консьюмера. Guard в `Consumer.cpp:136`
устраняет её. Для `DUPS_OK_` и `INDIVIDUAL_` `acknowledgeOn` вызывается явно
(`DupsOkAckTest`, мои пробы `ZZ_DupsOkRecover` / `ZZ_IndividualAckRecover`) —
рост `_inFlight` там ограничен неподтверждённым набором, что семантически требуется.

### (в) Объяснение «смещение от порядка прогонов» — заслуживает доверия, перемерил сам

Не поверил на слово, перемерил независимо: release (`RelWithDebInfo`) обеих версий,
`main` на merge-base `ce54047` в отдельном worktree вне репозитория,
**сбалансированный ABBA-порядок** (MAIN, BRANCH, BRANCH, MAIN) ×6, ожидание падения
load average перед стартом, медиана `cpu_time` по 12 прогонам на бенч:

| Бенч | MAIN (медиана) | BRANCH (медиана) | Δ медианы | Δ min |
|---|---|---|---|---|
| `AutoAck_NonPersistent_RoundTrip` | 152.08 ns | 155.03 ns | **+1.94 %** | +2.76 % |
| `Topic_AutoAck_NonPersistent_RoundTrip` | 166.14 ns | 163.55 ns | **−1.56 %** | +0.63 % |

Два бенча дают разный знак, оба внутри порога ~5 %, разброс (σ ≈ 5–8 ns) сопоставим
с эффектом. Направленной регрессии на пути `AUTO_ACKNOWLEDGE` нет.
**Вывод Producer'а подтверждаю**: наблюдавшийся ранее разрыв 7–9 % — смещение
порядка измерения, а не следствие диффа. ABBA-балансировка его снимает; это,
кстати, и есть методика, которую стоит закрепить в `perf-check` вместо
«цикл 1 в одном порядке, цикл 2 в другом».

## 6. B1 (**блокер**) — квадратичная регрессия на пути `CLIENT_/DUPS_OK_/INDIVIDUAL_ACK`

### Механизм

`Consumer::acknowledgeOn()` (`Consumer.cpp:329-331`):

```cpp
auto flightIt = std::find_if(_inFlight.begin(), _inFlight.end(),
                              [&message](const Message::Ptr& m) { return m.get() == &message; });
if (flightIt != _inFlight.end()) _inFlight.erase(flightIt);
```

Линейный поиск по вектору плюс `erase` со сдвигом. При `n` неподтверждённых
сообщений один ack стоит O(n), а подтверждение всей пачки — **O(n²)**.

Паттерн «принять много, потом подтвердить» — это не экзотика, а **основной сценарий
`CLIENT_ACKNOWLEDGE`**: весь смысл режима в батчевом подтверждении. Для
`DUPS_OK_ACKNOWLEDGE` он тем более типичен — там и сами storage-removal'ы
батчатся пачками по 100 (`Consumer.cpp:349`).

### Замер

Существующие бенчи весь этот класс не покрывают: `ClientAck_Persistent_RoundTrip`
делает `send → recv → ack` в одной итерации, то есть всегда `n = 1`, где эффекта
нет; к тому же он storage-bound (~4000 ns), что топит любые наносекунды.
Non-persistent бенча для `CLIENT_ACK` в наборе нет вообще.

Добавил временный бенч (в дерево не коммитил, обе версии собирал с одинаковым
кодом бенча): `CLIENT_ACKNOWLEDGE`, NOT_PERSISTENT, «отправить N → принять N →
подтвердить N». ABBA, 10 прогонов на точку, медиана `cpu_time`:

| N (неподтверждённых) | MAIN | BRANCH | Δ |
|---|---|---|---|
| 1 | 164.6 ns | 165.8 ns | **+0.68 %** |
| 100 | 16.49 µs | 19.26 µs | **+16.81 %** |
| 1000 | 173.29 µs | 404.97 µs | **+133.70 %** |

Тот же прогон в обратном порядке подтверждения (worst case для линейного поиска):
+15.11 % @100, +95.83 % @1000.

Форма кривой не оставляет сомнений в квадратичности — по пропускной способности:

```
MAIN:    N=1 6.44 M/s   N=100 6.38 M/s   N=1000 6.03 M/s   (плоско — линейно)
BRANCH:  N=1 5.92 M/s   N=100 5.34 M/s   N=1000 2.54 M/s   (обваливается)
```

`main` держит ~6 M/s независимо от размера пачки; ветка проседает в 2.4 раза уже на
1000. При 10 000 неподтверждённых разрыв будет ещё на порядок хуже.

### Почему это блокер

- `CLAUDE.md`: «treat a significant regression (rule of thumb: > ~5 % throughput/latency
  without justification) as a blocker, not something to defer». Здесь 16 % и 134 %.
- `CLAUDE.md`: «When adding functionality on a hot path that existing benchmarks don't
  cover, add a benchmark for it» — бенча нет, из-за чего перф-гейт Producer'а не мог
  этого увидеть. Producer добросовестно прогнал перф и добросовестно расследовал
  найденное на `AUTO_ACK`; пробел не в старательности, а в покрытии набора бенчей.
- Деградация зависит от нагрузки, а не от конфигурации: она не проявится в тестах и
  проявится в проде тем сильнее, чем больше батч.

### Что требуется от Producer'а (не чиню сам)

1. Заменить линейный поиск на структуру с O(1) удалением. Варианты на выбор:
   `phmap::flat_hash_map<Message*, size_t>` (или по `uuid`) параллельно вектору,
   сохраняющему порядок, с ленивым удалением дыр; либо хранить в самом `Message`
   индекс/итератор позиции в `_inFlight`; либо `std::list` + мапа итераторов.
   Порядок восстановления обязан остаться исходным — это требование спеки.
2. Добавить в `tests/BenchmarkTest.cpp` постоянный бенч на паттерн
   «`CLIENT_ACKNOWLEDGE`, NOT_PERSISTENT, batch N → ack N» хотя бы для N ∈ {1, 100, 1000}.
   Без него регрессия вернётся незамеченной. Non-persistent — принципиально: только
   он достаточно чувствителен, персистентный тонет в storage I/O.
3. Перемерить ABBA-балансированно относительно `ce54047` и приложить цифры.

## 7. Границы, гонки, ADR — чисто

Все пробы ниже прошли на ветке как есть.

| Проверка | Результат |
|---|---|
| `recover()` без in-flight сообщений | no-op, не падает (`ZZ_EmptyAndDoubleRecover`) |
| Два `recover()` подряд | второй — no-op: `deliveryCount` остаётся 1, дублей нет. `swap` в начале `Consumer::recover()` делает операцию идемпотентной по построению |
| `deliveryCount` через 3 цикла | 0 → 1 → 2, `redelivered` false → true → true |
| `INDIVIDUAL_ACKNOWLEDGE`: подтвердить второе, `recover()` | возвращается только первое; подтверждённое не всплывает |

| Обе durable-ветки | `save` / `deliverCommitted` не менялись и не должны были (§4) |
| Формат `0x02` | не тронут |
| Queue-семейство, общая очередь | `recover()` на одном консьюмере кладёт сообщение в **общую** `_queue` дестинации, так что забрать его может другой консьюмер — для Queue это JMS-легально. ### Замечание O3 (не блокер): восстановленные сообщения встают в хвост

`_queue->enqueue(msg)` кладёт в хвост своего priority-бэнда, поэтому если в очереди
уже ждут новые сообщения того же приоритета, повторно доставляемые уйдут **за**
ними. Спека 23 требует лишь исходного порядка *внутри* восстанавливаемого набора —
это выполнено, — а JMS не предписывает жёстко приоритет redelivery над новыми
сообщениями. Поведение стоит зафиксировать в документации фичи.

## 9. B2 (**блокер**) — интрузивные ссылки переживают `copy()` и не знают владельца

### Механизм — две независимые дыры в одном инварианте

Дизайн предполагает: **сообщение состоит максимум в одной цепочке, и цепочка эта —
того консьюмера, который его выдал.** Ни то, ни другое не обеспечено.

**(а) `copy()` копирует ссылки.** `Message.h:98-99` объявляет
`Message(const Message&) = default` (и так же `operator=`, move-версии), а новые поля
`_inFlightNext` (владеющий `shared_ptr`) и `_inFlightPrev` (сырой) — обычные члены.
`copy()` во всех подтипах реализован через копирующий конструктор
(`TextMessage.cpp:24` и аналоги), а `copy()` — это **основной механизм доставки**:
`Consumer::preparePush` (`Consumer.cpp:176`), `Destination::persistToOfflineSub`
(`Destination.cpp:199`), `Destination::deliverCommitted` (`Destination.cpp:464`).
Значит копия сообщения, находящегося в in-flight цепочке, наследует и владеющий
указатель на следующий узел чужой цепочки, и обратный указатель в неё же.

**(б) `acknowledgeOn()` не проверяет владельца.** Тест «отслежено ли сообщение»
(`Consumer.cpp:377`) — `message._inFlightPrev != nullptr || _inFlightHead.get() == &message`
— истинен для **любого** сообщения с непустым `prev`, в том числе принадлежащего
цепочке другого консьюмера. Дальше код пишет `prevPtr->_inFlightNext = ...` в чужой
узел и ставит `_inFlightTail = prevPtr` — указатель на чужое сообщение.
В раунде 1 линейный поиск по собственному вектору делал такой вызов безопасным no-op:
проверка принадлежности была встроена в структуру. Интрузивный дизайн её потерял.

Отдельно: `recv()` при пустой цепочке (`Consumer.cpp:157-159`, ветка `else`) ставит
`_inFlightHead = message`, **не обнуляя** `message->_inFlightPrev` и не проверяя
`_inFlightNext`. Поэтому сообщение с унаследованными от копии ссылками становится
головой с непустым `prev` — и инвариант «`prev == nullptr` ⟺ голова» ломается молча.

### Ответ на вопрос «нет ли пути, где один `Message::Ptr` попадает к двум консьюмерам»

Проверил перечисленные пути — **сам fan-out чист**:

| Путь | Вывод |
|---|---|
| Topic fan-out, `Destination::save` (`Destination.cpp:63-70`) | каждому консьюмеру идёт `Consumer::push` → `preparePush` → `message.copy()`; общий `Ptr` не разделяется |
| `Destination::deliverCommitted` (`Destination.cpp:456-465`) | queue-семейство — `std::move` + `return` (ровно один консьюмер); topic — `message->copy()` на каждого |
| durable-доставка, `persistToOfflineSub` (`Destination.cpp:198-208`) | работает с копией, в очередь не кладёт |
| транзакционный путь | сообщения в `_transactQueue`, в in-flight цепочку не линкуются вовсе |
| повторная постановка из `recover()` | обе ссылки узла обнуляются (`_inFlightNext` — move'ом, `_inFlightPrev` — явно) **до** `_queue->enqueue`; идемпотентно |
| `replayStoredMessages` | создаёт новые объекты-оболочки из байтов хранилища |

То есть беда не в том, что один и тот же `Ptr` уходит двоим. Беда в том, что
**копия несёт состояние оригинала**, а `acknowledgeOn()` принимает чужие сообщения.

### Воспроизведение — четыре пробы, все на неизменённой ветке

**ZZ5 — самая обыденная: подтверждение не на том консьюмере одной очереди.**
Никакого форвардинга, только публичный API (`session.createConsumer(q)` дважды):

```
c1->recv() ×2            → цепочка c1: [m0, m1]
c2->acknowledgeOn(*m1)   → prev(m1) = m0 ≠ null ⇒ ветка «отслежено»:
                           m0->_inFlightNext = null (цепочка c1 порвана),
                           c2->_inFlightTail = m0   (указатель в чужую цепочку)
p->send(m2); c2->recv()  → _inFlightTail->_inFlightNext = m2
                           ⇒ m2 уехал в цепочку c1, голова c2 осталась пустой
session.recover()
```
Результат: `c2 redelivered 0 (expected its own 1)` — сообщение c2 потеряно для
`recover()` и лежит в чужой цепочке; c1 при следующем `recover()` доставит себе
чужое сообщение. Инвариант «`_inFlightHead == nullptr` ⟺ `_inFlightTail == nullptr`»
у c2 нарушен.

**ZZ1 — форвардинг неподтверждённого сообщения (мейнстримный JMS-паттерн: мост,
DLQ, retry).** `pb->send(*r0)`, где `r0` — голова цепочки консьюмера A с непустым
`_inFlightNext`. Копия уносит владеющий указатель на `r1`; после `sb.recover()`:

```
LEAK: consumer B received a message it was never sent: A-second
```

Консьюмер B получил сообщение чужой очереди чужой сессии — межсессионная утечка
данных. Заодно это разделяемое владение узлом между двумя консьюмерами, которые по
ADR-0005 могут жить в разных потоках, — то есть ещё и гонка.

**ZZ2 — форвардинг сообщения из середины цепочки:**

```
ZOMBIE: acknowledged message redelivered by recover(): A-second
A lost a message from its own in-flight chain
```

Подтверждённое сообщение возвращается `recover()`'ом (голова B так и не сдвинулась,
потому что сработала ветка `prevPtr`), а цепочка A теряет узел.

**ZZ4 — то же плюс освобождение памяти: `_inFlightTail` консьюмера A повисает.**
Под ASan (`cmake-build-asan`):

```
==14349==ERROR: AddressSanitizer: heap-use-after-free on address 0x6150000005e8
READ of size 8 at 0x6150000005e8 thread T0
    #3 tiny_mq::Consumer::recv(long long) Consumer.cpp:156
freed by thread T0 here:
    #1 tiny_mq::TextMessage::~TextMessage() TextMessage.h:19
```

`Consumer.cpp:156` — это `_inFlightTail->_inFlightNext = message;`, запись в
освобождённый объект. В обычной сборке падения нет: `recover()` вернул 1 сообщение
из 3, тихо. Это ровно тот профиль дефекта, который ADR-0006 описывает как самый
опасный — не воспроизводится детерминированно и не диагностируется.

### Что требуется от Producer'а (не чиню сам)

1. **Копия не должна наследовать ссылки.** Объявить пользовательские
   копирующий/перемещающий конструктор и присваивание `Message`, обнуляющие
   `_inFlightNext`/`_inFlightPrev` (копия по определению ни в одной цепочке не
   состоит). Молчаливый `= default` на классе со скрытым состоянием идентичности —
   корень (а).
2. **`acknowledgeOn()` обязан проверять владельца.** Дешёвый и заодно
   самодокументирующий вариант — тег владельца на сообщении
   (`Consumer* _inFlightOwner`, ставится в `recv()`, снимается при отцеплении):

   одновременно даёт место для `assert`. Стоимость — один указатель и одна
   проверка, горячий путь не трогает.
3. **`recv()` должен обнулять/проверять ссылки при линковке** (ветка `else`
   не сбрасывает `_inFlightPrev`) — защита в глубину, а не замена п. 1.
4. **Тесты на все четыре сценария**: ack на чужом консьюмере той же очереди (ZZ5),

5. Прогнать сьют под `cmake-build-asan` — сборка уже сконфигурирована и ловит этот

## 10. B3 — `clearInFlight()` в деструкторе не защищён (ADR-0006)

`~Consumer()` (`Consumer.cpp:48-62`) получил новый вызов `clearInFlight()`, а тот
начинается с `TRACE(_logger)`. `TRACE` при включённом trace-уровне выполняет
`Poco::format(...)` (аллокация → `std::bad_alloc`) и запись в канал логирования
(Poco бросает на ошибках ввода-вывода). Деструктор неявно `noexcept` — значит
`std::terminate`.

Само разрушение цепочки безопасно: деструкторы `Message`/`TextMessage` тривиальны,
`shared_ptr` не бросает. Единственный источник — `TRACE`.

Смягчающее обстоятельство: в том же деструкторе `TRACE`, `flushPendingAcks()` и
`poco_information` уже стоят без защиты **до** этого диффа — то есть практика
преэкзистентна, и B3 — не новый класс дефекта, а новый экземпляр старого. Но
ADR-0006 прямо вменяет ревьюеру проверку «при добавлении в деструктор любых
вызовов», и цена устранения нулевая, а артефакт и так возвращается:
обернуть `clearInFlight()` в try/catch с `poco_error` по образцу соседнего
`rollback()`, либо убрать `TRACE` из `clearInFlight()` и пометить её `noexcept`.
Второй вариант предпочтительнее: `clearInFlight()` вызывается только из
деструктора, `noexcept` там честно выражает контракт.

| 100 | 16.28 µs | 6.14 M/s |
| 1000 | 174.5 µs | 5.73 M/s |

Пропускная способность **плоская по N**. Для сравнения, раунд 1 (вектор) на моём
же замере: 5.92 → 5.34 → **2.54 M/s**. Форма кривой, которая и была содержанием
B1, исправлена. Цифры Producer'а (`branch` 192.2 / 16721 / 178202 ns) с моими
согласуются в пределах шума машины (`cv` 1.8–5 % при load average ≈ 7).

### Вердикт по остатку

Принимаю 8.3 % @ N=1, 4.05 % @ N=100, 5.7 % @ N=1000 как **цену функциональности**,
а не регрессию. Основания:

1. **Базы для сравнения не существует.** На `main` нет ни `_inFlight`, ни
   `recover()`; бенч туда бэкпортирован. Порог «~5 %» в `CLAUDE.md` сформулирован
   про *регрессию* существующего поведения — здесь же измерена стоимость кода,
   которого в базе нет вовсе. Спека 23 по определению требует отслеживать
   in-flight; ноль стоимости недостижим.
2. **Регрессии существующих путей нет.** `AUTO_ACKNOWLEDGE` и topic-доставка
   измерены в раунде 1 ABBA-балансированно: **+1.94 % / −1.56 %**, разного знака,
   внутри шума. Раунд 2 в этих путях ничего не менял: для `AUTO_ACKNOWLEDGE`
   ветка `else if` не берётся, линковки не происходит. Отдельно перемерять не стал —
   и честно это отмечаю: моё «регрессии нет» для доставки опирается на замер
   раунда 1 плюс чтение диффа, а не на новый прогон.
3. **Остаток объясняется механикой и правдоподобен по величине.** ~15 нс на
   сообщение при N=1 — это две записи указателей, копия `shared_ptr` (атомарный
   инкремент) при линковке и атомарный декремент при отцеплении. Ниже этого можно
   уйти только отказавшись от владения в цепочке, а владение — как раз то, что
   даёт гарантию «сообщение живо, даже если приложение уронило свой `Ptr`».
4. **Три конструкции честно перебраны и измерены** (хеш-индекс 19 %,
   `std::list` + итератор 7–19 %, интрузивный список 4–8 %). Дальнейшая
   микрооптимизация не окупается: разница между 4 % и 8 % на этой машине
   сопоставима с `cv` бенча.

Отдельно отмечаю добросовестность: Producer сообщил остаток без округления вниз и
не выдал его за «в пределах порога». Это правильное поведение.

**Важное следствие для раунда 3:** устранение B2 (обнуление ссылок в копирующем
конструкторе + тег владельца) горячий путь не удорожает — один указатель и одно
сравнение. Полный ABBA-перезамер после него не требуется; достаточно прогнать
`ClientAck_Batch_NonPersistent` и убедиться, что кривая осталась плоской.

## 17. B4 (**блокер, он же повод к эскалации**) — `acknowledgeOn()` разрушает собственный аргумент и продолжает им пользоваться

### Механизм

`Consumer.cpp:405-421`:

```cpp
if (message._inFlightOwner == this) {
  Message* prevPtr = message._inFlightPrev;
  Message::Ptr nextOwning = std::move(message._inFlightNext);
  Message* nextPtr = nextOwning.get();

  if (prevPtr) {
    prevPtr->_inFlightNext = std::move(nextOwning);  // ← роняет владельца `message`
  } else {
    _inFlightHead = std::move(nextOwning);           // ← роняет владельца `message`
  }
  ...
  message._inFlightPrev = nullptr;   // строка 420 — запись в, возможно, уже освобождённый объект
  message._inFlightOwner = nullptr;  // строка 421
}

if (message.isPersistent()) { ... message._storageTomId ... message.uuid ... }  // строки 424+
```

Обе ветки присваивания уничтожают **старое** значение `shared_ptr`, а старое
значение — это владеющая ссылка на сам `message`. Если цепочка была последним
владельцем, объект освобождается прямо внутри присваивания (в libc++
`operator=(shared_ptr&&)` — это `shared_ptr(std::move(r)).swap(*this)`, старое
значение умирает вместе с временным объектом, то есть до следующего оператора).
Дальше функция ещё дважды пишет в освобождённую память (строки 420-421) и, для
персистентного сообщения, **читает из неё `_storageTomId`/`_storageOffset`/`uuid`
и по ним удаляет запись из хранилища** (строки 424+). То есть окно UAF — не две
строки, а весь остаток `acknowledgeOn()`, и в персистентном случае из мусора
формируется адрес записи для `remove`.

### Почему «цепочка — последний владелец» это штатное состояние, а не экзотика

Так написано в самом дизайне. Комментарий к `Message::_inFlightNext` (`Message.h:76-80`)
обещает это как гарантию:

> `_inFlightNext` is the *owning* pointer … keeps every in-flight message alive
> **even if the caller drops its own `Message::Ptr` without acknowledging**

Приложению явно разрешено уронить свой `Ptr` и продолжать держать `Message&`
(сигнатура `acknowledgeOn(const Message&)` ровно это и приглашает). Как только
оно так делает и потом подтверждает — UAF. Никакого форвардинга, никаких двух
консьюмеров, только публичный API одной сессии.

### Воспроизведение (проба ZZ6, вне дерева)

```cpp
Message::Ptr r0 = consumer->recv();
Message &ref0 = *r0;
r0.reset();                    // цепочка — единственный владелец (документированное состояние)
consumer->acknowledgeOn(ref0); // ветка «был головой»
```

`cmake-build-asan`, `ASAN_OPTIONS=detect_stack_use_after_return=1`:

```
ERROR: AddressSanitizer: heap-use-after-free on address 0x615000000378
WRITE of size 8 at 0x615000000378 thread T0
    #0 tiny_mq::Consumer::acknowledgeOn(tiny_mq::Message const&) Consumer.cpp:420
freed by thread T0 here:
    #1 tiny_mq::TextMessage::~TextMessage() TextMessage.h:19
    ...
    #8 std::shared_ptr<tiny_mq::Message>::operator=(std::shared_ptr<tiny_mq::Message>&&) shared_ptr.h:576
    #9 tiny_mq::Consumer::acknowledgeOn(tiny_mq::Message const&) Consumer.cpp:413
```

Строка 413 освобождает, строка 420 пишет. Проба удалена из дерева после прогона.

### Что это значит по инвариантам

- **ADR-0006 по духу**: класс дефекта тот же, что и в трёх предыдущих случаях
  проекта — не воспроизводится детерминированно, в обычной сборке не падает,
  а тихо портит память и (для персистентного сообщения) состояние хранилища.
- Сьют 133/133 и ASan 9/9 этого **не видят**: ни один тест не подтверждает
  сообщение, уронив свой `Ptr` — везде `acknowledgeOn(*r)` при живом `r`.
  То есть зелёный ASan-прогон здесь не свидетельство отсутствия дефекта, а
  свидетельство того, что тесты не заходят в документированное состояние.

### Исправление тривиально — и это отдельный довод

Достаточно снять `message._inFlightPrev`/`_inFlightOwner` **до** первого
присваивания, либо на время отцепления удержать узел живым
(`Message::Ptr self = prevPtr ? prevPtr->_inFlightNext : _inFlightHead;`).
Две строки. Но именно дешевизна каждого отдельного исправления и тревожит:
каждый раунд обнаруживает новую ошибку времени жизни в одном и том же
шестидесятистрочном куске, каждая по отдельности чинится за пять минут, и после
каждой кажется, что теперь-то всё. Это профиль структуры, у которой инварианты
не проверяются ни компилятором, ни типом, а держатся вниманием автора в шести
местах сразу.

## 18. Вопрос задания №1 — держится ли B2 «по построению»: **частично, и это второй довод к эскалации**

### Что проверено и в порядке

- Перечисление полей в четырёх функциях **сейчас полное**: все 10 значимых членов
  (`_number`, `_properties`, `_cachedStorageBytes`, `_storageTomId`,
  `_storageOffset`, `_pendingDeliveryDelay`, `uuid`, `reliability`, `jmsHeaders`,

  ссылок сделал бы их висячими молча.
- `_inFlightOwner` (сырой `Consumer*`) **повиснуть не может**: он ставится ровно
  там же, где узел подцепляется (`recv()`), и снимается на **всех** трёх путях
  отцепления (`acknowledgeOn`, `recover`, `clearInFlight`), а `~Consumer()` через
  `clearInFlight()` обнуляет его у каждого узла своей цепочки. Инвариант
  «`_inFlightOwner != nullptr` ⟺ узел в цепочке этого консьюмера» замкнут;
  сценария «консьюмер мёртв, сообщение живо, тег указывает на освобождённую
  память» я не нашёл. Пункт задания снимаю.

### Что не в порядке

Инвариант «копия не наследует членство в цепочке» теперь держится **договорённостью**:
при добавлении нового поля в `Message` его надо не забыть в **четырёх** рукописных
функциях, и компилятор об этом не скажет ни слова. Цена забывчивости — не «копия
попадёт в чужую цепочку» (это как раз защищено), а **тихая потеря поля при
доставке**: `copy()` и есть механизм fan-out'а (`Consumer::preparePush`,
`Destination::persistToOfflineSub`, `Destination::deliverCommitted`). До раунда 3
`= default` терял ссылки — теперь рукописный список может потерять данные.
Режим отказа сменил знак, а не исчез.

Конструктивная альтернатива стоит десяти строк и снимает вопрос целиком —
завернуть три поля в тип, который сам себя не копирует:

```cpp
struct InFlightLink {
  std::shared_ptr<Message> next;
  Message* prev{nullptr};
  Consumer* owner{nullptr};
  InFlightLink() = default;
  InFlightLink(const InFlightLink&) noexcept {}            // копия ни в одной цепочке не состоит
  InFlightLink(InFlightLink&&) noexcept {}
  InFlightLink& operator=(const InFlightLink&) noexcept { return *this; }
  InFlightLink& operator=(InFlightLink&&) noexcept { return *this; }
};
```

После этого все четыре специальные функции `Message` возвращаются к `= default`,
любое новое поле копируется автоматически, а «копия не в цепочке» становится
свойством **типа**, а не дисциплины. Сам по себе этот пункт я бы блокером не
сделал — но вместе с §17 он часть одного и того же ответа на вопрос
«сколько ещё стоит этот дизайн».

## 21. B4 — **закрыт**, мутационное доказательство приложено

Механизм пина корректен:

```cpp
self = prevPtr ? prevPtr->_inFlightLink.next : _inFlightHead;
```

Это **копия** (не перемещение) владеющей ссылки цепочки на `message`, снятая
**до** обоих присваиваний, которые эту ссылку роняют. `self` живёт до закрывающей
скобки `acknowledgeOn`, то есть перекрывает всё окно — и записи в
`_inFlightLink.prev/.owner`, и чтение `_storageTomId`/`_storageOffset`/`uuid`
в персистентной ветке, и финальное логирование.

### Все пути отцепления в `acknowledgeOn()` — перебрал

| Случай | Ветка | Пин корректен? |
|---|---|---|
| единственный узел | `prevPtr == nullptr`, `self = _inFlightHead`; далее `_inFlightHead = nullptr`, `_inFlightTail = nullptr` | да |
| голова, есть следующий | `self = _inFlightHead`; `_inFlightHead = next`, `next->prev = nullptr` | да |
| середина | `self = prevPtr->_inFlightLink.next`; обе связи перешиты | да |
| хвост | `self = prevPtr->_inFlightLink.next`; `_inFlightTail = prevPtr` | да |
| чужой владелец (`owner != this`) | ветка не берётся, пин не нужен — `message` не в моей цепочке, её ссылку я не роняю | да |
| неперсистентное | пин снимается в конце функции, после него `message` не трогается | да |

Инвариант, на котором держится корректность пина: «`owner == this` ⟹
(`prev ? prev->next : _inFlightHead`) указывает ровно на `message`». Он замкнут:
`owner` ставится только в `recv()` там же, где узел подцепляется, и снимается на
всех трёх путях отцепления. Но, как и весь остальной инвариантный аппарат этой
структуры, он держится вниманием, а не типом (см. §18 раунда 3). **Нит:**
`assert(self.get() == &message);` сразу после присваивания сделал бы его
самопроверяющимся; в release стоит ноль.

## 23. `InFlightLink` — инвариант стал конструктивным, защита переехала, а не исчезла

### Защита действительно в типе

```cpp
InFlightLink(const InFlightLink&) noexcept {}
InFlightLink(InFlightLink&&) noexcept {}
InFlightLink& operator=(const InFlightLink&) noexcept { return *this; }
InFlightLink& operator=(InFlightLink&&) noexcept { return *this; }
```

Пустые тела означают, что члены получают свои
default-member-initializer'ы (`next` — пустой `shared_ptr`, `prev`/`owner` —
`nullptr`) независимо от источника. Все четыре специальные функции `Message`
вернулись к `= default`, и это теперь **корректно по построению**: новое поле
`Message` копируется автоматически, а членство в цепочке не наследуется —
режим отказа §18 («рукописный список молча теряет новое поле») устранён,
а не заменён другим.

### Мутационное доказательство

Заменил четыре тела на `= default`, пересобрал debug:

```
[  FAILED  ] RecoverTest.ForwardingHeadMessageDoesNotLeakChainToOtherConsumer
[  FAILED  ] RecoverTest.ForwardingMiddleMessageDoesNotCorruptEitherChain
[  PASSED  ] 9 tests.
```

Падают **ровно те же два теста**, что и при мутации «рукописные конструкторы
`Message` → `= default`» в раунде 3 (§16). Защита эквивалентна прежней:
переехала, не растворилась.

### Что происходит при перемещении `Message` — разобрал

Вопрос задания. Поведение при `= default`-перемещении `Message`, находящегося в
цепочке:

- **приёмник** получает пустой `InFlightLink` (не в цепочке) — правильно;
- **источник** свой `InFlightLink` **сохраняет** (пустое тело move-конструктора
  источник не трогает). То есть цепочка остаётся целой и по-прежнему указывает на
  исходный объект: соседи хранят его адрес, его `next` по-прежнему владеет
  следующим узлом. Висячих указателей не возникает — что и есть правильный ответ
  на замечание «соседние узлы хранят адрес исходного объекта»: единственная
  безопасная семантика здесь — не переносить связи, и она реализована.

Остаточный (не блокер) эффект: перемещённый-из `Message`, оставшийся в цепочке,
при `recover()` будет доставлен как выпотрошенный объект. Это не небезопасно и
недостижимо в текущем коде — fan-out везде через `copy()`, а `Message` живёт в
`make_shared` и не перемещается (проверено ещё в раунде 2, §9). Комментарий в
`Message.h` это состояние описывает верно.

Присваивание (копирующее и перемещающее) в **подцепленный** `Message`: `operator=`
у `InFlightLink` — no-op, значит целевой узел сохраняет своё членство и цепочка
остаётся консистентной. Тоже верно.

`Message(Message&&) noexcept = default` продолжает компилироваться, значит
`noexcept` честен (при несовпадении с неявной спецификацией программа была бы
ill-formed) — проверка раунда 3 §18 остаётся в силе, `InFlightLink` объявлен
`noexcept` явно.

## 24. Перф — **перемерил**, оценка Producer'а по диффу неверна; результат принимаю

Producer записал: «по диффу горячий путь не удорожается (… фикс B4 — удержание
локального `Ptr`)». Это неверно: удержание — это **копия `shared_ptr`**, то есть
два атомарных RMW (инкремент при снятии пина, декремент при выходе из функции) на
каждое подтверждённое сообщение, ровно на горячем пути `CLIENT_/DUPS_OK_/INDIVIDUAL_ACK`.

Измерил изолированно: два release-бинаря из одного дерева, отличающиеся ровно
одной строкой пина, ABBA (BRANCH, NOPIN, NOPIN, BRANCH) ×3, медиана `cpu_time`:

| N | без пина | с пином (ветка) | Δ | на сообщение |
|---|---|---|---|---|
| 1 | 188.6 нс | 196.9 нс | **+4.37 %** | +8.2 нс |
| 100 | 17.64 мкс | 18.13 мкс | **+2.80 %** | +4.9 нс |
| 1000 | 191.9 мкс | 197.1 мкс | **+2.72 %** | +5.2 нс |

**Принимаю.** Основания:

1. Величина под порогом `~5 %` на всех трёх точках, и это не регрессия
   существующего поведения, а стоимость безопасности памяти на коде, которого в
   `main` нет вовсе (та же логика, что в §12 раунда 2).
2. ~5 нс/сообщение — ровно ожидаемая цена двух атомарных операций над счётчиком
   ссылок; альтернативы (сырой указатель + ручная проверка) вернули бы класс
   дефекта, ради которого раунд 4 и существует.
3. **Форма кривой осталась плоской**: 196.9 нс/сообщение при N=1, 181 нс при
   N=100, 197 нс при N=1000. Сложность не изменилась — B1 закрыт по-прежнему.
4. Путь доставки (`copy()`, куда попал рефакторинг `InFlightLink`) не изменился:
   `AutoAck_NonPersistent_RoundTrip` 153.7 нс и `Topic_AutoAck_NonPersistent_RoundTrip`
   166.7 нс против замеров раунда 1 (`main` 152.1 / 166.1, ветка 155.0 / 163.6) —
   в пределах шума.

**Для протокола:** оценка «по диффу» второй раунд подряд разошлась с измерением
(раунд 1: перф-гейт прошёл вхолостую и пропустил квадратику; раунд 4: «не
удорожает» при фактических +3 %). Оба раза величина оказалась терпимой, но
методика — нет. Рекомендация к `perf-check`: любое изменение, добавляющее или
убирающее операцию над `shared_ptr` на пути ack/delivery, меряется, а не
оценивается.

## 25. Фикс `~Consumer()` — **корректен и несущий**, но диагноз в комментарии неверен

### Дефект реален — воспроизвёл обратной мутацией

Вернул `_destination.get().uri()` в `~Consumer()`, полный сьют под ASan:

```
[ RUN      ] PersistentTransactionTest.testTransactionRecoveryAfterRestart
ERROR: AddressSanitizer: heap-use-after-free on address 0x6040000498d0
    #2 tiny_mq::Consumer::~Consumer() Consumer.cpp:62
freed by thread T0 here:
    #1 std::string::~basic_string()
    #2 tiny_mq::Destination::~Destination() Destination.cpp:422
```

То есть без этого фикса ASan-гейт красный на первом же прогоне. Включение правки
в эту ветку — не расширение скоупа, а предусловие гейта (см. §27).

### Полнота фикса — проверил

`grep '_destination\b'` по `Consumer.cpp` даёт всего четыре живых обращения:
конструктор (строки 24-25, 39 — `Destination` заведомо жив), `enqueueOrSchedule()`
(строка 234) и аксессор `destination()` (строка 375). **Ни одного в путях
разрушения**: `~Consumer()` → `flushPendingAcks()` / `rollback()` /
`clearInFlight()` / логирование — все теперь через `_destinationUri`;
`rollback()` получил такой же перевод и снабжён комментарием, объясняющим почему
(он вызывается и из деструктора). Полно.

### Расхождение кэша с реальным значением — невозможно

`Destination::_uri` инициализируется один раз в списке инициализации
(`Destination.cpp:29`, из `_type` и `_name`, оба тоже неизменяемые) и нигде не
переприсваивается; `uri()` возвращает `const std::string&`. Кэш разойтись не может.

### Замечание O4 (не блокер): комментарий описывает не тот механизм

Комментарий в `Consumer.h` объясняет дефект так: «`~Destination()` очищает
`_consumers` **до** разрушения собственных `_uri`/`_name`, поэтому Consumer читал
освобождённую строку». Это неверно, и ровно наоборот: `~Destination()`
**намеренно** начинает с `_consumers.clear()` (`Destination.cpp:411`) именно
затем, чтобы консьюмеры умирали при живом `_uri`.

Настоящий механизм виден в стеке выше: строка освобождена на **закрывающей скобке**
`~Destination()` (строка 422), то есть при разрушении членов, а Consumer умер
**позже**. Причина — совладение: `Consumer::Ptr` держат и
`Destination::_consumers`, и `Session::_consumers` (`Session.h:120`). Консьюмер,
переживший свой `Destination` (в этом тесте — `_exchange.reset()` при живой
сессии), имеет **висячий `_destination` на весь остаток своей жизни**, а не
только в деструкторе.

Практических последствий для спеки 23 нет — фикс закрывает все обращения в
путях разрушения, а `enqueueOrSchedule()`/`destination()` в этом состоянии не
вызываются. Но: (1) текст комментария стоит заменить на фактический механизм,
иначе он уведёт следующего читателя; (2) «Consumer переживает свой Destination» —
кандидат в отдельную задачу (по-хорошему `_destination` должен быть
`std::weak_ptr`), вне скоупа спеки 23.

### Преэкзистентный overread в `BytesMessageTest` — корректен

`setBytes` просят прочитать `sizeof(uint32_t) * len` байт, буфер теперь ровно
такого размера. Ожидание `dataSize()` не подгонялось — тест продолжает проверять
то же самое. Правка минимальная и правильная (альтернатива — уменьшить
запрашиваемый размер — изменила бы предмет теста).

## 26. ASan-задание в CI — как гейт полезно; две дыры, обе обязательны к закрытию

### Что хорошо

- Ловит **ровно тот** класс дефектов, ради которого заведено: §21 показывает, что
  два теста `RecoverTest` без ASan не диагностируют B4 вовсе. Гейт не
  дублирует `build-test`, а покрывает то, что тот принципиально не видит.
- Зелёный с первого дня — подтверждаю независимо: 135/135, exit=0 (§20). Решение
  человека не сдавать «известный красный» правильное; заведомо красный гейт
  деградирует в шум за неделю.
- Флаги адекватны: `-fsanitize=address -fno-omit-frame-pointer -g`,
  `ASAN_OPTIONS=detect_stack_use_after_return=1`.
- `-DCMAKE_CXX_FLAGS=` дыры в предупреждениях не создаёт: `CMakeLists.txt:39`
  **дописывает** `-Wall -Werror -Wextra -Wshadow` к переданному значению, а не
  затирает его.
- Одна платформа для гейта на класс дефекта — согласен, `ubuntu-latest` достаточно.

### Дыра 1 (обязательно к правке): комментарий у шага противоречит комментарию у задания

```yaml
      - name: Тесты под ASan
        run: |
          rm -rf tiny-mq bench-mq
          # См. комментарий на job'е: полный фильтр красный на преэкзистентном
          # дефекте вне скоупа спеки 23. Меняйте фильтр здесь только вместе с
          # обновлением того комментария.
          ASAN_OPTIONS=... ./cmake-build-asan/tiny_mq --gtest_filter='-*Bench*'
```

Это **уцелевший фрагмент старой редакции «ИЗВЕСТНЫЙ КРАСНЫЙ СТАТУС»**: человек
переписал комментарий у задания, но не у шага. Сейчас он утверждает, что полный
фильтр красный на преэкзистентном дефекте, — прямо противоречит заголовку
задания («гейт зелёный с первого дня») и факту (§20).

Хуже: он ссылается на «фильтр», которого фактически нет. Проверил —
`--gtest_list_tests` даёт 135 тестов, под `-*Bench*` прогоняется те же **135**;
ни одного теста с `Bench` в имени в сьюте нет (бенчи живут за `--gbench`).
Фильтр инертен, а комментарий объясняет его несуществующим дефектом.

Требуется: удалить или переписать комментарий; фильтр либо убрать как ненужный,
либо оставить с честным пояснением «страховка на случай появления gtest-обёрток
над бенчами». Правка чисто редакторская.

### Дыра 2 (обязательно к решению): LeakSanitizer на Linux не проверялся ничем

На `ubuntu-latest` ASan включает LeakSanitizer **по умолчанию** (`detect_leaks=1`),
и он завалит задание при любой утечке — включая утечки Poco-синглтонов и всё, что
никогда не было предметом этого проекта. Вся верификация «гейт зелёный» выполнена
на arm64 macOS, где LSan недоступен в принципе:

```
$ ASAN_OPTIONS=detect_leaks=1 ./cmake-build-asan/tiny_mq --gtest_filter=...
==58946==AddressSanitizer: detect_leaks is not supported on this platform.
```

То есть утверждение «зелёный с первого дня» проверено для тех проверок, которые
на macOS выполняются, и **не проверено для той, которая появится только в CI**.
Риск ровно тот, ради предотвращения которого человек и возвращал задание.

Требуется одно из двух: либо явно `detect_leaks=0` в `ASAN_OPTIONS` с
комментарием «гейт про lifetime-ошибки; утечки — отдельная задача» (дёшево,
честно, гейт остаётся зелёным), либо сознательно оставить включённым, приняв, что
первый прогон может быть красным, и заранее завести задачу на разбор. Молча
полагаться на «наверное, не течёт» — нельзя.

### Замечания без требования правки

- UBSan не включён, хотя локальная `cmake-build-asan` собрана с
  `-fsanitize=address,undefined`. Расширить до `address,undefined` стоило бы —
  цена нулевая, покрытие шире. Не блокер.
- Задание не в `needs:` ни у кого и не блокирует `package`/`release` — как гейт
  на PR этого достаточно (branch protection настраивается вне workflow).
