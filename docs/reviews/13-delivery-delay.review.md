## Блокеры

### B1. Два разных определения «транзакционности» — задержка молча теряется

`Producer::applyOptions` решает, отложить ли резолв `deliveryTime` до commit,
по **режиму сессии**:

```cpp
// Producer.cpp:79, :93
bool transactional = _session.get().acknowledgeMode() == Session::AcknowledgeMode::SESSION_TRANSACTED;
applyOptions(const_cast<Message &>(message), opts, transactional);
```

А `Consumer::push` решает, куда отдать сообщение, по **id текущей транзакции**:

```cpp
// Consumer.cpp:191
if (producer.transactionId().empty()) { ... }
```

Эти предикаты расходятся. `Producer::transactionId()` возвращает `Session::_suffix`
(`Producer.cpp:117`), а `Session::commit()` / `Session::rollback()` **очищают
`_suffix` на время своего выполнения** — намеренно (`Session.cpp:219-220`,
комментарий: «`_suffix` is cleared first so that any deliveries triggered inside
commit() are treated as non-transactional»). Режим же сессии остаётся
`SESSION_TRANSACTED` всегда.

Итого при `send()` в окне, когда `_suffix` пуст, на SESSION_TRANSACTED-сессии:

1. `applyOptions(transactional=true)` → `jmsHeaders.deliveryTime = 0`, задержка
   уходит в транзиентный `_pendingDeliveryDelay`;
2. `Consumer::push` видит `transactionId().empty() == true` → нетранзакционная ветка;
3. там проверяется `msg->jmsHeaders.deliveryTime != 0` — а он **0** →
   `_queue->enqueue(...)` **немедленно**;
4. `_pendingDeliveryDelay` не резолвит уже никто.

Результат: **отложенное сообщение доставляется потребителю сразу, задержка
исчезает бесследно** — ровно то окно, которого спека не допускает («Message becomes
visible to consumers only once `now_ms >= deliveryTime`»). Диагностики нет: ни
исключения, ни лога.

Сегодня путь латентный — внутри `Session::commit()` пользовательский код не
исполняется (MessageListener в кодовой базе ещё нет), поэтому тесты и не падают.
Но это не «пока не баг», а несогласованность контракта: один и тот же message
классифицируется двумя разными способами, и режим отказа — тихая потеря семантики.
Появление async-листенеров (или любого вложенного `send`) делает его живым.

**Фикс:** один предикат на оба решения. Проще всего — определять
транзакционность в `Producer::send` как `!transactionId().empty()` (тот же
источник истины, что и у `push`), либо протаскивать уже вычисленный флаг до
`push`. Плюс: если `_pendingDeliveryDelay != 0` попало в нетранзакционную ветку —
это инвариантное нарушение, его надо резолвить или логировать, а не игнорировать.

### B2. Персистентное транзакционное отложенное сообщение приезжает с `JMSDeliveryTime == 0`

`Producer::commit` резолвит задержку в двух местах — в памяти и в буфере
транзакции:

```cpp
// Producer.cpp:133-140
message->jmsHeaders.deliveryTime = nowMs + message->_pendingDeliveryDelay;
message->_pendingDeliveryDelay = 0;
if (message->isPersistent()) {
  _destination.get().patchPendingDeliveryTime(message->uuid, message->jmsHeaders.deliveryTime);
}
```

Но **не** в третьем — в `Message::_cachedStorageBytes`. Эти байты сериализованы
в `Consumer::preparePush` (`Consumer.cpp:163-170`) в момент send, когда для
транзакционной отправки `deliveryTime` был принудительно выставлен в 0
(`Producer.cpp:52`). Дальше:

```cpp
// Consumer.cpp:78-85 — recv()
if (message->isPersistent()) {
  if (!message->_cachedStorageBytes.empty()) {
    ...
    message->fromBytes(bytesData);   // <-- перезатирает jmsHeaders.deliveryTime нулём
```

`fromBytes` для magic `0x02` читает `deliveryTime` (`Message.cpp:158`) и
затирает корректное значение нулём. Планирование при этом отрабатывает верно
(scheduler смотрит на header **до** recv), то есть тайминг правильный, — а вот
приложение получает сообщение с `JMSDeliveryTime == 0` вместо фактического
времени доставки. JMS 2.0 требует, чтобы на принятом сообщении `JMSDeliveryTime`
отражал реальное время доставки.

Это дефект именно спеки 13: `priority`/`expiration` резолвятся до сериализации и
не страдают, патчится после сериализации только `deliveryTime`.

**Почему это не поймали:** комбинация *персистентное + транзакционное +
отложенное* не покрыта ни одним тестом. Тест #2 (рестарт) — персистентный, но
нетранзакционный; тест #3 (транзакция) — `Message::NOT_PERSISTENT` в обоих
сценариях (`tests/DeliveryDelayTest.cpp:114`, `:124`). А это пересечение пунктов
2 и 3 Test plan и единственное место, где встречаются оба новых механизма
(`TransactionBuffer::patchDeliveryTime` + реплей). Побочно это значит, что
`patchDeliveryTimeInBytes` со своим `memcpy` по смещению 43 **не исполняется ни
разу за весь прогон** — ошибка в смещении прошла бы незамеченной.

**Фикс:** патчить `_cachedStorageBytes` тем же значением в `Producer::commit`
(или инвалидировать кэш, чтобы recv пошёл в storage), и добавить тест
persistent+transactional+delayed, желательно с рестартом.

### B3. Новый поток на destination против ADR-0005 — нет ни ADR, ни зафиксированного обоснования

Спека сама помечает это открытым вопросом: «Single global timer vs
per-destination timer? Start with per-destination for isolation». Producer выбрал
per-destination, но обоснование не записал (в handoff прямо стоит
`"НЕ ПРОВЕРЕНО"` по этому пункту).

Фактическое решение (`DeliveryScheduler.h:33`, `Destination.h:46`):
один `DeliveryScheduler` на `Destination`, **worker стартует лениво** — только
при первой реально отложенной доставке (`DeliveryScheduler.cpp:38-41`).

Оценка масштабируемости:

- 100 назначений без delayed-трафика → **0 потоков**. Ленивый старт — правильное
  и существенное смягчение, горячий путь не платит ничего сверх одной проверки
  `deliveryTime != 0` (`Consumer.cpp:192`).
- 100 назначений, каждое хоть раз использовало delay → **100 потоков**, каждый
  спит на `wait_until`. Работоспособно, но это линейный рост по назначениям,
  и потоки уже не освобождаются: раз запущенный worker живёт до разрушения
  destination, даже если отложенных сообщений больше не будет.
- ADR-0005 явно отклоняет «поток на сессию на сервере» с формулировкой
  «не масштабируется, дублирует модель реактора». Ровно тот же аргумент
  применим к «потоку на destination», а целевая модель (ADR-0002/0005, реактор
  с пулом потоков) естественно ложится на **одно** таймер-колесо, а не на N
  спящих потоков.

Я не отклоняю сам выбор — спека санкционирует per-destination как стартовую
точку, и ленивый старт делает его приемлемым для M2. Блокер в другом: изменение
потоковой модели, прямо задевающее отклонённую в ADR-0005 альтернативу, ушло в
код без единой записи о решении. По чек-листу ревьюера это триггер «решение
меняет инвариант → требуй ADR».

**Фикс:** ADR (скилл `adr-write`), фиксирующий: выбран per-destination
с ленивым стартом; цена — до N потоков при N назначениях с delayed-трафиком;
условие пересмотра — переход на глобальное таймер-колесо при интеграции
с реактором (M3+) или при появлении сценариев с сотнями delayed-назначений.
Достаточно короткого ADR, но он должен быть.

## Замечания (не блокирующие)

### N1. Очень большая задержка → знаковое переполнение и немедленная доставка

Валидируется только нижняя граница:

```cpp
// Producer.cpp:90
if (opts.timeToLive < 0 || opts.deliveryDelay < 0) throw std::invalid_argument(...);
```

Верхней границы нет. При `deliveryDelay`, близком к `INT64_MAX`,
`nowMs + opts.deliveryDelay` (`Producer.cpp:59`) — знаковое переполнение (UB);
на практике результат уходит в отрицательные, `deliveryTime <= nowMs()`
(`DeliveryScheduler.cpp:32`) истинно, и сообщение **доставляется немедленно** —
поведение, обратное запрошенному. Симметрично в worker:
`std::chrono::milliseconds(deadlineMs - nowMs())` (`DeliveryScheduler.cpp:58`)
при конвертации в разрешение `system_clock` переполняется на очень больших
значениях. Прошу добавить верхнюю границу в валидацию (или насыщение
до разумного максимума).

Остальные краевые значения проверены и корректны: `deliveryTime == 0` →
немедленно; `deliveryTime` в прошлом → немедленно (`<= nowMs()`, что совпадает
с требованием спеки `now_ms >= deliveryTime`); отрицательный `deliveryTime`
из хранилища → немедленно, не теряется.

### N2. `wait_until` по `system_clock` вместо `steady_clock`

`DeliveryScheduler.cpp:58` ждёт на `std::chrono::system_clock`. Дедлайн
вычисляется относительно (`now() + delta`), так что систематической ошибки нет,
но скачок стенных часов назад (NTP-степ) во время ожидания отложит срабатывание
на величину скачка. Для монотонного ожидания корректнее `steady_clock`.
`deliveryTime` при этом остаётся абсолютным wall-clock значением — это правильно,
он персистится и должен переживать рестарт.

### N3. Латентный `std::terminate` после `stop()` (класс ADR-0006)

`enqueueOrSchedule` не смотрит на `_stopped`:

```cpp
// DeliveryScheduler.cpp:37-41
std::unique_lock<std::mutex> lock(_mutex);
if (!_threadStarted) { _thread = std::thread(&DeliveryScheduler::run, this); _threadStarted = true; }
```

Сценарий: `stop()` вызван до того, как хоть раз что-то планировалось
(`_threadStarted == false`, `_stopped == true`). Последующий `enqueueOrSchedule`
с будущим `deliveryTime` **запускает новый поток**; тот видит `_stop == true`
и сразу выходит. Деструктор вызывает `stop()`, который выходит на
`if (_stopped) return;` (`:81`) и **не джойнит**. Дальше `~std::thread` на
joinable-потоке → `std::terminate`. Это ровно режим отказа ADR-0006 —
не перехватываемое исключение, а падение процесса, и try/catch в деструкторе
от него не спасает.

Сегодня недостижимо: единственный вызов `stop()` — в `~Destination`
(`Destination.cpp:389-397`), после чего в scheduler уже никто не ходит. Но
`stop()` публичен и в заголовке описан как штатная точка teardown, которую
владелец обязан вызывать до разрушения — то есть приглашение наступить на это.
Фикс однострочный: `if (_stopped) return;` (или сброс в очередь немедленно)
в начале `enqueueOrSchedule`.

### N4. Гонка при остановке — проверено, чисто

Разбирал отдельно, дефектов нет, и это стоит отметить как сделанное правильно:

- `Entry` держит `std::shared_ptr<QueueT>` (`DeliveryScheduler.h:51`), поэтому
  очередь переживает `_consumers.clear()` в `~Destination`, даже если worker
  в этот момент находится в `entry.queue->enqueue(...)` с отпущенным мьютексом
  (`DeliveryScheduler.cpp:71-73`). Use-after-free нет.
- Сообщение «в полёте» при разрушении дописывается в живую очередь.
- Потерянных пробуждений нет: `_version` перечитывается на каждой итерации,
  `wait_until` с предикатом возвращает `false` только по таймауту, вставка
  более раннего дедлайна корректно вынуждает пересчёт вершины.

Что действительно теряется: **все ещё не наступившие записи в `_pending`
отбрасываются при `stop()` молча**, без счётчика в логе. Для персистентных это
безопасно (они остаются в storage и переставляются реплеем), для
non-persistent — легальная по JMS потеря. Просьба хотя бы логировать
количество отброшенных при остановке — иначе диагностировать «сообщение
пропало при рестарте» будет нечем.

### N5. Хрупкость тестов по времени

Прогон `--gtest_repeat=10` локально: 10/10, разброс 1493–1509 мс — очень стабильно.
Но подменить таймер нечем: `nowMs()` в `DeliveryScheduler.cpp:13` и
`Poco::Timestamp()` в `applyOptions` читают часы напрямую, шва для инъекции нет,
так что тесты неустранимо завязаны на реальное время.

Запасы:

- тест #2 (рестарт) — уже защищён guard'ом `if (elapsedMs < kDelayMs)`
  (`:89-93`) и финальным `recv(2000000)`. Устойчив;
- тест #1 — упадёт, если между `send()` и входом в `recv` раннер встанет
  на >150 мс. Маловероятно, но возможно на перегруженном CI;
- тест #3 (commit-часть) — самое узкое место: между `session.commit()` и входом
  в `recv` должно пройти <150 мс, иначе `EXPECT_EQ(recv(50000), nullptr)`
  на строке 127 упадёт. Запас 150 мс на пути, где ещё и storage не участвует
  (NOT_PERSISTENT), — рабочий, но не щедрый.

Рекомендация: вынести чтение часов в scheduler за шов (например,
`std::function<int64_t()> _now` с дефолтом на `Poco::Timestamp`), тогда
инвариант «невидимо до срока» проверяется детерминированно, а wall-clock
остаётся только в одном smoke-тесте. До тех пор — поднять `kDelayMs`
в тестах #1 и #3 до ~400 мс: стоимость прогона вырастет незначительно,
а запас утроится.

### N6. Неверный комментарий смещения в `TransactionBuffer.cpp`

`kDeliveryTimeOffset` (`TransactionBuffer.cpp:19-25`) собран из тех же слагаемых
`1+1+8+16+1+8+8`, что и в `Destination.cpp:117`, и равен **43** — значение
верное и совпадает с раскладкой `Message::toBytes` (`Message.cpp:112-121`).
Но хвостовой комментарий говорит `// expiration (total = 35)`. `35` — это
смещение `expiration`, а не `deliveryTime`. Заголовок
(`TransactionBuffer.h:32`) при этом честно пишет «offset 43». Комментарий
надо поправить, иначе он собьёт следующего, кто полезет патчить формат.

### N7. `_pendingDeliveryDelay` не сбрасывается на исходном сообщении

`applyOptions` мутирует объект вызывающего (через `const_cast`, поведение
досталось по наследству). Транзиентный `_pendingDeliveryDelay` копируется
копирующим конструктором (`TextMessage::copy()`), что и требуется для работы
механизма. Но на **исходном** объекте пользователя он остаётся ненулевым после
транзакционного send. Повторная отправка того же `Message` через
`send(message)` **без** `_default` не вызывает `applyOptions` вовсе — и на
commit'е сообщение получит задержку от прошлой отправки. Путь узкий, но
дешевле обнулять поле на исходнике сразу после копирования.

# Раунд 2 — ревью дельты

- **Стадия:** reviewer, iteration 2
- **Producer:** claude-sonnet-5 (handoff `handoffs/spec-13/producer.json`, iteration 2)
- **Reviewer:** claude-opus-5
- **Вердикт: `rejected`** (default-deny, §5.3) — один новый блокер **B4**, обнаруженный
  в правке раунда 2 (пункт N1). Пункты B1, B2, B3, N3, N4-логирование, N6 — **закрыты**.

## Блокер раунда 2

### B4. Граница поставлена не на том слое: абсурдный `deliveryTime` → 100% CPU и вечное зависание `stop()`

`validateSendOptions` (Producer.cpp) валидирует `SendOptions::deliveryDelay`. Но в
арифметику планировщика попадает **не** `deliveryDelay`, а `jmsHeaders.deliveryTime` —
и до него валидация не доходит ни по одному из трёх путей:

1. `Message::jmsHeaders` — **публичное поле**. `producer->send(message)` без
   `setDefault()` вообще не вызывает `applyOptions`/`validateSendOptions`
   (`Producer.cpp:92-107`) — заголовок уезжает в `Consumer::push` как есть;
2. реплей из хранилища: `deliveryTimeFromStorageBytes` (`Destination.cpp:116`) читает
   8 байт по смещению 43 и отдаёт их в `enqueueOrSchedule` **без единой проверки** —
   ровно сценарий из задания «что если в хранилище лежит запись с абсурдным
   `deliveryTime`»; проверяется только `data[1] == 0x02` и размер, так что любые
   мусорные 8 байт в записи 0x02 принимаются;
3. будущий сетевой ingress (M3+) — заголовок придёт с провода.

Режим отказа хуже, чем описанный в раунде 1 «немедленная доставка». В
`DeliveryScheduler::run` (`:73`):

```cpp
const auto deadline = std::chrono::system_clock::now() + std::chrono::milliseconds(deadlineMs - nowMs());
```

При `deadlineMs`, далёком настолько, что конверсия мс→тик `system_clock` переполняет
`int64_t`, `deadline` оказывается **в прошлом**. Тогда `wait_until` возвращается
мгновенно с `woken == false`, внутренний цикл доставки не находит ничего due
(`INT64_MAX <= now` — ложь), `while (!_stop)` крутится заново — **и всё это с
удержанным `_mutex`**, который отпускается лишь на мгновение внутри `wait_until`.
Итог: воркер жжёт ядро на 100%, а `stop()` навсегда виснет на `std::lock_guard`.

Воспроизведено, не выведено:

- изолированный chrono-репро (libc++, `system_clock` = мкс): `now() + milliseconds(INT64_MAX)`
  даёт дедлайн **раньше** `now()` (`delta_us = -1000`);
- прямой репро на продуктовом коде (слинкован с объектниками `cmake-build-debug`,
  дерево не менялось): `DeliveryScheduler` + сообщение с `deliveryTime = INT64_MAX` →
  0.000 с CPU в контроле (`now+60s`) против непрерывных 100% CPU в дефектном случае;
  `sample(1)` зафиксировал стек: main — `DeliveryScheduler::stop()` →
  `std::mutex::lock()` → `__psynch_mutexwait` (заблокирован намертво), worker —
  `DeliveryScheduler::run()` DeliveryScheduler.cpp:81 → `nowMs()` → `gettimeofday`
  (крутится);
- **end-to-end только через публичный API**: `Exchange` → `Session` → `producer->send(m)`,
  где `m.jmsHeaders.deliveryTime = INT64_MAX` и **никаких** `SendOptions`. Печатается
  «sent; now tearing down», после чего процесс висит на 99% CPU (убит по таймауту 20 с).
  Разрушение `Destination` не завершается никогда.

Порог срабатывания зависит от разрешения `system_clock`: на libc++ (мкс, macOS) это
≈292 тыс. лет вперёд, на libstdc++ (нс, Linux CI) — ≈236 лет. Значения абсурдные, но
именно поэтому и нужна была граница: источники таких значений — порча файла хранилища,
чужая/старая запись, баг вызывающего, враждебный ввод. Цена — неустранимый внутри
процесса отказ: брокер не выключается.

Отдельно: утверждение в handoff «граница выбрана с большим запасом ниже точки
переполнения… и nowMs+delay, и chrono-конверсия гарантированно не переполняются»
**неверно** — гарантия распространяется только на путь через `SendOptions`, а
переполняется другой вход. Сама константа 10 лет при этом безопасна (проверено:
`now + 10y` в мкс и в нс укладывается в `int64_t`), а обоснование «~292 млн лет»
ошибочно на шесть порядков: диапазон `int64` в наносекундах — ~292 **года** от эпохи
(предел ≈2262 г.), и именно он, а не 292 млн лет, ограничивает допустимый максимум.

**Что нужно:** защита в точке использования, а не только на ingress. Минимально —
в `DeliveryScheduler::run` ограничить ожидание сверху (например,
`std::min(deadlineMs - nowMs(), kMaxWaitMs)` с повторным проходом цикла): это
одновременно снимает переполнение, снимает спин и делает цикл устойчивым к любым
будущим странностям часов. Дополнительно — валидировать/клампить `deliveryTime`
там, где он входит в систему помимо `SendOptions`: `deliveryTimeFromStorageBytes`
(мусор → 0, то есть немедленная доставка, + `poco_warning`) и вход `enqueueOrSchedule`.
Нужен тест: сообщение с `deliveryTime = INT64_MAX` → destination разрушается за
конечное время, CPU не жжётся.

## Что подтверждено закрытым

### 1. Обход ADR-0006 — окно закрыто полностью

Проверил все пути старта потока: `_thread` присваивается **ровно в одном месте**
(`DeliveryScheduler.cpp:54`), под `_mutex`, за проверкой `_stopped` (`:38`). `stop()`
выставляет `_stopped` под тем же мьютексом до того, как трогает `_thread`, поэтому
`_thread.joinable()`/`join()` вне лока гонки не образуют: любой `enqueueOrSchedule`,
который успел взять мьютекс раньше, завершит присваивание до того, как `stop()`
войдёт в критическую секцию, а любой, кто взял его позже, уходит в ветку `_stopped`.
Чтение `_pending.size()` в конце `stop()` без лока тоже корректно: воркер уже
приджойнен, а новые вставки после `_stopped` невозможны. Второй `stop()` из
деструктора идемпотентен. Тест
`testSchedulerDeliversImmediatelyInsteadOfStartingThreadAfterStop` детерминирован (без
часов), и Producer доказал его невырожденность откатом (assertion + `libc++abi:
terminating`) — принимаю.

Семантика «после остановки доставляем немедленно» — см. N9: приемлемо, но
непоследовательно.

### 2. B2 — оба кэша согласованы, смещение 43 верифицировано по раскладке

Смещение проверено **фактически по `Message::toBytes`** (`Message.cpp:110-121`), а не
по комментарию. Кэш = `[1 байт type][payload]`; payload: magic(1) → `_number`(8) →
uuid(16) → reliability(1) → `timestamp`(8) → `expiration`(8) → `deliveryTime`(8).
Абсолютные индексы в кэше: magic = 1, deliveryTime = 1+1+8+16+1+8+8 = **43**. Совпадает
и с `TransactionBuffer::kDeliveryTimeOffset`, и с `Message::patchCachedDeliveryTime`,
и с `deliveryTimeFromStorageBytes`, и с читателем `fromBytes` (`Message.cpp:172-176`).
Проверка `bytes[1] == 0x02` в обоих патчерах корректна для этой раскладки.

Оба кэша действительно патчатся: `Producer::commit` (`Producer.cpp:146-170`) резолвит
`nowMs + _pendingDeliveryDelay`, затем `patchPendingDeliveryTime` (буфер транзакции,
уходит в storage) **и** `patchCachedDeliveryTime` (собственный кэш сообщения, который
читает быстрый путь `Consumer::recv`, `Consumer.cpp:79-85`). Для топика каждая копия
потребителя лежит в том же `_transactQueue` и патчится отдельно, а запись в
`_bufferedData` одна на uuid — расхождений нет.

`patchDeliveryTimeInBytes` со смещением 43 теперь **исполняется**: тест
`...PreservesDeliveryTimeAcrossRestart` — единственный путь, где выживший экземпляр
`deliveryTime` только один, тот, что записал патч буфера транзакции; после рестарта
он читается обратно и по 43 (`deliveryTimeFromStorageBytes` → расписание) и через
`fromBytes` (→ `EXPECT_NEAR` к `commitTime + kDelayMs`). Если бы смещение расходилось
с читателем, тест дал бы `deliveryTime == 0` и немедленную доставку. Невырожденность
теста «OnReceipt» Producer доказал откатом (`0 vs 0`) — принимаю.

Порядок в `Producer::commit` тоже верен: дренаж и патч идут **до**
`commitTransaction`, то есть до сброса буфера в storage; доставка (`deliverCommitted`)
по-прежнему после персистенса.

### 3. B1 — предикат единый там, где это нужно спеке

`Session::_suffix` непуст ровно для `SESSION_TRANSACTED` (`Session.cpp:21-23`) и
временно очищается на время `commit()`/`rollback()` (`:219-220`, `:232-233`). Значит
переход `acknowledgeMode() == SESSION_TRANSACTED` → `!transactionId().empty()`
семантически эквивалентен везде, **кроме** ровно того окна, ради которого он и
делался: теперь `applyOptions` и `Consumer::push` классифицируют одно и то же
сообщение одинаково, и «тихая потеря задержки» структурно невозможна. Случаев, где
`acknowledgeMode()` был правильным критерием для *send*, не нашёл.

Оставшиеся `acknowledgeMode()` законны:
- `Producer.cpp:25` и `Consumer.cpp:42` — аллокация `_transactQueue` в конструкторе.
  Это решение о **времени жизни ресурса** сессии, а не о классификации сообщения; в
  момент конструирования оба предиката совпадают, но режим здесь честнее;
- `Consumer.cpp:132` (recv) и `Consumer::commit/rollback` — учёт **принятых**
  сообщений для транзакционного ack. Это другая ось (потребительская сторона), и
  привязка к режиму сессии там корректна. Отмечаю явно: предикат унифицирован на
  стороне отправки — этого спеке 13 достаточно.

Отсутствие отдельного теста принимаю: сценарий требует `send()` изнутри
`commit()`/`rollback()`, чего в кодовой базе нет; тест на совпадение предикатов был бы
тестом реализации. Инвариант зафиксирован комментариями на обеих перегрузках.

### 5. Счётчик отброшенных

`poco_warning` в `stop()` печатает `_pending.size()`. Формат `%z` корректен —
в Poco это конверсия для `std::size_t` (`Format.cpp:229-231`, `AnyCast<std::size_t>`),
тип аргумента совпадает точно, `BadCastException` не будет. Диагностики достаточно:
это ровно то, чего просил N4. См. N9 про непоследовательность политики.

### 6. ADR-0007

Решение зафиксировано корректно и **честно**: выбран per-destination с ленивым
стартом; цена (до N спящих потоков при N назначениях с delayed-трафиком, воркер не
освобождается между всплесками) названа прямо, а не сглажена; альтернативы
(глобальное таймер-колесо на `Exchange`, поток на сессию, `Poco::Timer`) описаны с
реальными причинами отклонения, а не для галочки; условие пересмотра конкретно
(реактор M3+ / сотни назначений с активным delayed-трафиком) и проверяемо. Раздел
«Почему ADR-0005 не нарушается» аргументирует по существу (поток привязан к
использованию фичи, а не к клиентскому соединению) — противоречия с ADR-0005 не вижу,
формулировка «отклоняет поток-на-сессию как постоянную модель сервера» точна.
Строка в `arch/README.md` добавлена, комментарий класса ссылается на ADR.

## Замечания раунда 2 (не блокирующие)

### N9. Непоследовательная политика на остановке

В `stop()` ещё не наступившие записи **отбрасываются** (и логируются) — для
персистентных это правильно: запись остаётся в storage и реплей переставит таймер.
А `enqueueOrSchedule` после `stop()` делает противоположное — **доставляет
немедленно**. Для персистентного сообщения это хуже отбрасывания: потребитель
получит его раньше срока, заакает, запись уйдёт из storage — задержка потеряна
безвозвратно, тогда как отбрасывание сохранило бы корректную семантику через реплей.
Сегодня путь недостижим (`stop()` зовётся только из `~Destination`, после
`_consumers.clear()`/`_producers.clear()`), но тест закрепляет это как контракт.
Предложение: привести к одной политике (drop + счётчик) либо записать в комментарии,
почему поздние приходы трактуются иначе.

### N10. Фактические ниты в ADR-0007

«вводит `JMSXDeliveryDelay`» — такого свойства в JMS нет: API называется
`MessageProducer.setDeliveryDelay`, заголовок — `JMSDeliveryTime`. Также опечатка
«недоложенные» → «неотложенные».

### N11. Перф: транзакционный путь тронут, бенч не гонялся

`Producer::commit` в этом раунде **структурно переписан**: очередь `_transactQueue`
теперь дренируется в `std::vector<Message::Ptr> staged` до `commitTransaction`, а
доставка идёт вторым проходом. CLAUDE.md относит «acknowledge/transaction paths» к
горячим путям явно, и бенчи на него **есть**: `Transacted_NonPersistent_RoundTrip`,
`Transacted_Persistent_RoundTrip`, `Transacted_Batch_{NonPersistent,Persistent}`
с N=10/100/1000 (`tests/BenchmarkTest.cpp`). В handoff записано «горячий путь не
тронут» и перф не прогонялся — это утверждение фактически неверно; в раунде 1 цифры
по `Transacted_*` тоже не приводились. Сама правка выглядит дешёвой (один move
`shared_ptr` в вектор + две ветки на сообщение против батча в storage), регрессии >5%
не жду, но перф-гейт по этому пункту не пройден, а не пройден-и-обоснован. Прошу в
следующем раунде прогнать `--gbench --benchmark_filter=Transacted` до/после и
приложить цифры.

### N12. Хрупкость тестов по времени (пункт 7 задания)

Локально сегодня — 10/10 итераций зелёные, 2.16 с на итерацию, разброс незаметный.
Риск на нагруженном раннере не снят и не изменился по классу; шва для подмены часов
по-прежнему нет.

- `testSchedulerDeliversImmediatelyInsteadOfStartingThreadAfterStop` — от часов не
  зависит (дедлайн +60 с, проверяется факт немедленной доставки). Флакать не может;
- `...PreservesDeliveryTimeAcrossRestart` — `kDelayMs = 500` + guard
  `if (elapsedMs < kDelayMs)` + финальный `recv(2000000)` + `EXPECT_NEAR` с допуском
  5000 мс. Устойчив;
- `...PreservesDeliveryTimeOnReceipt` — **самый узкий из новых**: `kDelayMs = 150`,
  из которых 50 мс съедает первый `recv`, а между стартом часов (внутри
  `Producer::commit`) и входом в `recv` укладывается ещё и персистентный коммит
  (сброс буфера транзакции в storage). Запас ~100 мс — уже, чем у теста #3 из
  раунда 1, при большем объёме работы в окне. Измеренное время теста 161 мс;
- тесты #1 и #3 не менялись, оценка раунда 1 в силе.

Рекомендация прежняя и теперь относится к трём тестам (#1, #3, новый #5): поднять
`kDelayMs` со 150 до ~400 мс. Стоимость — доли секунды на прогон, запас утраивается.
Долгосрочно — шов для часов в `DeliveryScheduler` (`std::function<int64_t()> _now`),
тогда «невидимо до срока» проверяется детерминированно.

### N13 (перенос из раунда 1, подтверждено фиксированным)

### N14. Побочно: `timeToLive` тоже получил верхнюю границу

## B4 — разбор обоих слоёв

### Слой 2 (`DeliveryScheduler::run` + `cappedWaitDeltaMs`) — тот, который держит всегда

Это единственный слой, который защищает при **любом** обходе остальных, поэтому
проверял его первым и отдельно.

`run()` больше не формирует `deadlineMs - nowMs()` напрямую: длительность одного
сна ограничена `kMaxWaitMs` (сутки). Разбор цикла: капнутый сон гарантирует, что
воркер действительно спит на `wait_until` с **отпущенным** `_mutex`, просыпается
по таймауту, не находит ничего due, пересчитывает вершину и снова уходит в сон на
сутки. Ни переполнения конверсии мс→тик `system_clock`, ни спина, ни удержания
мьютекса — то есть оба компонента отказа из раунда 2 (100% CPU и `stop()`,
навсегда заблокированный на `std::lock_guard`) устранены в корне. Легальная
задержка длиннее суток при этом не ломается: она просто просыпается несколько
раз (30 дней → 30 пробуждений), семантика прежняя.

Новая `cappedWaitDeltaMs` — сравнение **до** вычитания, что и требовалось: замечание
человека про свёртку `delta < 0` при `-O2` верное, и подход «сначала сравнить»
единственный корректный.

**Проверено на живом компиляторе, а не выведено** (`scratchpad/capped.cpp`, точная
копия тела функции, `clang++ -std=c++20 -O2`, `noinline`, сверка со 128-битным
эталоном):

- исчерпывающий перебор краёв — `nowMsValue ∈ {0, 1, 1000, реальные часы,
  INT64_MAX - kMaxWaitMs, отрицательные часы, INT64_MIN+1, INT64_MIN}` ×
  `deadlineMs ∈ {INT64_MIN, INT64_MIN+1, −1, 0, 1, now, now+kMaxWaitMs∓1,
  now+kMaxWaitMs, INT64_MAX−1, INT64_MAX}`;
- 5 000 000 случайных пар (`now` в правдоподобном диапазоне часов, `deadline`
  произвольный, включая отрицательные);
- **0 расхождений с эталоном**, включая явно запрошенный заданием случай
  отрицательного `nowMsValue`: при `now < 0` выражение `nowMsValue + kMaxWaitMs`
  не переполняется, и оба охранника отрабатывают верно.

Тест `testSchedulerWaitDeltaCappedAgainstOverflow` расширен осмысленно и
невырожденно: точные значения, а не «≥0/≤cap» — граница ровно `kMaxWaitMs`
(должна вернуть cap), на единицу внутри (должна вернуть точную дельту, а не cap
— это ловит off-by-one в `>=`), `INT64_MAX`, `INT64_MAX−1`, `INT64_MIN`,
`INT64_MIN+1`, и отдельно `hugeNow = INT64_MAX − kMaxWaitMs − 1` (самое большое
`now`, при котором охранник ещё не переполняется). Старая реализация провалила бы
как минимум случаи `INT64_MIN`/`INT64_MIN+1`.

### Слой 1 (`enqueueOrSchedule` + `deliveryTimeFromStorageBytes`)

Прошёл по всем входам `deliveryTime` в арифметику планировщика — несанированных
не осталось:

| Вход | Санитайзер |
|---|---|
| `SendOptions.deliveryDelay` | `validateSendOptions` → `kMaxFutureHeaderMs`, бросает |
| публичное поле `jmsHeaders.deliveryTime` (`send(message)` без `setDefault`) | кламп в `enqueueOrSchedule` |
| реплей из storage (`replayFromStorage`) | кламп в `deliveryTimeFromStorageBytes` (`< 0` или `> now + 10 лет` → 0 + `poco_warning`) |
| `deliverCommitted` (постком) | тот же `enqueueOrSchedule` |
| `Producer::commit`: `nowMs + _pendingDeliveryDelay` | `_pendingDeliveryDelay` приходит только из провалидированных `SendOptions` (≤ 10 лет), переполниться не может |
| будущий сетевой ingress (M3+) | попадёт в `enqueueOrSchedule` → клампится |

Порядок в `enqueueOrSchedule` корректен: кламп стоит **до** проверки `_stopped` и
до постановки в `_pending`, поэтому абсурдное значение физически не доходит до
`_pending`. Горячий путь не подорожал: для `deliveryTime == 0` ветка клампа не
берётся (`if (deliveryTime > 0)`), а `deliveryTime == 0 ||` короткозамыкает вызов
`nowMs()` на строке 60 — ноль чтений часов на неотложенном сообщении, что
согласуется с измеренными цифрами перфа.

Единая константа `kMaxFutureHeaderMs` в `Message.h` вместо двух — правильное
решение и честно обосновано в комментарии: это буквально одна и та же
арифметическая опасность.

### Семантика зажима (пункт 2 задания)

Абсурдный `deliveryTime` → немедленная доставка + правка заголовка + `poco_warning`.
Оцениваю как верный выбор:

- **Формат `0x02` не тронут** — ни один клампер не пишет в storage. Байты записи
  остаются как были; клампится только то, что уходит в планировщик и в
  in-memory заголовок. Ожидания спеки 10 (раскладка заголовков) не задеты.
- **Немедленная доставка против drop** — доставка правильнее: сообщение
  существует и легально (ошибочен только один заголовок), а drop потерял бы
  полезную нагрузку. «Признак повреждения записи» не теряется бесследно: он
  уходит в `poco_warning` с исходным значением и с `now` — то есть
  диагностируемое «почему» есть, и это ровно то, чего я просил.
- Единственное, что действительно теряется, — машиночитаемый признак на самом
  сообщении (свойства вида `JMSXCorrupt` в JMS нет, изобретать его в спеке 13 не
  надо). Для M2 лога достаточно.

Но обещание комментария «fix up the header so a consumer doesn't see a bogus
JMSDeliveryTime» выполняется только для непepersistent — см. **N15**.

### Покрытие B4 тестами

- `testAbsurdDeliveryTimeDoesNotHangTeardown` — end-to-end через публичный API,
  ровно тот сценарий, которым я воспроизводил дефект в раунде 2 (публичное поле,
  никаких `SendOptions`). Проверил на невырожденность по другой оси: destination
  очередного семейства получает default-консьюмера в `Session::createDestination`

- `testSchedulerWaitDeltaCappedAgainstOverflow` — детерминированный, без часов и

## Что ещё подтверждено закрытым

### N9 — асимметрии не возникло, политика теперь последовательная

`enqueueOrSchedule` после `stop()` разделяет по долговечности: персистентное —
**drop** с `poco_warning` (запись остаётся в storage, реплей переставит таймер
корректно), неперсистентное — немедленная доставка (второй жизни у него нет,
поздно-но-доставлено лучше, чем потеряно). Это ровно то, чего просил N9:
персистентный случай приведён к той же политике, что и дренаж в `stop()`, а
расхождение для неперсистентного явно обосновано в комментарии, а не оставлено
молча. Новой асимметрии между drop и немедленной доставкой не вижу — асимметрия
теперь по оси долговечности, и она семантически правильная.
Путь по-прежнему недостижим в проде (`stop()` зовётся только из `~Destination`
после `_consumers.clear()`), но контракт зафиксирован верно.
Тест `...AfterStop` остаётся зелёным и продолжает пиннить ADR-0006-часть
(поток не стартует после `stop()` → нет joinable-потока в `~std::thread`).

### N10 — исправлено

`JMSXDeliveryDelay` в ADR-0007 больше нет (grep по `arch/` чист), «неотложенные»
исправлено. Остальное содержание ADR не менялось, оценка раунда 2 в силе.

### N12 — практически закрыто

`kDelayMs` поднят 150 → 400 (тесты #1, #3, `...OnReceipt`) и 500 (рестартовые).
Запас на самом узком тесте вырос со ~100 мс до ~350 мс. Шва для подмены часов
по-прежнему нет (структурно), но 8 прогонов подряд дали разброс 43 мс на 3.5 с —
риск на нагруженном раннере снижен втрое, чего я и просил. Считаю достаточным
для M2; долгосрочная рекомендация (инъекция `_now`) остаётся в силе как
пожелание, не как требование.

## Замечания раунда 3 (не блокирующие)

### N15. Правка заголовка при клампе не видна приложению для персистентных

Комментарий в `enqueueOrSchedule` обещает «fix up the header so a consumer doesn't
see a bogus JMSDeliveryTime». Для персистентного сообщения это не выполняется:
`Consumer::preparePush` сериализовал байты (и записал их в storage) **до** клампа,
с исходным абсурдным значением, а `Consumer::recv` на быстром пути перечитывает
заголовок из `_cachedStorageBytes` через `fromBytes` и затирает поправленный ноль.

**Воспроизведено, не выведено.** Отдельная программа, слинкованная с объектниками
`cmake-build-debug` (дерево не менялось): `Exchange` → `Session` → персистентное
`TextMessage` с `jmsHeaders.deliveryTime = INT64_MAX`, `send()` без `SendOptions`:

```
RESULT: delivered; JMSDeliveryTime seen by application = 9223372036854775807
        expected after clamp fix-up = 0
```

Сообщение доставляется немедленно и корректно (B4 закрыт — зависания нет), но
приложение получает `JMSDeliveryTime = INT64_MAX`. После рестарта то же самое:
`deliveryTimeFromStorageBytes` вернёт 0 для планирования, а `recv` прочитает
исходные байты из storage и снова отдаст абсурдное значение.

Это тот же класс, что закрытый в раунде 2 **B2** — «заголовок и кэш
сериализованных байт разъехались», — вновь возникший в новом коде раунда 3, и
новая асимметрия persistent/non-persistent (для неперсистентного правка работает).
Блокером не считаю: вход по определению уже мусорный, доставка корректна, потери
и зависания нет, инвариант проекта не нарушен, пункт `Test plan` не затронут.
Фикс однострочный — рядом с `msg->jmsHeaders.deliveryTime = 0` добавить
`msg->patchCachedDeliveryTime(0)` (метод уже существует с раунда 2). Просьба
сделать при ближайшем касании файла и закрыть тестом на персистентном сообщении.

### N16. Остаточное переполнение в `cappedWaitDeltaMs` — по стороне `now`, не по стороне дедлайна

`nowMsValue + kMaxWaitMs` переполняется при `nowMsValue > INT64_MAX - kMaxWaitMs`.
UBSan на `-O2` это подтверждает явно:

```
runtime error: signed integer overflow: 9223372036854775806 + 86400000 cannot be
represented in type 'int64_t'
```

и результат при этом неверен (`cappedWaitDeltaMs(INT64_MAX, INT64_MAX-1)` = 86400000
вместо 1). Оцениваю как приемлемое:

- недостижимо из `run()` — `nowMsValue` там всегда показание реальных часов (~1.7e12);
- допущение записано в комментарии функции честно и явно, а doc-комментарий в
  заголовке обещает устойчивость только по стороне `deadlineMs` — то есть
  контракт не переобещан;
- **направление отказа безопасное**: результат всё равно лежит в `[0, kMaxWaitMs]`,
  то есть худшее следствие — «поспать дольше, чем нужно», а не спин. Режим отказа
  B4 закрыт и здесь.
- тест сознательно останавливается на единицу ниже края (`hugeNow`), то есть
  граница осознана автором, а не пропущена.

Хардненная версия — `if (nowMsValue > std::numeric_limits<int64_t>::max() - kMaxWaitMs)
return kMaxWaitMs;` первой строкой. Одна строка, если захочется закрыть до конца.

Родственный нит: `enqueueOrSchedule` по-прежнему считает `deliveryTime - now >
kMaxFutureHeaderMs` — вычитание до сравнения, ровно тот паттерн, который раунд 3
убрал из `cappedWaitDeltaMs`. Здесь он безопасен (`deliveryTime > 0` и `now ≥ 0`
при исправных часах), но при часах, выставленных до 1970, `now` отрицателен и
разность переполняется. Для симметрии стиля лучше `deliveryTime > now +
kMaxFutureHeaderMs` (правая часть переполниться не может: ~1.7e12 + 3.15e11).

### N17. Мелочи

- `deliveryTimeFromStorageBytes` читает `Poco::Timestamp()` **на каждую запись**
  внутри цикла реплея — путь стартовый, не горячий, но при большом storage это
  N обращений к часам. Дешевле вычислить границу один раз в `replayFromStorage` и
  передать вниз.
- `testAbsurdDeliveryTimeDoesNotHangTeardown` на ветке отказа делает
  `teardown.detach()`, а отсоединённый поток держит ссылку на локальный
  `exchange` тела теста. Если тест когда-нибудь провалится, висячая ссылка
  способна уронить процесс уже на других тестах и сделать диагностику
  запутанной. Комментарий этот компромисс признаёт; как минимум стоит перевести
  `EXPECT_TRUE` в `ASSERT_TRUE`, чтобы падение было терминальным для теста.
- N14 (`kMaxFutureHeaderMs` применяется и к `timeToLive`) закрыт оформлением:
  обоснование записано в `Message.h` внятно и по существу. Формально это всё ещё
  дельта за пределами спеки 13 (ужесточение ingress спеки 44) — просьба
  упомянуть строкой в доке фичи, чтобы «TTL больше 10 лет теперь бросает» не
  всплыло сюрпризом.
- N2, N7 остаются зафиксированными как известные и отложенные; возражений нет.
